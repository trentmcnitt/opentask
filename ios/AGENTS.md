# iOS App — Development Reference

Detailed development reference for the OpenTask iOS companion app. The root `AGENTS.md` § iOS and macOS apps owns the overview: targets, shared-code rules, the server endpoints the native apps call, and the contract-fixtures rule. This file holds the implementation detail.

## Notification Mechanisms

1. **Default actions** (AppDelegate): Done, +1hr, All +1hr, then one bulk-snooze-to-slot action per cached time slot (`TimeSlotStore`, "All → Next period" plus "All → \<slot label\>", earliest first) — used from lock screen or when content extension is unavailable. Which server call each action makes, and which delivered banners go, is `NotificationActionRunner` (`ios/Shared/NotificationActionRunner.swift`, tested by `NotificationActionRunnerTests`), shared by the phone's `AppDelegate`, `MacAppDelegate`, `WatchAppDelegate` and the content extension; each delegate keeps only its navigation, haptics, error banners, badge and completion handler
2. **Silent dismissal**: Server sends `content-available: 1` push with `type: "dismiss"` when a task is snoozed/completed from the web UI — iOS app removes matching delivered notifications
3. **Content extension** (long-press): Interactive 3x4 snooze grid (presets, increments, decrements) — extension makes API calls directly and dismisses. The preset row is the user's pad presets (`pad_presets` from `GET /api/user/preferences`, 2026-10-21 — the web Quick panel's four buttons, editable in Settings and optionally linked to a period; the server sends each time already resolved). The iPhone app caches them in `PadPresetStore` (App Group, `padPresets.cache`) from `refreshSlotActions()` on launch and foreground; the grid reads the cache when it's built and shows the defaults (9:00 AM, 12:00 PM, 4:00 PM, 8:30 PM) until the first fetch, or when the cache isn't four valid times. A change in Settings, or a linked period's new start time, reaches the grid the next time the app is opened
4. **Slot batch checklist** (`SLOT_REMINDER`, long-press): a §6 time-slot notification expands into a checklist of that slot's pending reminders (fetched live from `GET /api/reminders`, filtered by the payload's `slot_id`); rows stage check-marks, the "Complete N checked" action button commits them in ONE `POST /api/tasks/bulk/complete`, and "Complete all" takes the whole slot. Titles wrap in full, and the extension asks for SwiftUI's own ideal height (`UIHostingController.sizeThatFits`, re-measured on the host's `preferredContentSizeDidChange`; the bottom pin yields rather than compressing rows — 2026-09-24, the grouped-notification row overlap). **Device-test only** — content extensions cannot be invoked in the simulator (see below), so the long-press path is unverifiable there and must not be attempted.
5. **"AI finished" actions** (`TASK_ADDED`, 2026-09-29): the quiet push for a just-added task (`buildEnrichedNotification`, `src/core/notifications/apns.ts`) carries **Done** and **Delete** (`.destructive`, no `.authenticationRequired` — an undoable soft delete). Registered with the others in `registerNotificationCategories()`, so iPhone, Watch and Mac all get them; `NotificationActionRunner` sends `markDone` / `deleteTask` (`action: "delete"` on `POST /api/notifications/actions`). Not a content-extension category, so iOS shows its default expanded view. Since 2026-10-05 the "AI failed to process" push for a failed enrichment (`buildEnrichmentFailedNotification`) uses the same category with its own `thread-id`/collapse id `ai-failed-<id>`; the runner keys on category and `taskId` only, so nothing native changed.
6. **Bulk snooze feedback** (`TASK_SUMMARY`, collapse id `sweep-result`, 2026-10-04): after a token sweep leaves High/Urgent overdue, the server sends a soundless result banner (long-press opens the bulk grid). Surfaces that show the result themselves (Home Screen quick actions, watch sheet and Smart Stack card, Mac menu-bar panel) send `notify: false` through `APIClient.snoozeOverdue*(notify:)`; see docs/NOTIFICATIONS.md § Bulk snooze feedback.
7. **Body tap on any task notification**: `.openTask` → `WebViewManager.navigateToTask` → `/?task=<id>` (`DeepLinkRouter.notificationTaskPath`). The dashboard brings the row into view and selects it; nothing opens (see Deep links below). The Watch has no web view and ignores the tap beyond opening its app.
8. **The deadlines-page nag** (2026-10-22, `kind: "deadlines"`, no category, no `taskId`, a silent banner): a body tap is `.openDeadlines` → `WebViewManager.navigate(path: DeepLinkRouter.notificationDeadlinesPath)` → `/?tasks=deadlines`, the dashboard's Tasks card on the task queue's deadlines page (`src/lib/tasks-panel-link.ts`); the Watch only opens its app. A build from before 2026-10-22 ends at `.missingTaskId` and comes forward where it was. See docs/NOTIFICATIONS.md § The deadlines-page nag.
9. **The named reminder push** (`REMINDER_NAG`, 2026-10-26, PR 3 of the named pushes): one Medium+ reminder by its own title, thread `ot-reminders`, collapse id `reminder-<id>`; data `taskId` and `reminder_day` (the OpenTask date), no `priority`. Registered with the others in `registerNotificationCategories()` (iPhone, Watch, Mac) with ONE action, **Considered** — the `DONE` identifier under its own title. `NotificationActionRunner` gives the category its own case: Considered sends `APIClient.markDone(taskId:day:)` (`done` with `day` on `POST /api/notifications/actions`) and returns `.reminderConsidered(taskId:considered:)`; the server's `considered: false` (another day's banner, or a reminder no longer waiting) is a success, never an error banner. No `reminder_day` → nothing sent; every other button → `.ignored`. The banner goes before the call (as for any task banner); a body tap is `.openTask` → `/?task=<id>`, which the web forwards to /reminders, and the Watch only opens its app. A sweep never clears it: a sweep clears only the moved tasks' banners (item 10), and never moves a reminder. Not in the content extension's categories, so iOS shows its default expanded view. See docs/NOTIFICATIONS.md § Named reminder pushes.
10. **Which banners a sweep clears** (2026-10-26): exactly the moved tasks', nothing else. Both bulk snooze routes return `moved_ids` (queued tasks included), decoded as `APIClient.BulkSnoozeResult.movedIds`; `dismissNotificationsAfterSweep` removes every delivered banner whose `taskId` is in it (`bannerIdentifiers`, `ios/Shared/SweepDismissal.swift`, the same match the silent `dismiss` push uses). Every sweep path calls it: the runner (notification "All →" actions, the content extension), `QuickActionHandler`, the Tasks widget's `SnoozeAllOverdueIntent` (iPhone and Mac), `WatchViewModel.bulkSnoozeOverdue`, the Smart Stack's `OverdueSweep`, the Mac's `MenuActions` and `MenuBarModel.snoozeAll`. It replaced the priority ceiling (`sweepDismissCeiling`), which also cleared the period push, "AI finished", the deadlines nag, reminder banners and overdue banners the sweep held back. The server's own `dismissNotificationsForTasks(snoozedIds)` clears the same set on the other devices. An older server sends no `moved_ids` (`movedIds` nil, not empty), so nothing is cleared locally. The same ids decide what leaves the watch's cached task list after a Smart Stack sweep (`WatchCache.removeSweptOverdueTasks(after:)` → `BulkSnoozeResult.tasksLeft(after:)`, `ios/Shared/SweepSummary.swift`): exactly the moved tasks, and from an older server the old guess from the counts (every overdue task but Urgent, reminders and quotas; High only when none was skipped). See docs/NOTIFICATIONS.md § Which banners a sweep clears.
11. **The named quota-prompt push** (`QUOTA_NAG`, 2026-10-26, Push PR 4b): one waiting prompt of a Medium+ quota, titled with the quota's short title, its body count-first ("Morning · 1/3 this week"); thread `ot-reminders`, collapse id `prompt-<prompt_key>`; data `taskId` (the quota) and `prompt_key` (`QuotaNagKey.promptKey`), no `priority`, no `badge`. Registered with the others in `registerNotificationCategories()` (iPhone, Watch, Mac) with TWO actions, **Considered** (`NotificationAction.considered`, `CONSIDERED`) and **Did it** (`.didIt`, `DID_IT`); no snooze, no delete, not a content-extension category. `NotificationActionRunner.performQuotaNag`: Considered → `considerPrompts(keys: [key])` (no `source`), Did it → `didPrompts(keys: [key], source: ProgressSource.forNotificationActions)` (`watch` / `mac` / nil on the iPhone); no `prompt_key` → nothing sent; any other button → `.ignored`. The banner goes before the call (`handle(_:)`). The server's **400** (another day's key): Considered → `.promptConsidered` (quiet, as a success); Did it → `.promptDidStale` — nothing was logged, so the device shows `NotificationActionRunner.staleDidMessage`, "That was yesterday's — open OpenTask to log it" (the web's words): the Watch with its failure buzz and `postLocalErrorNotification`, the iPhone and Mac with `postLocalNotice` (a soundless local notification; their only failure feedback before was a log line). Any other error propagates to each device's failure handling. `.promptDid` → `WidgetCenter.shared.reloadAllTimelines()` on all three: the app processes don't compile `WidgetStore`, so there is no cache write-through from here — the reload is what `QuickActionHandler` and `WatchViewModel.actOnPrompt` do, next to the server's (budgeted) widget push. Considered relies on the widget push. A body tap is `.openPrompt` → `PromptDeepLink.webPath(promptKey:)` → `/reminders?prompt=<key>` (phone, Mac; the Watch only opens its app); a payload without a key falls back to `.openTask`. The phone and Mac skip `refreshBadgeFromServer()` after it (a quota is never in the badge). **Dismiss by key:** the silent `dismiss` push may carry `promptKeys` (`QuotaNagKey.dismissPromptKeys`); every delegate passes them to `removeDeliveredNotifications(forTaskIds:promptKeys:)`, and `bannerIdentifiers` closes a banner with a `prompt_key` only when its key is listed (a daily quota's Morning and Evening banners share a `taskId`), every other banner by `taskIds`; a dismiss without `promptKeys` closes by `taskIds` alone, prompt banners included. A sweep never clears it (item 10: a quota has no target, so it is never in `moved_ids`). See docs/NOTIFICATIONS.md § Named quota-prompt pushes.

## Widgets (`OpenTaskWidgets`)

WidgetKit extension (`io.mcnitt.opentask.widgets`, iOS 17, App Group `group.io.mcnitt.opentask`) with three independent widget kinds — `OpenTaskReminders`, `OpenTaskTasks`, `OpenTaskTrack`. Separate kinds, not one configurable widget, so each gets its own refresh budget (REDESIGN-V03 §8).

| Kind                | Shows                                                                                                             | Primary size                                       |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `OpenTaskReminders` | Current time slot's reminders, trailing check-off buttons (§6), a per-slot progress strip                         | `systemLarge`                                      |
| `OpenTaskTasks`     | Today's dated tasks by project (plus a Today/Up next unified pair, §below) — reminders AND tracked items excluded | `systemLarge`                                      |
| `OpenTaskTrack`     | Every `progress_target > 1` quota, `+1` buttons (§5)                                                              | `systemSmall` (ring + fraction, §8's flagship 2×2) |

All three support `systemSmall` / `systemMedium` / `systemLarge` / `accessoryRectangular` / `accessoryCircular`. The Reminders and Tasks 2×2s are glanceable-only (a headline number, one item, whole-card deep link) — at ~126pt across, per-item buttons would be mis-tap machines.

- **Data**: timeline providers call `APIClient` (`GET /api/reminders`, `/api/tasks?done=false`, `/api/projects`) with the Keychain credentials shared through the App Group. Tasks and Track are two slices of ONE payload and share `TaskFeed` (fetch + cache + fallback + optimistic staging) — never add a second fetch of `/api/tasks`. Every successful payload is cached in App Group `UserDefaults` (`WidgetStore`); a failed fetch renders the cache with an "as of HH:MM" note rather than blanking.
- **Interaction**: `AppIntent` buttons only — check-off, `+1` progress, and the `‹ ›` pagers. Widgets get no swipe gestures (§8), and Lock Screen accessory families are glanceable-only because interactive widgets are inert on a locked device.
- **Tap targets (2026-09-22, the misclick fix; check-off moved 2026-09-23; background tap removed 2026-09-23)**: only `systemSmall` and the Lock Screen families use a whole-card `.widgetURL` — they are glanceable-only with nothing else to hit. `systemMedium`/`systemLarge` have no card-wide link: the header (title/count text, wrapped in its own `Link` to the section) opens Reminders/Tasks/Track's quotas surface, each row's `Link` opens that item, and `Button(intent:)` controls (check-off, `+1`/`−`, chevrons) stay buttons. `WidgetSignedOutView`'s signed-out message follows the same split — `compact` (small/accessory) keeps a whole-card `.widgetURL`, non-compact wraps just the message TEXT in a `Link` — it was the one remaining `.widgetURL` a source-level audit found on `systemMedium`/`systemLarge` when Trent asked that "tapping the widget in general should not bring me to the app" (2026-09-23). Caveat: that view only renders SIGNED OUT, and Trent's own phone is signed in — so this fix is unlikely to be what he actually felt. WidgetKit doesn't expose per-element hit targets to simulator automation (same class of limitation as notification content extensions — see below), so a background tap couldn't be tested against the fix; the community-reported `Link`/`Spacer` hit-test bleed two sentences below remains the leading unverified suspect and needs an on-device check (empty area below the last row, and empty area right of a short title — the latter may be the row `Link`'s intentional `maxWidth: .infinity` fill, not a bug). Per Apple's WidgetKit model a tap that lands on none of those — e.g. a near-miss on `+1` — should hit nothing, rather than deep-linking away from where the user was aiming; this is unverified on-device (there are community reports of hit-testing bleeding onto an adjacent `Spacer` when a container holds multiple `Link`s, so confirm a near-miss really is inert before relying on it). Reminders' and Tasks' check-off moved from the row's LEADING edge to its TRAILING edge (2026-09-23, thumb reach on a Large widget) — the title `Link` now fills the leading space and the marker (circle for Reminders, project-colored square for Tasks — see below) sits at the trailing 36pt column; they are plain `HStack` siblings with fixed/flexible widths, not overlapping views, so this doesn't touch the hit-testing question above. Tasks' marker no longer encodes priority (a filled dot by priority color) — priority still reads through the title's font weight — and instead outlines in the task's PROJECT color (`WidgetTheme.projectColor`, same source as a project header's dot), which is also how the unified "Up next" scope (all projects, due-soonest) tells rows apart. (Superseded: priority colors 2026-10-11, then High/Urgent only with the row corner 2026-10-16 — see § Task segments and the target model, "Tasks widget".)
- **Optimistic (§8)**: intents stage their effect in `WidgetStore` and repaint from cache before the server call — a completion tombstones (row vanishes, reappears on failure), and staged progress renders as `progress_current + net pending delta` (a counter, so rapid `+1`s and `−1`s all draw), floored at 0. **The cache must stay server-true, because the fast path trusts it (2026-09-24, the stale-count fix)**: a reload within 10s of ANY widget tap (`hasRecentInteraction()` — a toggle, a pager, another chip) repaints from cache, and so does the server's widget push that lands ~2s after a mutation. So every mutating intent either writes the confirmed result INTO the cache (`confirmCompletion`; `confirmProgress`, from the task `POST /api/tasks/:id/progress` returns) or declares it stale (`clearInteraction()` — snooze, restore, Undo/Redo), which sets per-payload fetch-required stamps the fast paths honor (`canRepaintTasksFromCache`/`canRepaintRemindersFromCache`) until a fetch that STARTED after them lands. Before this, a `+1`/`−1` only retired its staged delta, and a tap within 10s of the Takeback toggle (i.e. every takeback `−1`) drew the pre-tap count back on round 2 and on the push — Trent took Rowing Sets 3/3 → 0/3 on the server while the widget stayed at 3/3.
- **Outbox — check-offs don't wait for the server (2026-09-30, instant check-off)**: a reminder/task check-off (`CompleteTaskIntent`), a quota prompt's considered/did-it (`ActOnPromptIntent`) and a Quotas `+1`/`−1` (`IncrementProgressIntent`) stage their optimistic marker, append the mutation to a persisted queue in the App Group (`WidgetStore`'s "Outbox" section) and RETURN; `WidgetOutboxDrainer` (`OpenTaskWidgets/WidgetOutbox.swift`) sends it. Why: the tap's only free repaint on iOS is the interaction reload after `perform()` returns, and WidgetKit runs one extension's intents serially, so awaiting the request in `perform()` made the first visible change cost a round trip plus a timeline pass, and a fourth rapid tap wait for the first three's requests. Now the repaint needs no network and the next tap's intent starts at once. **One request per tap**, oldest first (not `bulk/complete`): each tap stays its own server undo entry, so Undo after four quick taps takes back the last one, and a refused id can't fail a whole batch (`validateBulkTasks` refuses the batch when any id is already done). **When it's sent**: kicked (not awaited) at the end of each of those intents, inside `performExpiringActivity` on iOS (an activity assertion on macOS), and by every provider's `getTimeline` after it has handed WidgetKit its timeline — so any later reload (scheduled, pushed, the app's leave-the-app reload) retries whatever is stuck. Undo/Redo, a DONE-row restore and a prompt put-back `drain()` it first, so they act on the tap the user just made; with taps still queued after that (offline), Undo takes back the newest unsent tap locally with no server call, and a restore/put-back of a still-queued tap cancels it locally. **Idempotency**: `sendingSince` is persisted before a request goes out, so a send cut off by suspension is detectable. A completion is never blindly resent — completing a recurring task twice advances it two occurrences — the entry records the occurrence's `due_at` at the tap, and before any resend (or after any failure) the drainer reads the task back (`APIClient.fetchTaskState`, raw `GET /api/tasks/{id}`): done or `due_at` moved on = landed; gone = dropped; unchanged = send. Prompt considered/did-it are idempotent per key, so they're simply resent. A `+1`/`−1` can't be verified, so it's at-most-once, as before: provably unsent errors (no connection, 401/408/429) retry, anything else retires the staged delta and fetches; an unsent `+1` older than 90s is dropped with its staged count. **Failure**: a definite refusal (4xx, or giving up after 8 attempts / 6h) clears the marker and the auto-advance, marks the payload fetch-required and repaints the tapped kind — on iOS a budgeted reload, the one this design adds, on failure only (the free reload ran before the failure was known). While queued, an item stays hidden past the 90s tombstone (`pendingCompletions`/`pendingPromptActions` include the queue) but doesn't keep the 10s fast path alive. **Known trade-off**: a did-it that completes a sibling prompt in another period (`confirmPromptAction`'s re-count) shows on the next repaint, not the tap's own. `CompleteSelectedTasksIntent` (select-mode Done) is unchanged: a deliberate multi-pick, one request and one undo entry. Tests: `WidgetOutboxTests`.
- **Chevrons**: `ChevronPager` is told about its ring — it dims when there is nowhere to page. Glyphs only: it used to name the adjacent page beside each glyph in `systemLarge` (`‹ Midday   Evening ›`, truncated ~10 chars), which Trent read as "cut off" on first use (2026-09-11). The header already names the page you are on. 40pt hit targets are a floor, not a suggestion. **Where they are (2026-09-25)**: Reminders' header on `systemMedium` AND `systemLarge` (the period ring, `ShiftReminderSlotIntent`; accessibility "Previous period"/"Next period"), laid out undo/redo then `‹ ›` at the right edge. Tasks' header pair was replaced on 2026-10-12 by `TasksPageControl` (see the Tasks page-control bullet below). Reminders `systemLarge` had dropped them on 2026-09-24 for the slot strip's tappable segments; Trent asked for them back on 2026-09-25. They don't read as the bottom `‹ n/N ›`: the header pair changes the period (the title beside it changes and the page resets to 1), the small bottom pager pages within it and carries its count. Quotas dropped its header pair for good (it paged the same pages as its bottom pager; Trent couldn't tell what it switched). **Reminders header fallback**: when title + undo/redo + chevrons don't fit on one line ("Early morning" at XXX Large on a 402pt iPhone 16 Pro ran a few points past the card, and a title that may not truncate pushes the whole card sideways), a `ViewThatFits` moves undo/redo to the right end of the subtitle line, with their vertical padding cancelled so the header's height doesn't change. Renders: `~/hub-store/capabilities/opentask/screens-2026-09-25-reminders-chevrons/`.
- **Row counts (2026-09-24, height-based paging)**: the Reminders and Tasks lists have no row count and no `ViewThatFits` any more. The header (and Reminders' slot strip) are laid out for real; a `RenderedTextReader` takes the remaining height and hands the list `WidgetTextMetrics` — the text size from the view's own `\.dynamicTypeSize` (never a trait-less `UIFont.preferredFont`, which answers for the process, not the widget), with the measuring font scaled to SwiftUI's drawn width and the line height taken from SwiftUI's drawn pitch, both read back from clear probe texts (at XXX Large, UIKit says 25.06pt per `.subheadline` line; SwiftUI draws 24.13). Every row's height is computed up front — title lines via `WidgetTheme.measuredLineCount` at the row's real column, UNCAPPED on every family and platform (the iOS 3-line cap and systemMedium's one-line rows were removed later on 2026-09-24 — Trent: never truncate a reminder/task title), clamped only so no row is taller than the whole list area (a title that long gets a page to itself and ends in "…") — and the row is FRAMED to exactly that height. `WidgetTheme.pages` (the loop is `ListPaging.pages` in `ios/Shared/PageAnchor.swift`) then fills each page greedily until the next row genuinely doesn't fit, breaking only between whole rows; at rest the partition is a pure function of the list, so the page count is the same whichever page is showing — while the user is tapping, the page on screen is ANCHORED instead (see the List paging bullet). The layout adds exactly what the budget subtracted: rows in their own `rowSpacing` stack, then a `Spacer`, then the bottom row with its own `rowSpacing` of top padding (a spaced outer stack would put a second gap around the Spacer that no budget counted). iOS `systemLarge`'s check-off bleeds its tap target half a `rowSpacing` into the gaps instead of forcing a 36pt row; `systemMedium` iOS rows wrap too, on the 36pt finger floor (no pager there, so it just shows fewer rows). Tasks' due label is `fixedSize` (it used to wrap on its own, handing width back to a title measured without it); a two-part label (day word + time: "Tomorrow" / "4:00 pm", "Sat" / "9:00 am", "Oct 1" / "9:00 am") ALWAYS stacks, day over time, right-aligned, on every family — one rule since 2026-09-24 (it used to stack only where that made the row shorter, so adjacent rows mixed "Tomorrow 9:00 am" inline with "Tomorrow" over "12:00 pm"); a time-only (today) or day-only (date-only task) label is one line, and every row's measured height includes the two-line label. **Why (Trent's phone, 2026-09-24, XXX Large text)**: the old `ViewThatFits` ladder sliced UNIFORM pages of whichever candidate fit, so the page holding the longest rows set every page's size ("7 left" as 1/4 with two rows; "26 due" as 13 pages of two), and each candidate sliced its own page from the stored index, so page 2 of the same list read "2/2" with one row. See `WidgetTheme.pages`' doc and the "row-height truthing" addendum in `WidgetTheme.swift`.
- **Budget (corrected 2026-09-25, "Quotas still 0/2 after did-it")**: on iOS the ONLY free reload a tap gets is WidgetKit's own reload of the TAPPED kind after `perform()` returns — chronod logs it `interaction-immediate-free`. Every `WidgetCenter.reloadTimelines(ofKind:)` the extension issues, for its own kind or another, is logged `externalRequest(… WidgetCenterServer …)-immediate-budgeted` and charged to that kind's daily budget, and so is the server's widget push. The old rule here ("reloads triggered by a widget's own intent are free") was wrong, and every intent spent budget reloading its own kind twice — the pre-server one never even ran ("Delaying reload … because entry is paused" until `perform()` returned, then replaced). The bug it caused: did-it on the Reminders widget's "Piano Scales · 0/2" prompt; prod took it (1/2), the intent wrote the returned quota into the cache, the push went out 2s later — and the phone's Quotas widget still drew 0/2 until the app was opened (its leave-the-app reload fetched at 10:59:06). Nothing was wrong with the data: the same taps on the iOS 27 simulator (idb HID taps; the sim doesn't enforce budgets) rebuild Quotas from the confirmed cache every time, with no fetch. The phone just never ran the budgeted Quotas reload — and a Reminders tap has no other way to reach Quotas. Trent's iPhone confirms it (read-only `idevicesyslog -p chronod`, 11:33 the same day): `budget: com.apple.dasd.widget_io.mcnitt.opentask.widgets::OpenTaskTrack, budget: -0.357` (Tasks 0.63, Reminders 22.3), a queued Track reload sitting unrun until a push replaced it, and the extension's widget-PUSH budget at `-17` ("Reduced budget for io.mcnitt.opentask.widgets to: -17") — so the server's push can be throttled too. Same shape as PR #82's "Quotas stuck at 1/2 after Undo". Rule now: intents never reload their own kind on iOS (`reloadTappedWidget(kind:)` is a no-op there, kept at each call site to say where the repaint comes from), and ask for another kind only when the tap changed what it shows (prompt did-it/considered → Track; Quotas `±1` → Reminders; Undo/Redo → the other two). Since the outbox (2026-09-30, above) those cross-kind requests are made by the drain after the server has answered, once per drain pass rather than once per tap, and a failed check-off's repaint of its own kind is the one budgeted reload on the failure path. macOS logs no interaction reload and its extension reloads are free (09-23/24: `externalRequest … free`, `push … free`), so there the explicit tapped-kind reload stays, both rounds. To check a reload's class: `xcrun simctl spawn <udid> log stream --predicate 'process == "chronod" AND eventMessage CONTAINS "opentask"'` and read the `Reload with configuration [...]` lines. App-triggered reloads are free. The app reloads all kinds as it goes to the BACKGROUND (`OpenTaskApp`'s scenePhase `.background`) — not on activation any more (removed 2026-09-24: the user can't see a widget while in the app, and the leave-the-app reload plus the server's widget push already cover what changed). Unprompted refreshes are budgeted, so the timeline policy is `.after(+30 min)` plus zero-cost entries pre-scheduled at each time-slot boundary and upcoming due time.
- **Widget push token registration (2026-09-25, "the Mac has no row in widget_push_tokens")**: the Mac's App Group held `widgetPush.registeredToken` = `widgetPush.pendingToken` = `8038d39b…`, prod had no row for that token (only the iPhone's and the watch's), so `WidgetPushRegistration.retryIfNeeded()` skipped it on every reload — for good, because WidgetKit re-delivers the SAME token after a reinstall (chronod: "Public token has not changed") and the App Group, "registered" mark included, survives deleting the app on macOS. Two ways the row disappears without the extension knowing: (1) the extension itself used to DELETE it on a `pushTokenDidChange` with no widgets, and the Mac's chronod sends exactly that on every start while the widgets are on the desktop (09-23 19:02:52 `initial` reloads of all three placed kinds, then 19:03:04 "Sending 0 WidgetInfo instance(s) to 1 PushHandler instances" after a reboot; 22:09:01 the same after the reinstall's `killall chronod`); (2) the server deletes a token when APNs answers Unregistered/BadDeviceToken, e.g. while the app is deleted mid-reinstall (`sendApnsWidgetReload`). Prod's journal only goes back to 09-25 04:14, so which one removed row 8 isn't recorded. Fix: an empty list no longer unregisters (a token with no widget costs one ignored push; APNs retires dead ones), and `savePending` forgets the old confirmation so every delivery is POSTed (the server upserts). The watch copy got the second half then, and the first on 2026-09-29 (`WatchWidgetPushHandler` only logs an empty list too, until watchOS is shown to behave differently). Since 2026-09-29 there is no copy: both handlers are thin wrappers over `WidgetPushRegistration` in `ios/Shared/`, configured per extension. - **A widget tap landing on the wrong tab (2026-09-23)**: a deep link tapped while the app is backgrounded on a NON-dashboard tab (e.g. Reminders, reached by an in-page SPA transition, never a native `navigate()` call) could open the app but leave it on the old tab instead of switching. Root cause, reproduced in the simulator (`ios/OpenTask/WebView.swift`'s `Coordinator`, instrumented with temporary `decidePolicyFor`/`didStartProvisionalNavigation`/`didFinish`/`didFail` logging — reached via a deep link to `/reminders` rather than an actual in-app tab tap, since the tab tap's pushState transition is invisible to this instrumentation; the race mechanism is the same either way): coming to the foreground fires TWO navigations at once — our own `WebViewManager.navigate(path:)` from `handleWidgetLink`, and a client-side redirect fired from the PAGE ITSELF (`router.push(loginUrlFromLocation())`, e.g. in `reminders/page.tsx`) — confirmed client-side (not our own request redirected server-side) because the `/login` this raced carried `callbackUrl=/reminders`, the OLD page's `window.location`, which only that still-loaded page's own `loginUrlFromLocation()` can produce. The likeliest trigger — not directly observed, but the only automatic session-recheck this app wires up — is `SessionProvider`'s NextAuth default `refetchOnWindowFocus: true`, firing on the same foreground/focus event and finding the session momentarily stale right after resume. When that competing redirect wins the race (cancelling our own request — logged as `didFailProvisionalNavigation`/`NSURLErrorCancelled` immediately before the `/login` decidePolicyFor), the existing `/login` rescue (`resumePath(fromLoginURL:)`) used to trust the redirect's callbackUrl unconditionally — which names the OLD tab, not the tap's actual destination. Fixed by tracking whether the navigation immediately preceding a `/login` bounce was cancelled (`Coordinator.lastNavigationWasCancelled`); when it was, `resumePath` trusts `lastRequestedPath` (set synchronously by `navigate(path:)`, before either navigation's network round trip) instead of the callback. See `resumePath`'s doc for the full mechanics and why the ordinary (non-race) case is unaffected. Every backgrounded-deep-link repro run in this investigation — control (dashboard) included — bounced through this `/login` detour once before landing; the fix corrects the destination but not that extra round trip, which may be worth a follow-up look.

### The two project specs

`project.yml` is canonical. `project-sim.yml` is **generated** from it by `ios/scripts/make-sim-spec.py` — it is the same spec minus every target whose `platform` is `watchOS` (currently `OpenTaskWatch` and `OpenTaskWatchWidgets`), because generating and building the canonical spec requires the watchOS SDK to be installed, and without it every `xcodebuild` fails before compiling a single file (including iOS-only builds). The strip is by platform, not by a hardcoded target name/list, so a future watchOS target is dropped from the sim spec automatically.

```bash
python3 ios/scripts/make-sim-spec.py            # regenerate project-sim.yml
python3 ios/scripts/make-sim-spec.py --check    # fail if it's stale
cd ios && xcodegen generate                     # canonical (OpenTask.xcodeproj)
cd ios && xcodegen generate --spec project-sim.yml   # sim (OpenTaskSim.xcodeproj)
```

Never hand-edit `project-sim.yml` — add targets to `project.yml` and regenerate, or the new target silently builds on one spec and not the other.

- **Overdue mode — the sharing rule**: (1) a sweep result from the last 2 min wins; (2) else if any overdue task is bulk-snoozable (priority < 4) the card becomes "N overdue" with two side-by-side buttons (2026-09-28): "+1h", filled as the default (`SnoozeOverduePlusHourIntent` → `POST /api/tasks/bulk/snooze-overdue` `delta_minutes: 60`, an hour from now), and "⏭ <next slot's time>" (`SnoozeOverdueNextPeriodIntent` → the same endpoint with `slot: "next"`) — the watch bulk sheet's exact calls, then shows the server's real counts ("Deferred 2 · Moved to Midday · 1 High still overdue"); (3) else reminders. - **Intents live in `WatchShared/`** (`WatchWidgetIntents.swift`) so both watch targets compile them (Apple: add widget intents to the extension AND the app). They run in the extension process; ✓ is optimistic (tombstone in `WatchWidgetState`, reload, then the server call; failure clears the tombstone) and writes through `WatchCache`; both use a TTL-backstopped in-flight claim against double taps.
- **Interactivity support**: every watchOS widget family supports `Button`/`Toggle` intents from watchOS 11 (WWDC24 "What's new in watchOS 11"); Apple's general interactivity page lists accessoryCircular/Rectangular "on iPhone and iPad" — that's the iOS Lock Screen rule, not a watchOS limit. Deployment floor is watchOS 10, where the buttons draw but are inert; the whole-card `widgetURL` still works. Circular/corner stay glanceable (ring + count) on purpose — a button in a watch-face-sized ring is a mis-tap machine.
- **Relevance ("rises on its own")**: `ReminderStackProvider.relevance()` (watchOS 11+ `TimelineProvider` requirement) returns `WidgetRelevance` attributes built from cache: each slot with reminders from its start to the next slot's start (today's still-waiting ones + all of tomorrow's), 3h from now while something snoozable is overdue, 2h from each upcoming due time. `RelevantContext.date(interval:kind: .scheduled)` on watchOS 26 (Apple: "increased priority because it displays important content or requires action"), `date(from:to:)` below. - **Zero-cost flips**: entries pre-scheduled at each slot start, each upcoming due time (12h), and the snooze-result expiry, so the card changes slot / enters overdue mode on time without a fetch.
- **Tap the card** (outside the buttons): `opentask://reminders` or `opentask://tasks` → `WatchRootView.onOpenURL` selects that page of the `TabView` (`opentask://quotas` → Quotas too, for a future card).
- **Staying current (2026-09-24)** — what refreshes the card when data changes elsewhere, fastest first:
  1. **WidgetKit push (watchOS 26)**: `WatchWidgetPushHandler` (a copy of the phone's `OpenTaskWidgetPushHandler`, attached via `#available(watchOS 26.0, *)` `.pushHandler`) registers the extension's token with `POST /api/push/apns/widget-token` (`platform: "watchos"`, `bundle_id: "io.mcnitt.opentask.watchapp"`, `environment` from `ApsEnvironment` — the embedded profile's `aps-environment`, never `#if DEBUG`); the server's widget push then reloads the card after a mutation — coalesced per token since 2026-09-25 (2s settle, at most one push per 5 min window, none during quiet hours; docs/NOTIFICATIONS.md § Coalescing). Token persisted and retried from every `getTimeline` until the server confirms it. Needs `aps-environment` on the widget extension's own entitlements (added). Verified end-to-end in the watchOS 26.5 simulator: token delivered, row registered, dev server → APNs sandbox → simulator `apsd` → `chronod` "Reload success" within ~1s. Apple still budgets these pushes.
  2. **Silent `dismiss` pushes to the watch app** (`WatchAppDelegate.didReceiveRemoteNotification`): the server already sends one to every registered device on each done/snooze/edit; the app now also reloads the card's timeline. Works below watchOS 26 too; best-effort (Apple throttles background silent pushes).
  3. **Opening the watch app** (`load()` on launch and every return to foreground) and every in-app mutation reload the card.
  4. **Own schedule** (`ReminderStackTimeline.refreshDate`): a real fetch every 15 min while any task is overdue, 20 min otherwise, and at the next slot start if sooner — plus the zero-cost pre-scheduled entries above. WidgetKit treats `.after` as a floor, not a promise.

## Quota prompts (quota reminders, phase 2, 2026-09-25)

Every unmet quota also appears as a reminder-like PROMPT in a slot each day (server-computed, `GET /api/reminders` `groups[].prompts`, `QuotaPromptDTO`). Two actions everywhere: the DASHED CIRCLE (where a reminder has its solid circle; `circle.dashed`/`circle.dashed.inset.filled`, lucide `CircleDashed` on the web — 2026-09-25, because Trent read the solid circle as "done"; an eye came first, #96, and read as creepy) = CONSIDERED (handled today, no progress), the square beside the count ("Piano Scales · 1/2") = DID IT (+1, and considered). A thin leading stripe wears the quota's label color (server-resolved `stripe_color`, never green). Prompts come after the slot's reminders and count exactly like reminders — every count reads `ReminderGroupDTO.waitingCount`/`consideredCount`/`hasNothingWaiting`, never `reminders.count`/`considered` alone. Rows are keyed by `prompt_key`: a daily quota's prompts in different slots share one task id. `ReminderGroupDTO`'s memberwise init has NO default for `prompts`, so every rebuild site has to say what happens to them.

- **Reminders widget**: `PromptRow` (label `Link` → `opentask://reminders/prompt/<prompt_key>`, the row on the Reminders surface — see § Deep links; then square, then dashed circle — it stays in the reminder circles' column). Its height is measured from `QuotaPromptDTO.labelText` at `PromptRowMetrics.titleWidth` (card minus stripe and BOTH 36pt controls). Handled prompts join the DONE section, and their filled dashed circle (`circle.dashed.inset.filled`, for a did-it too) PUTS THEM BACK (2026-09-25; it used to be an inert glyph, and a tap there fell through to the row's `Link` and opened the app): `RestorePromptIntent` → `POST /api/quota-prompts/restore` (never `/undone`, which refuses quotas) — the prompt waits again and a did-it's progress comes off. It stages a put-back tombstone by key (`stagePendingPromptRestore`, drawn waiting via `QuotaPromptDTO.putBack()`, count unchanged — only the server knows what a did-it added), then writes the returned quotas into Tasks/Quotas (`confirmTasks`) and the prompt un-handled plus every sibling re-counted into Reminders (`confirmPromptRestore`, which retires the tombstone and calls `requireRemindersFetch` where only the server knows: a once-a-day prompt's "logged today", or a sibling daily row left considered above the new count). A put-back and an action on the same key cross-clear each other's tombstone. Reloads: Track (the other kind), plus the tapped Reminders kind on macOS only — PR #85's budget rule. `ActOnPromptIntent` stages a tombstone by key (`WidgetStore.stagePendingPromptAction`, drawn as handled, not removed), then on success writes the server's answer into both caches: the returned quotas into Tasks/Quotas (`confirmTasks`), and the prompt handled plus every prompt of that quota re-counted into Reminders (`confirmPromptAction`, the prompt twin of `confirmCompletion`, so the next tap repaints from cache instantly and nothing pops back after the tombstone expires). Auto-advance is snapshotted and restored on failure or Undo exactly as for a reminder. A failure (likeliest: a key from before midnight) marks Reminders fetch-required (`requireRemindersFetch`). A Quotas `+1`/`−1` also calls `requireRemindersFetch` and reloads Reminders. It's `requireRemindersFetch`, not `clearInteraction`, because the latter forgets the interaction stamp that keeps Takeback mode armed.
- **Quota segments (2026-10-13, mockup r4 size S4; the web twin is `src/components/QuotaSegments.tsx`)**: a quota's count is N small skewed segments (0.45em × 0.65em of the host font, 0.11em gap, 1pt outline, −16°), indigo per completion, ALL green once met (past the cap too: "3/2" is two green segments), then the period word "today" / "week" / "month" / "year" — "this week" survives only in VoiceOver. ## The OpenTask day ("Day starts at" PR 3, 2026-10-24)

Every native "today" runs on the user's OpenTask day, as the server and the web do (docs/TASK-MODEL.md § The OpenTask day): from the day start (`rollover_time`, 03:00 unless changed) to the next, with the server's task-queue switch on; midnight with it off. A start at or before 12:00 names the day by the date it begins on (with 3:00 AM, Tuesday 01:30 is still Monday); after 12:00 by the next date (with 11:00 PM, Sunday 23:30 is already Monday).

- **One helper:** `OpenTaskDay` (`ios/Shared/OpenTaskDay.swift`), the Swift mirror of `src/lib/opentask-day.ts` — `openTaskDay(of:)`, `dayStart(of:)`, `daySpan(containing:)`, `nextRollover(after:)`, `periodOpensAt`, `minutesIntoDay`, `orderedByDay`, `LocalDate` for the date maths. Same DST rule (a skipped time → the next valid minute, a repeated one → its first instant). Pure: the day start and zone are injected. Nothing native works out a day from `startOfDay` any more; the wall-clock helpers that mirror the server's own calendar rules (`TimeSlotStore.nextPeriodStart`, `DateHelpers.snapToNextPreset`, the Smart Stack's `nextPeriod`) stay as they are, as does `DateHelpers.adjustByDays`.
- **The cache:** `DayStartStore` (App Group, like `PadPresetStore`): the resolved boundary and `week_start`, written by every successful `APIClient.fetchPreferencesPage()` — `refreshSlotActions()` on launch/foreground on the iPhone and the Mac, the watch app's every load (its label fetch) and the Quotas widget's reload; the Tasks and Reminders widgets read what those last wrote. Remembered until the next fetch; midnight only when nothing is known. The watch has its own container, written by its own processes. `DayStartStore.current` is read at the edge (providers, views, `fetchTodaysCompletions`, `fetchReminders`); the pure functions take `day:` explicitly.
- **Surfaces:** the Tasks widget's Today page and counts, done today and Up next (`TaskLists.dueToday`, `TaskDayProgress`), the completions window (`fetchTodaysCompletions`), the due labels (`DueLabel.parts`, `WatchFormatting.dueLine`, the Mac menu bar's), the Reminders widget's and the watch's current slot, slot states and boundaries (`minutesIntoDay` / `periodOpensAt`: with 3:00 AM a 1:00 AM period ends the day), the reminder groups' order (`RemindersPayload.orderedByDay`, applied once in `fetchReminders`), the Smart Stack's change dates, refresh and relevance windows, the watch skip list's day, and the Quotas widget's period clock (`QuotaPeriodBounds.swift`: bounds, % gone, "N days left"; each quota's pace uses the served `progress_period_end`, the chips the served `period_last_day`). The Tasks and Reminders timelines reload no later than the day start, and the Tasks one has an entry at it.
- **Sweeps and the queue:** with the queue on the server sends a below-High task whose landing is at or after the day start to the Tasks queue at the rollover. `BulkSnoozeResult` decodes `queued` / `queued_until` / `summary`: the watch sheet and Smart Stack card add "N to the queue at 3:00 AM" (`SweepLine.queued`) and drop "Moved to <period>" when every task went there; the Mac menu bar shows the server's `summary`.
- **Night labels (2026-10-26, native catch-up PR 2; docs/TASK-MODEL.md § The OpenTask day, the web's `src/lib/night-day.ts`):** `NightDay` (`ios/Shared/NightDay.swift`) is the one rule for a label that names a moment's day. Between midnight and a before-noon day start a moment belongs to the evening before, and its label says so with the evening's weekday and date: "Tomorrow night" / "1:00 am", "Mon night", "Last night" (never "Yesterday night"), "deadline Mon night Oct 26". Outside the night a timed label names the moment's own calendar day, and "Tomorrow" / "Yesterday" only where its OpenTask day and its date agree (with an 11 PM start, Sat 23:30 read at Sat 12:30 is "Sat", never "Tomorrow"). Midnight (the switch off) and starts after 12:00 have no night. Surfaces: `DueLabel.parts` (the Tasks widget, the Mac menu bar), `WatchFormatting.dueLine` (which still names no past weekday — a yesterday the words can't name reads as its date), and a segment row's target and deadline words (`TaskDTO.segmentMeta` / `upcomingMeta`, `dayStart:` defaulting to `DayStartStore.current`; the night form keeps its weekday in every Upcoming form). Date-only targets (local midnight) are calendar dates, never a night.

## Simulator Limitations

- **Notification content extensions cannot be tested in the simulator.** Long-press expansion is a known Apple limitation across all Xcode versions. Use a physical device.
- **watchOS notification actions cannot be tested in the simulator.** Mirrored notifications and action forwarding require a physical iPhone + Apple Watch pair.
- `xcrun simctl push` delivers banners but does not invoke service or content extensions.
- iOS 18.2 simulator: apps don't appear in Settings (known bug, fixed in 18.4+).

## Installing on devices (2026-10-26)

**Installs go through the scripts, never a hand-typed `xcodebuild` + `devicectl`.** On 10-26 several Mac builds went out without the push entitlements and the installed app got no push for hours, with nothing failing. The scripts build Release, check every bundle's SIGNED entitlements for `aps-environment` with `codesign`, and stop loudly before installing a build that would not get push.

```bash
# iPhone (the watch app rides along). UDIDs from `xcrun devicectl list devices`.
OPENTASK_DD_IOS=<scratchpad>/dd-ios ios/scripts/install-iphone.sh <iphone-udid> [<iphone-udid> ...]
ios/scripts/install-iphone.sh --verify-only     # build and check, install nothing

# Mac (~/Applications/OpenTask.app)
OPENTASK_DD_MAC=<scratchpad>/dd-mac macos/scripts/install-mac.sh
```

- **iPhone** (`ios/scripts/install-iphone.sh`): Release for `generic/platform=iOS`, scheme `OpenTask` (embeds `Watch/OpenTaskWatch.app`). Checks `aps-environment` on `OpenTask.app`, `OpenTaskWidgets.appex`, `OpenTaskWatch.app` and `OpenTaskWatchWidgets.appex`. `OpenTaskNotification.appex` is checked for its signature and App Group only: a content extension draws a notification the app already received and never registers for push, so it has no `aps-environment` and its App ID has no Push capability. Then it installs on each UDID it is given, skips one devicectl doesn't list as available (and says why), and prints the commit and installed/skipped/failed per device. It never launches the app (see below). No device ids live in the script; the caller passes them.
- **Mac** (`macos/scripts/install-mac.sh`): see `macos/README.md` § Installing.
- Derived data defaults to `ios/build` / `macos/build` (gitignored); builders sharing one dir across worktrees set `OPENTASK_DD_IOS` / `OPENTASK_DD_MAC`. Shared helpers: `ios/scripts/native-install-lib.sh`.

## Physical Device Caution

- **Avoid `devicectl device process launch` on a physical device** unless specifically needed. It kills the running app process, which can reset app state and force re-entry of credentials. Prefer letting the user launch the app themselves after install.
- **`install_app_device` (XcodeBuildMCP) / `devicectl device install app` is safe** — it replaces the binary without losing Keychain data or app state.

## XcodeBuildMCP Workarounds

XcodeBuildMCP is an MCP tool server for building and interacting with iOS simulators and devices from Claude Code.

- On iOS 26+, use `touch` (down+up) instead of `tap` to focus SwiftUI text fields — `tap` doesn't reliably activate them.
- WKWebView content is not exposed in the accessibility tree. Use screenshot coordinates for web view interactions.
- **watchOS device builds**: `devicectl` cannot reliably connect to the Apple Watch directly (shows "unavailable" even with Developer Mode on). XcodeBuildMCP's `build_device` and `install_app_device` also don't work for watchOS targets. Instead, deploy the watch app **through the iPhone** — the watch app is embedded in the iOS app bundle and iOS automatically syncs it to the paired watch over Bluetooth:

  ```bash
  # 1. Build (from ios/ directory) — builds both iOS and watchOS targets
  xcodebuild -project OpenTask.xcodeproj -scheme OpenTaskWatch \
    -destination 'generic/platform=watchOS' \
    -allowProvisioningUpdates -allowProvisioningDeviceRegistration \
    -derivedDataPath build build

  # 2. Install the iOS app on the iPhone (the embedded watch app syncs automatically)
  xcrun devicectl device install app --device IPHONE_UDID \
    build/Build/Products/Debug-iphoneos/OpenTask.app
  ```

  - Get the iPhone UDID: `xcrun devicectl list devices`
  - The watch app lives at `OpenTask.app/Watch/OpenTaskWatch.app` inside the iOS bundle
  - If the watch shows "unavailable" in devicectl, try `sudo pkill -9 remoted` on the Mac to force a reconnection (though direct watch install is not needed with this approach)
