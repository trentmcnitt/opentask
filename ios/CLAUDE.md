# iOS App — Development Reference

Detailed development reference for the OpenTask iOS companion app. See the main `AGENTS.md` for the overview, targets, shared code, build instructions, and API endpoints.

## Notification Mechanisms

1. **Default actions** (AppDelegate): Done, +1hr, All +1hr, then one bulk-snooze-to-slot action per cached time slot (`TimeSlotStore`, "All → Next period" plus "All → \<slot label\>", earliest first) — used from lock screen or when content extension is unavailable
2. **Silent dismissal**: Server sends `content-available: 1` push with `type: "dismiss"` when a task is snoozed/completed from the web UI — iOS app removes matching delivered notifications
3. **Content extension** (long-press): Interactive 3x4 snooze grid (presets, increments, decrements) — extension makes API calls directly and dismisses
4. **Slot batch checklist** (`SLOT_REMINDER`, long-press): a §6 time-slot notification expands into a checklist of that slot's pending reminders (fetched live from `GET /api/reminders`, filtered by the payload's `slot_id`); rows stage check-marks, the "Complete N checked" action button commits them in ONE `POST /api/tasks/bulk/complete`, and "Complete all" takes the whole slot. Titles wrap in full, and the extension asks for SwiftUI's own ideal height (`UIHostingController.sizeThatFits`, re-measured on the host's `preferredContentSizeDidChange`; the bottom pin yields rather than compressing rows — 2026-09-24, the grouped-notification row overlap). **Device-test only** — content extensions cannot be invoked in the simulator (see below), so the long-press path is unverifiable there and must not be attempted.

## Widgets (`OpenTaskWidgets`)

WidgetKit extension (`io.mcnitt.opentask.widgets`, iOS 17, App Group `group.io.mcnitt.opentask`) with three independent widget kinds — `OpenTaskReminders`, `OpenTaskTasks`, `OpenTaskTrack`. Separate kinds, not one configurable widget, so each gets its own refresh budget (REDESIGN-V03 §8).

| Kind                | Shows                                                                                                             | Primary size                                       |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `OpenTaskReminders` | Current time slot's reminders, trailing check-off buttons (§6), a per-slot progress strip                         | `systemLarge`                                      |
| `OpenTaskTasks`     | Today's dated tasks by project (plus a Today/Up next unified pair, §below) — reminders AND tracked items excluded | `systemLarge`                                      |
| `OpenTaskTrack`     | Every `progress_target > 1` quota, `+1` buttons (§5)                                                              | `systemSmall` (ring + fraction, §8's flagship 2×2) |

All three support `systemSmall` / `systemMedium` / `systemLarge` / `accessoryRectangular` / `accessoryCircular`. The Reminders and Tasks 2×2s are glanceable-only (a headline number, one item, whole-card deep link) — at ~126pt across, per-item buttons would be mis-tap machines.

- **Data**: timeline providers call `APIClient` (`GET /api/reminders`, `/api/tasks?done=false`, `/api/projects`) with the Keychain credentials shared through the App Group. Tasks and Track are two slices of ONE payload and share `TaskFeed` (fetch + cache + fallback + optimistic staging) — never add a second fetch of `/api/tasks`. Every successful payload is cached in App Group `UserDefaults` (`WidgetStore`); a failed fetch renders the cache with an "as of HH:MM" note rather than blanking.
- **Interaction**: `AppIntent` buttons only — check-off, `+1` progress, and the `‹ ›` pagers. Widgets get no swipe gestures (§8), and Lock Screen accessory families are glanceable-only because interactive widgets are inert on a locked device.
- **Tap targets (2026-09-22, the misclick fix; check-off moved 2026-09-23; background tap removed 2026-09-23)**: only `systemSmall` and the Lock Screen families use a whole-card `.widgetURL` — they are glanceable-only with nothing else to hit. `systemMedium`/`systemLarge` have no card-wide link: the header (title/count text, wrapped in its own `Link` to the section) opens Reminders/Tasks/Track's quotas surface, each row's `Link` opens that item, and `Button(intent:)` controls (check-off, `+1`/`−`, chevrons) stay buttons. `WidgetSignedOutView`'s signed-out message follows the same split — `compact` (small/accessory) keeps a whole-card `.widgetURL`, non-compact wraps just the message TEXT in a `Link` — it was the one remaining `.widgetURL` a source-level audit found on `systemMedium`/`systemLarge` when Trent asked that "tapping the widget in general should not bring me to the app" (2026-09-23). Caveat: that view only renders SIGNED OUT, and Trent's own phone is signed in — so this fix is unlikely to be what he actually felt. WidgetKit doesn't expose per-element hit targets to simulator automation (same class of limitation as notification content extensions — see below), so a background tap couldn't be tested against the fix; the community-reported `Link`/`Spacer` hit-test bleed two sentences below remains the leading unverified suspect and needs an on-device check (empty area below the last row, and empty area right of a short title — the latter may be the row `Link`'s intentional `maxWidth: .infinity` fill, not a bug). Per Apple's WidgetKit model a tap that lands on none of those — e.g. a near-miss on `+1` — should hit nothing, rather than deep-linking away from where the user was aiming; this is unverified on-device (there are community reports of hit-testing bleeding onto an adjacent `Spacer` when a container holds multiple `Link`s, so confirm a near-miss really is inert before relying on it). Reminders' and Tasks' check-off moved from the row's LEADING edge to its TRAILING edge (2026-09-23, thumb reach on a Large widget) — the title `Link` now fills the leading space and the marker (circle for Reminders, project-colored square for Tasks — see below) sits at the trailing 36pt column; they are plain `HStack` siblings with fixed/flexible widths, not overlapping views, so this doesn't touch the hit-testing question above. Tasks' marker no longer encodes priority (a filled dot by priority color) — priority still reads through the title's font weight — and instead outlines in the task's PROJECT color (`WidgetTheme.projectColor`, same source as a project header's dot), which is also how the unified "Up next" scope (all projects, due-soonest) tells rows apart.
- **Optimistic (§8)**: intents stage their effect in `WidgetStore` and repaint from cache before the server call — a completion tombstones (row vanishes, reappears on failure), and staged progress renders as `progress_current + net pending delta` (a counter, so rapid `+1`s and `−1`s all draw), floored at 0. **The cache must stay server-true, because the fast path trusts it (2026-09-24, the stale-count fix)**: a reload within 10s of ANY widget tap (`hasRecentInteraction()` — a toggle, a pager, another chip) repaints from cache, and so does the server's widget push that lands ~2s after a mutation. So every mutating intent either writes the confirmed result INTO the cache (`confirmCompletion`; `confirmProgress`, from the task `POST /api/tasks/:id/progress` returns) or declares it stale (`clearInteraction()` — snooze, restore, Undo/Redo), which sets per-payload fetch-required stamps the fast paths honor (`canRepaintTasksFromCache`/`canRepaintRemindersFromCache`) until a fetch that STARTED after them lands. Before this, a `+1`/`−1` only retired its staged delta, and a tap within 10s of the Takeback toggle (i.e. every takeback `−1`) drew the pre-tap count back on round 2 and on the push — Trent took Weight Lift 3/3 → 0/3 on the server while the widget stayed at 3/3.
- **Chevrons**: `ChevronPager` is told about its ring — it dims when there is nowhere to page. Glyphs only: it used to name the adjacent page beside each glyph in `systemLarge` (`‹ Midday   Evening ›`, truncated ~10 chars), which Trent read as "cut off" on first use (2026-09-11). The header already names the page you are on. 40pt hit targets are a floor, not a suggestion. **Where they are (2026-09-25)**: Tasks' header (the scope ring — Today, Up next, each project with something due) and Reminders' header on `systemMedium` AND `systemLarge` (the period ring, `ShiftReminderSlotIntent`; accessibility "Previous period"/"Next period"), both laid out undo/redo then `‹ ›` at the right edge. Reminders `systemLarge` had dropped them on 2026-09-24 for the slot strip's tappable segments; Trent asked for them back on 2026-09-25. They don't read as the bottom `‹ n/N ›`: the header pair changes the period (the title beside it changes and the page resets to 1), the small bottom pager pages within it and carries its count. Quotas dropped its header pair for good (it paged the same pages as its bottom pager; Trent couldn't tell what it switched). **Reminders header fallback**: when title + undo/redo + chevrons don't fit on one line ("Early morning" at XXX Large on a 402pt iPhone 16 Pro ran a few points past the card, and a title that may not truncate pushes the whole card sideways), a `ViewThatFits` moves undo/redo to the right end of the subtitle line, with their vertical padding cancelled so the header's height doesn't change. Renders: `~/hub-store/capabilities/opentask/screens-2026-09-25-reminders-chevrons/`.
- **Row counts (2026-09-24, height-based paging)**: the Reminders and Tasks lists have no row count and no `ViewThatFits` any more. The header (and Reminders' slot strip) are laid out for real; a `RenderedTextReader` takes the remaining height and hands the list `WidgetTextMetrics` — the text size from the view's own `\.dynamicTypeSize` (never a trait-less `UIFont.preferredFont`, which answers for the process, not the widget), with the measuring font scaled to SwiftUI's drawn width and the line height taken from SwiftUI's drawn pitch, both read back from clear probe texts (at XXX Large, UIKit says 25.06pt per `.subheadline` line; SwiftUI draws 24.13). Every row's height is computed up front — title lines via `WidgetTheme.measuredLineCount` at the row's real column, UNCAPPED on every family and platform (the iOS 3-line cap and systemMedium's one-line rows were removed later on 2026-09-24 — Trent: never truncate a reminder/task title), clamped only so no row is taller than the whole list area (a title that long gets a page to itself and ends in "…") — and the row is FRAMED to exactly that height. `WidgetTheme.pages` then fills each page greedily until the next row genuinely doesn't fit, breaking only between whole rows; the partition is a pure function of the list, so the page count is the same whichever page is showing. The layout adds exactly what the budget subtracted: rows in their own `rowSpacing` stack, then a `Spacer`, then the bottom row with its own `rowSpacing` of top padding (a spaced outer stack would put a second gap around the Spacer that no budget counted). iOS `systemLarge`'s check-off bleeds its tap target half a `rowSpacing` into the gaps instead of forcing a 36pt row; `systemMedium` iOS rows wrap too, on the 36pt finger floor (no pager there, so it just shows fewer rows). Tasks' due label is `fixedSize` (it used to wrap on its own, handing width back to a title measured without it); a two-part label (day word + time: "Tomorrow" / "4:00 pm", "Sat" / "9:00 am", "Oct 1" / "9:00 am") ALWAYS stacks, day over time, right-aligned, on every family — one rule since 2026-09-24 (it used to stack only where that made the row shorter, so adjacent rows mixed "Tomorrow 9:00 am" inline with "Tomorrow" over "12:00 pm"); a time-only (today) or day-only (date-only task) label is one line, and every row's measured height includes the two-line label. **Why (Trent's phone, 2026-09-24, XXX Large text)**: the old `ViewThatFits` ladder sliced UNIFORM pages of whichever candidate fit, so the page holding the longest rows set every page's size ("7 left" as 1/4 with two rows; "26 due" as 13 pages of two), and each candidate sliced its own page from the stored index, so page 2 of the same list read "2/2" with one row. See `WidgetTheme.pages`' doc and the "row-height truthing" addendum in `WidgetTheme.swift`.
- **Budget (corrected 2026-09-25, "Quotas still 0/2 after did-it")**: on iOS the ONLY free reload a tap gets is WidgetKit's own reload of the TAPPED kind after `perform()` returns — chronod logs it `interaction-immediate-free`. Every `WidgetCenter.reloadTimelines(ofKind:)` the extension issues, for its own kind or another, is logged `externalRequest(… WidgetCenterServer …)-immediate-budgeted` and charged to that kind's daily budget, and so is the server's widget push. The old rule here ("reloads triggered by a widget's own intent are free") was wrong, and every intent spent budget reloading its own kind twice — the pre-server one never even ran ("Delaying reload … because entry is paused" until `perform()` returned, then replaced). The bug it caused: did-it on the Reminders widget's "Daily Walks · 0/2" prompt; prod took it (1/2), the intent wrote the returned quota into the cache, the push went out 2s later — and the phone's Quotas widget still drew 0/2 until the app was opened (its leave-the-app reload fetched at 10:59:06). Nothing was wrong with the data: the same taps on the iOS 27 simulator (idb HID taps; the sim doesn't enforce budgets) rebuild Quotas from the confirmed cache every time, with no fetch. The phone just never ran the budgeted Quotas reload — and a Reminders tap has no other way to reach Quotas. Trent's iPhone confirms it (read-only `idevicesyslog -p chronod`, 11:33 the same day): `budget: com.apple.dasd.widget_io.mcnitt.opentask.widgets::OpenTaskTrack, budget: -0.357` (Tasks 0.63, Reminders 22.3), a queued Track reload sitting unrun until a push replaced it, and the extension's widget-PUSH budget at `-17` ("Reduced budget for io.mcnitt.opentask.widgets to: -17") — so the server's push can be throttled too. Same shape as PR #82's "Quotas stuck at 1/2 after Undo". Rule now: intents never reload their own kind on iOS (`reloadTappedWidget(kind:)` is a no-op there, kept at each call site to say where the repaint comes from), and ask for another kind only when the tap changed what it shows (prompt did-it/considered → Track; Quotas `±1` → Reminders; Undo/Redo → the other two). macOS logs no interaction reload and its extension reloads are free (09-23/24: `externalRequest … free`, `push … free`), so there the explicit tapped-kind reload stays, both rounds. To check a reload's class: `xcrun simctl spawn <udid> log stream --predicate 'process == "chronod" AND eventMessage CONTAINS "opentask"'` and read the `Reload with configuration [...]` lines. App-triggered reloads are free. The app reloads all kinds as it goes to the BACKGROUND (`OpenTaskApp`'s scenePhase `.background`) — not on activation any more (removed 2026-09-24: the user can't see a widget while in the app, and the leave-the-app reload plus the server's widget push already cover what changed). Unprompted refreshes are budgeted, so the timeline policy is `.after(+30 min)` plus zero-cost entries pre-scheduled at each time-slot boundary and upcoming due time.
- **Widget push token registration (2026-09-25, "the Mac has no row in widget_push_tokens")**: the Mac's App Group held `widgetPush.registeredToken` = `widgetPush.pendingToken` = `8038d39b…`, prod had no row for that token (only the iPhone's and the watch's), so `WidgetPushRegistration.retryIfNeeded()` skipped it on every reload — for good, because WidgetKit re-delivers the SAME token after a reinstall (chronod: "Public token has not changed") and the App Group, "registered" mark included, survives deleting the app on macOS. Two ways the row disappears without the extension knowing: (1) the extension itself used to DELETE it on a `pushTokenDidChange` with no widgets, and the Mac's chronod sends exactly that on every start while the widgets are on the desktop (09-23 19:02:52 `initial` reloads of all three placed kinds, then 19:03:04 "Sending 0 WidgetInfo instance(s) to 1 PushHandler instances" after a reboot; 22:09:01 the same after the reinstall's `killall chronod`); (2) the server deletes a token when APNs answers Unregistered/BadDeviceToken, e.g. while the app is deleted mid-reinstall (`sendApnsWidgetReload`). Prod's journal only goes back to 09-25 04:14, so which one removed row 8 isn't recorded. Fix: an empty list no longer unregisters (a token with no widget costs one ignored push; APNs retires dead ones), and `savePending` forgets the old confirmation so every delivery is POSTed (the server upserts). The watch copy got the second half. Separately, the Mac has NO local OpenTask widget placed right now: `OpenTaskMacWidgets` last ran 09-24 ~11:30, chronod's `PushSubscriptions` table is empty and it has run no local OpenTask reload since. Any OpenTask widget on that desktop is the iPhone's (`D3FA3629…::io.mcnitt.opentask`, rendered by the phone). With no local widget, chronod never subscribes and no token can arrive: after installing this build, add a widget from the gallery's Mac entry (not the iPhone one); chronod then logs "Creating new subscription … Push token sent to extension" and the row appears. - **Undo / Redo (2026-09-23, replaces the old 60s window)**: `UndoRedoButtons` — two icon buttons (`arrow.uturn.backward` / `arrow.uturn.forward`), right-aligned before the chevrons, in ALL THREE kinds' `systemLarge` (and `systemMedium`, when it fits) headers — is ALWAYS present, not shown-then-hidden. Enabled state comes from the server's own counts, not a local clock: `WidgetStore.undoableCount`/`redoableCount` (a `-1` sentinel reads as "enabled" before the first fetch ever lands), refreshed on every widget fetch by piggybacking `GET /api/undo/status` onto `RemindersProvider`'s and `TaskFeed`'s existing network calls, plus updated optimistically the instant a local completion/`+1`/`−1` succeeds (`WidgetStore.recordLocalMutationForUndoCount()` — exact, since every mutation both adds one undoable entry and clears the redo stack server-side, `src/core/undo/log-action.ts`). Tapping either (`UndoLastActionIntent`/`RedoLastActionIntent`) calls `POST /api/undo`/`POST /api/redo` — the SAME endpoints the web toast's Undo/Redo buttons use, with no task id, so they act on "whatever changed/was-undone last" server-wide, not "this row specifically" — wipe every optimistic/confirmed marker in `WidgetStore` (`clearAllPendingState()`), refetch both payloads concurrently, then reload all three kinds ONCE (the one deliberate exception to `reloadOpenTaskWidget(kind:)`'s single-kind rule), the kinds other than the tapped one first (`reloadAfterUndoRedo`; the buttons carry their header's `kind`). **No reload before the server call (2026-09-25, "Quotas stuck at 1/2 after Undo")**: did-it on the Reminders widget's "Daily Walks · 0/2" prompt, then Undo on the Reminders widget — the server undid it and Reminders put the prompt back, but Quotas stayed at 1/2. Prod's request log for that tap shows the refetch ran (the shared tasks cache held 0/2), then exactly ONE provider build fetched (Reminders') and no Quotas/Tasks build ran at all until the app was opened a minute later. The code path is right — a `swiftc` harness driving the real intents against dev, and real widget taps on the iOS 27 simulator (driven with `idb` HID taps), rebuild Quotas at 0/2 every time — so on the phone WidgetKit never ran the Quotas reload Undo asked for. What Undo did differently from the did-it tap, whose cross-kind Quotas reload DID land: it had already reloaded all three kinds before `POST /api/undo` (a pass with nothing new to draw) and asked again ~1.3s later. The only reload WidgetKit is guaranteed to run is its own reload of the tapped widget after `perform()` returns; don't spend a kind's reload on a pass that can't show anything, and ask for the other kinds first. A shared `WidgetStore.tryClaimUndoRedo()` in-flight claim (TTL-backstopped, not time-windowed) stops a double-tap or an overlapping Undo+Redo from firing two server calls for one intended action. The response's `description` is cached (`WidgetStore.recordLastAction`) and shown in place of the header's ordinary count subtitle — "Undid: …" / "Redid: …" — for `WidgetStore.lastActionWindow` (60s) on whichever slot/page happens to be on screen; each provider's `getTimeline` schedules an explicit expiry entry at that window's close (WidgetKit has no "expire after N seconds" primitive) so it reliably reverts to the ordinary subtitle. `WidgetStore.recordMutation`/`consumeLastMutation` still exist, narrowed to ONE job: correlating an undo with the Reminders auto-advance snapshot it might need to restore (see below) — not gating the buttons' visibility any more.
- **List paging (2026-09-23; bottom row 2026-09-24)**: where the Reminders/Tasks `systemLarge` list used to show "+N more" (a `Link` to the app), a `ListPager` (`‹ n/N ›`, non-wrapping, dims at the ends) pages through the list in place — `ShiftReminderPageIntent`/`ShiftTasksPageIntent` — on every page whenever there is more than one. It lives in `ListBottomBar`, a fixed-height (`WidgetTextMetrics.bottomBarHeight`) row pinned to the card's bottom: leading "Select" (Tasks resting mode only), the pager centred on the card, trailing the completed dot. Quotas uses the same bottom row (pager + "met" dot). The page index is stored per KIND (`WidgetStore.remindersPage(for:)`/`tasksPage(for:)`), paired with the slot/scope it was paged within so it self-resets to 0 the moment that slot/scope changes for ANY reason — a chevron, a jump, an auto-advance, or just the clock crossing into a new natural slot — and clamped by the list on every render.
- **Quotas paging and long chips (2026-09-24)**: the Quotas header is laid out for real above a `RenderedTextReader` (it used to be a FIXED 40pt guess; at XXX Large the real header is ~15pt taller, pages were cut for room they didn't have, and the pinned pager was pushed off the bottom — "the pager disappears on page 2"). Every line's height comes from `QuotaFlow.height(of:isFirstOnPage:)`, built from the same `QuotaMetrics` constants `QuotaLinesView` draws with (cluster titles used to be counted at 15pt and drawn at 20). A chip wider than the card on its own (no `short_title` yet — `short_title ?? title` stays) gets a row to itself, drawn exactly card-wide with its title wrapped to at most `QuotaMetrics.wrappedTitleLines` (2), count trailing, cut at the end of line 2 only if still too long; `QuotaMetrics.chipHeight(lines:)` gives that row its two-line height.
- **Quotas Takeback mode (2026-09-24)**: the ONE way to take a count back from the widget (Trent: Undo alone was "too disorienting" for 2/3 → 1/3). A `minus.circle` button (`TakebackModeToggle`, icon only — "○ met" + the word "Takeback" doesn't fit beside the centred pager even at the default text size; accessibility label "Takeback mode") sits at the right end of the `systemLarge` bottom row, after the "met" dot. Tapping it (`ToggleQuotasTakebackModeIntent`) arms the mode: the button goes red (`WidgetTheme.takebackTint` — an action color, not a §5 state color), every chip with progress shows a red "│ −1" and taps as `IncrementProgressIntent(delta: -1)`, chips at 0 are dimmed and disabled (still buttons, so a tap can't fall through to the card's background link), and met chips show even with the dot off. The mode STAYS ON across `−1`s (2026-09-24 — it exited after one for a day, and Trent found that "weird": 3/3 → 0/3 meant re-arming before every tap); tapping the button again exits without doing anything; and any Track timeline built outside `hasRecentInteraction()` (a scheduled refresh, a push after a change elsewhere, the app's leave-the-app reload, Undo) clears it (`TrackProvider.currentEntry`) — every chip tap stamps `markInteraction()`, so a tap's own round 2 and the server's widget push right after it keep the mode. Persisted as `WidgetStore.quotasTakebackMode`; honored only for a `systemLarge` instance (`context.family`). It replaced PR #65's met-chip "│ −1": outside the mode every chip — met included — is `+1`, matching the web panel, which allows over-target counts ("2/1"; `TrackChip`'s tap is an unconditional `log(1)`).
- **Reminders slot strip and auto-advance (2026-09-23)**: `ReminderSlotStrip` draws one segment per slot with something in it (indigo = started and still waiting, green = started and finished, near-invisible = not started yet), mirroring the web's `ReminderSlotBar` for state/color but with equal-width segments (a widget has no room for the web's proportional layout). `systemLarge` only. Completing the last item in the on-screen slot auto-advances the widget to the EARLIEST slot (day's first through the slot the clock is in, inclusive) that still has something waiting (`RemindersTimeline.autoAdvanceSlot`, via the existing slot-override mechanism) — never forward into a slot that hasn't started. When every started slot is finished, the empty state reads "All caught up" instead of the per-slot "Nothing left here" / "\<Slot\> done". Each segment is its own tap target (`JumpToReminderSlotIntent`, same storage as the chevrons' `ShiftReminderSlotIntent` but addressed by slot key instead of an offset) — the finger target is taller than the 3-4pt bar via the same bleed trick `ReminderRow`'s check-off uses (`ReminderSlotStrip.segmentBleed`, half of `WidgetTheme.rowSpacing`), so it costs no extra row. The on-screen slot also draws a ring outside its bar (`.overlay(Capsule().stroke(...).padding(-2))`, not a stroke layered on the bar itself, which would eat into a 3-4pt fill) — the pre-existing height bump alone didn't read clearly enough at a glance (Trent, 2026-09-23: "we need some kind of outline... to show which segment we're currently on").
- **Notes glyph (2026-09-25)**: a row whose item has notes wears a small muted `doc` symbol after the last word of its title — the web's `NotesMarker`. Reminder rows and task rows read `TaskDTO.hasNotes` (decoded from the server's `notes`, cached as a `has_notes` flag, never the text); prompt rows read `QuotaPromptDTO.hasNotes` (`has_notes`, defaulted false) and put it after the count, as the web does. Open and DONE reminder/prompt rows, open task rows only (a DONE task row comes from `/api/completions`, which carries no notes); the 2×2s and Lock Screen don't (glanceable, no rows). It is drawn inside the title's `Text` by `WidgetTheme.titleText(_:notesGlyphSize:)`, joined by a no-break space, at 0.75× the title's drawn size (`WidgetTextMetrics.notesGlyphSize`), `.tertiary`, never a priority color; the pager measures the same thing (`measuredLineCount(for:notesGlyphSize:…)`, the glyph as an inline box of its width), so a glyph that pushes a title onto another line is paid for in the page math. One known edge: when the title's last "word" is already a full line on its own (e.g. "00-00000-00000)", unbreakable), the glyph drops to the next line alone — measured, so nothing clips. VoiceOver: the row label gains ", has notes" (`NotesGlyph.accessibilityLabel`). The watch Reminders page draws the same glyph (`WatchTheme.titleText`, after the title, since its count sits on its own line). Renders: `~/hub-store/capabilities/opentask/screens-2026-09-25-widget-note-glyph/`; previews in `NotesGlyphPreviews.swift` (Reminders only, generated from a read-only prod snapshot with notes text stripped; the Tasks renders came from the same snapshot's task list, which is deliberately not committed).
- **Deep links**: `opentask://today`, `opentask://reminders`, `opentask://reminders/slot/<slotId>`, `opentask://reminder/<id>`, `opentask://task/<id>`, `opentask://project/<id>`, `opentask://quota/<id>`, `opentask://quotas` — resolved to web paths in `OpenTaskApp.handleWidgetLink` (macOS: `OpenTaskMacApp.handleWidgetLink`, byte-parallel). - **A widget tap landing on the wrong tab (2026-09-23)**: a deep link tapped while the app is backgrounded on a NON-dashboard tab (e.g. Reminders, reached by an in-page SPA transition, never a native `navigate()` call) could open the app but leave it on the old tab instead of switching. Root cause, reproduced in the simulator (`ios/OpenTask/WebView.swift`'s `Coordinator`, instrumented with temporary `decidePolicyFor`/`didStartProvisionalNavigation`/`didFinish`/`didFail` logging — reached via a deep link to `/reminders` rather than an actual in-app tab tap, since the tab tap's pushState transition is invisible to this instrumentation; the race mechanism is the same either way): coming to the foreground fires TWO navigations at once — our own `WebViewManager.navigate(path:)` from `handleWidgetLink`, and a client-side redirect fired from the PAGE ITSELF (`router.push(loginUrlFromLocation())`, e.g. in `reminders/page.tsx`) — confirmed client-side (not our own request redirected server-side) because the `/login` this raced carried `callbackUrl=/reminders`, the OLD page's `window.location`, which only that still-loaded page's own `loginUrlFromLocation()` can produce. The likeliest trigger — not directly observed, but the only automatic session-recheck this app wires up — is `SessionProvider`'s NextAuth default `refetchOnWindowFocus: true`, firing on the same foreground/focus event and finding the session momentarily stale right after resume. When that competing redirect wins the race (cancelling our own request — logged as `didFailProvisionalNavigation`/`NSURLErrorCancelled` immediately before the `/login` decidePolicyFor), the existing `/login` rescue (`resumePath(fromLoginURL:)`) used to trust the redirect's callbackUrl unconditionally — which names the OLD tab, not the tap's actual destination. Fixed by tracking whether the navigation immediately preceding a `/login` bounce was cancelled (`Coordinator.lastNavigationWasCancelled`); when it was, `resumePath` trusts `lastRequestedPath` (set synchronously by `navigate(path:)`, before either navigation's network round trip) instead of the callback. See `resumePath`'s doc for the full mechanics and why the ordinary (non-race) case is unaffected. Every backgrounded-deep-link repro run in this investigation — control (dashboard) included — bounced through this `/login` detour once before landing; the fix corrects the destination but not that extra round trip, which may be worth a follow-up look.

### The two project specs

`project.yml` is canonical. `project-sim.yml` is **generated** from it by `ios/scripts/make-sim-spec.py` — it is the same spec minus every target whose `platform` is `watchOS` (currently `OpenTaskWatch` and `OpenTaskWatchWidgets`), because generating and building the canonical spec requires the watchOS SDK to be installed, and without it every `xcodebuild` fails before compiling a single file (including iOS-only builds). The strip is by platform, not by a hardcoded target name/list, so a future watchOS target is dropped from the sim spec automatically.

```bash
python3 ios/scripts/make-sim-spec.py            # regenerate project-sim.yml
python3 ios/scripts/make-sim-spec.py --check    # fail if it's stale
cd ios && xcodegen generate                     # canonical (OpenTask.xcodeproj)
cd ios && xcodegen generate --spec project-sim.yml   # sim (OpenTaskSim.xcodeproj)
```

Never hand-edit `project-sim.yml` — add targets to `project.yml` and regenerate, or the new target silently builds on one spec and not the other.

## Quota prompts (quota reminders, phase 2, 2026-09-25)

Every unmet quota also appears as a reminder-like PROMPT in a slot each day (server-computed, `GET /api/reminders` `groups[].prompts`, `QuotaPromptDTO`). Two actions everywhere: the round circle = CONSIDERED (handled today, no progress), the square beside the count ("Daily Walks · 1/2") = DID IT (+1, and considered). A thin leading stripe wears the quota's label color (server-resolved `stripe_color`, never green). Prompts come after the slot's reminders and count exactly like reminders — every count reads `ReminderGroupDTO.waitingCount`/`consideredCount`/`hasNothingWaiting`, never `reminders.count`/`considered` alone. Rows are keyed by `prompt_key`: a daily quota's prompts in different slots share one task id. `ReminderGroupDTO`'s memberwise init has NO default for `prompts`, so every rebuild site has to say what happens to them.

- **Reminders widget**: `PromptRow` (label `Link` → `opentask://quota/<id>`, then square, then circle — the circle stays in the reminder circles' column). Its height is measured from `QuotaPromptDTO.labelText` at `PromptRowMetrics.titleWidth` (card minus stripe and BOTH 36pt controls). Handled prompts join the DONE section with an inert marker (no put-back: /undone refuses quotas). `ActOnPromptIntent` stages a tombstone by key (`WidgetStore.stagePendingPromptAction`, drawn as handled, not removed), then on success writes the server's answer into both caches: the returned quotas into Tasks/Quotas (`confirmTasks`), and the prompt handled plus every prompt of that quota re-counted into Reminders (`confirmPromptAction`, the prompt twin of `confirmCompletion`, so the next tap repaints from cache instantly and nothing pops back after the tombstone expires). Auto-advance is snapshotted and restored on failure or Undo exactly as for a reminder. A failure (likeliest: a key from before midnight) marks Reminders fetch-required (`requireRemindersFetch`). A Quotas `+1`/`−1` also calls `requireRemindersFetch` and reloads Reminders. It's `requireRemindersFetch`, not `clearInteraction`, because the latter forgets the interaction stamp that keeps Takeback mode armed.
- **The count names its period (2026-09-25)**: every native prompt surface shows `QuotaPromptDTO.countText` — "1/2 today", "3/5 this week", "0/1 this month", "… this year", count only with no period (the web uses the same words). Count and words are joined with non-breaking spaces so they wrap as one unit. The title joins it through `QuotaPromptDTO.countSeparator` (" ·\u{00A0}": a plain space BEFORE the dot) — with NBSP on both sides, "omega-3) · 0/2 this week" became one run wider than the widget column and the text system broke it mid-unit at XXX Large. The widget's paging measures `labelText`, so the longer count is in the page math. The Smart Stack card is the exception: its count sits in the 30pt column above ☐, where even "0/2 today" truncated, so it draws `columnCountText` — "0/2" over "today"/"wk"/"mo"/"yr" (`compactPeriodWord`) — on two lines. The watch Reminders page's count line fits the full words at XXX Large on the 44mm SE (184pt). Renders: `~/hub-store/capabilities/opentask/screens-2026-09-25-prompt-period-words/`. The notification checklist (`ReminderChecklistView`) can't be rendered — Xcode previews can't be hosted in a content extension, and the simulator can't open one — so it's covered by sharing `countText`/`countSeparator` with the widget row.
- **Watch**: `PromptRowView`, where tap = considered. The count and a square did-it button sit on their own right-aligned line under the title: in a side column the 44mm SE left titles 1–2 words per line. The prompt's response goes through `settleConfirmedQuotas` (the `settleQuota` write path), then `load()`. In-flight actions overlay every payload (`pendingPromptActions`). A Quotas-page tap re-fetches reminders (`refreshReminders`).
- **Watch: move a prompt to another period (2026-09-25)**: touch and hold a prompt's title → a `confirmationDialog` of every period (the Tasks page's touch-and-hold pattern; the current one reads "Morning ✓" — NOT `.disabled`, because a watchOS confirmationDialog drops disabled buttons entirely). A tap is the web quota editor's write: `APIClient.fetchQuotaPromptConfig` (raw `GET /api/tasks/{id}`) → `WatchPromptMove.movedConfig` (daily row: only its `numbers`; others: `slot_id`; merged over the stored config) → `APIClient.setQuotaPromptConfig` (`PATCH`), then haptics, "Moved to <period>" under the header, `load()`; the toolbar Undo reverses it. The title area is `onTapGesture` + `onLongPressGesture(0.4)`, not a `Button` (a Button also fires on the release that ends a hold, which would consider the prompt). A daily row from a server without `numbers` offers no list (`canMove`) rather than moving every number.
- **Smart Stack**: prompts take the card in turn after reminders (`ReminderStackTimeline.cardItems`, skip keys are strings: `r:<id>` or the prompt key). ✓ = considered (`ActOnPromptCardIntent`, never `markDone`), and a ☐ did-it column with the count above it (`ReminderStackMetrics.promptCardShowsDidIt`), so a truncated title never takes the count with it.
- **Checklist**: prompt rows stage circle (considered) or square (did it), one choice per prompt. The commit is ONE `bulk/complete` with `ids` + `prompts`, and "Complete all" (`APIClient.completeSlotReminders`, all three app delegates) sends the waiting prompts as considered (in the expanded checklist, prompts staged as did-it keep their +1). A refused commit (a stale key after midnight) reloads today's slot and drops staging that no longer exists. Since phase 3 (2026-09-25) the server counts waiting prompts in SLOT_REMINDER pushes and the hourly nags (`reminder_count` = reminders + waiting prompts; `prompt_count` informational), so a prompts-only slot notifies too.

## Simulator Limitations

- **Notification content extensions cannot be tested in the simulator.** Long-press expansion is a known Apple limitation across all Xcode versions. Use a physical device.
- **watchOS notification actions cannot be tested in the simulator.** Mirrored notifications and action forwarding require a physical iPhone + Apple Watch pair.
- `xcrun simctl push` delivers banners but does not invoke service or content extensions.
- iOS 18.2 simulator: apps don't appear in Settings (known bug, fixed in 18.4+).

## Physical Device Caution

- **Avoid `devicectl device process launch` on a physical device** unless specifically needed. It kills the running app process, which can reset app state and force re-entry of credentials. Prefer letting the user launch the app themselves after install.
- **`install_app_device` (XcodeBuildMCP) / `devicectl device install app` is safe** — it replaces the binary without losing Keychain data or app state.

## XcodeBuildMCP Workarounds

XcodeBuildMCP is an MCP tool server for building and interacting with iOS simulators and devices from Claude Code.

- On iOS 26+, use `touch` (down+up) instead of `tap` to focus SwiftUI text fields — `tap` doesn't reliably activate them.
- WKWebView content is not exposed in the accessibility tree. Use screenshot coordinates for web view interactions.
- **watchOS device builds**: `devicectl` cannot reliably connect to the Apple Watch directly (shows "unavailable" even with Developer Mode on). XcodeBuildMCP's `build_device` and `install_app_device` also don't work for watchOS targets. Instead, deploy the watch app **through the iPhone** — the watch app is embedded in the iOS app bundle and iOS automatically syncs it to the paired watch over Bluetooth:

  ```bash
  # 1. Build (from ios/ directory) — builds both iOS and watchOS targets
  xcodebuild -project OpenTask.xcodeproj -scheme OpenTaskWatch \
    -destination 'generic/platform=watchOS' \
    -allowProvisioningUpdates -allowProvisioningDeviceRegistration \
    -derivedDataPath build build

  # 2. Install the iOS app on the iPhone (the embedded watch app syncs automatically)
  xcrun devicectl device install app --device IPHONE_UDID \
    build/Build/Products/Debug-iphoneos/OpenTask.app
  ```

  - Get the iPhone UDID: `xcrun devicectl list devices`
  - The watch app lives at `OpenTask.app/Watch/OpenTaskWatch.app` inside the iOS bundle
  - If the watch shows "unavailable" in devicectl, try `sudo pkill -9 remoted` on the Mac to force a reconnection (though direct watch install is not needed with this approach)
