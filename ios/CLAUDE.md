# iOS App — Development Reference

Detailed development reference for the OpenTask iOS companion app. See the main `AGENTS.md` for the overview, targets, shared code, build instructions, and API endpoints.

## Notification Mechanisms

1. **Default actions** (AppDelegate): Done, +1hr, All +1hr, then one bulk-snooze-to-slot action per cached time slot (`TimeSlotStore`, "All → Next period" plus "All → \<slot label\>", earliest first) — used from lock screen or when content extension is unavailable
2. **Silent dismissal**: Server sends `content-available: 1` push with `type: "dismiss"` when a task is snoozed/completed from the web UI — iOS app removes matching delivered notifications
3. **Content extension** (long-press): Interactive 3x4 snooze grid (presets, increments, decrements) — extension makes API calls directly and dismisses
4. **Slot batch checklist** (`SLOT_REMINDER`, long-press): a §6 time-slot notification expands into a checklist of that slot's pending reminders (fetched live from `GET /api/reminders`, filtered by the payload's `slot_id`); rows stage check-marks, the "Complete N checked" action button commits them in ONE `POST /api/tasks/bulk/complete`, and "Complete all" takes the whole slot. **Device-test only** — content extensions cannot be invoked in the simulator (see below), so the long-press path is unverifiable there and must not be attempted.

## Widgets (`OpenTaskWidgets`)

WidgetKit extension (`io.mcnitt.opentask.widgets`, iOS 17, App Group `group.io.mcnitt.opentask`) with three independent widget kinds — `OpenTaskReminders`, `OpenTaskTasks`, `OpenTaskTrack`. Separate kinds, not one configurable widget, so each gets its own refresh budget (REDESIGN-V03 §8).

| Kind                | Shows                                                                                                             | Primary size                                       |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `OpenTaskReminders` | Current time slot's reminders, trailing check-off buttons (§6), a per-slot progress strip                         | `systemLarge`                                      |
| `OpenTaskTasks`     | Today's dated tasks by project (plus a Today/Up next unified pair, §below) — reminders AND tracked items excluded | `systemLarge`                                      |
| `OpenTaskTrack`     | Every `progress_target > 1` quota, `+1` buttons (§5)                                                              | `systemSmall` (ring + fraction, §8's flagship 2×2) |

All three support `systemSmall` / `systemMedium` / `systemLarge` / `accessoryRectangular` / `accessoryCircular`. The Reminders and Tasks 2×2s are glanceable-only (a headline number, one item, whole-card deep link) — at ~126pt across, per-item buttons would be mis-tap machines.

- **Data**: timeline providers call `APIClient` (`GET /api/reminders`, `/api/tasks?done=false`, `/api/projects`) with the Keychain credentials shared through the App Group. Tasks and Track are two slices of ONE payload and share `TaskFeed` (fetch + cache + fallback + optimistic staging) — never add a second fetch of `/api/tasks`. Every successful payload is cached in App Group `UserDefaults` (`WidgetStore`); a failed fetch renders the cache with an "as of HH:MM" note rather than blanking.
- **Interaction**: `AppIntent` buttons only — check-off, `+1` progress, and the `‹ ›` pagers. Widgets get no swipe gestures (§8), and Lock Screen accessory families are glanceable-only because interactive widgets are inert on a locked device.
- **Tap targets (2026-09-22, the misclick fix; check-off moved 2026-09-23; background tap removed 2026-09-23)**: only `systemSmall` and the Lock Screen families use a whole-card `.widgetURL` — they are glanceable-only with nothing else to hit. `systemMedium`/`systemLarge` have no card-wide link: the header (title/count text, wrapped in its own `Link` to the section) opens Reminders/Tasks/Track's quotas surface, each row's `Link` opens that item, and `Button(intent:)` controls (check-off, `+1`/`−`, chevrons) stay buttons. `WidgetSignedOutView`'s signed-out message follows the same split — `compact` (small/accessory) keeps a whole-card `.widgetURL`, non-compact wraps just the message TEXT in a `Link` — it was the one remaining `.widgetURL` a source-level audit found on `systemMedium`/`systemLarge` when Trent asked that "tapping the widget in general should not bring me to the app" (2026-09-23). Caveat: that view only renders SIGNED OUT, and Trent's own phone is signed in — so this fix is unlikely to be what he actually felt. WidgetKit doesn't expose per-element hit targets to simulator automation (same class of limitation as notification content extensions — see below), so a background tap couldn't be tested against the fix; the community-reported `Link`/`Spacer` hit-test bleed two sentences below remains the leading unverified suspect and needs an on-device check (empty area below the last row, and empty area right of a short title — the latter may be the row `Link`'s intentional `maxWidth: .infinity` fill, not a bug). Per Apple's WidgetKit model a tap that lands on none of those — e.g. a near-miss on `+1` — should hit nothing, rather than deep-linking away from where the user was aiming; this is unverified on-device (there are community reports of hit-testing bleeding onto an adjacent `Spacer` when a container holds multiple `Link`s, so confirm a near-miss really is inert before relying on it). Reminders' and Tasks' check-off moved from the row's LEADING edge to its TRAILING edge (2026-09-23, thumb reach on a Large widget) — the title `Link` now fills the leading space and the marker (circle for Reminders, project-colored square for Tasks — see below) sits at the trailing 36pt column; they are plain `HStack` siblings with fixed/flexible widths, not overlapping views, so this doesn't touch the hit-testing question above. Tasks' marker no longer encodes priority (a filled dot by priority color) — priority still reads through the title's font weight — and instead outlines in the task's PROJECT color (`WidgetTheme.projectColor`, same source as a project header's dot), which is also how the unified "Up next" scope (all projects, due-soonest) tells rows apart.
- **Optimistic (§8)**: intents stage their effect in `WidgetStore` and repaint from cache before the server call — a completion tombstones (row vanishes, reappears on failure), and staged progress renders as `progress_current + net pending delta` (a counter, so rapid `+1`s and `−1`s all draw), floored at 0.
- **Chevrons**: `ChevronPager` is told about its ring — it dims when there is nowhere to page. Glyphs only: it used to name the adjacent page beside each glyph in `systemLarge` (`‹ Midday   Evening ›`, truncated ~10 chars), which Trent read as "cut off" on first use (2026-09-11). The header already names the page you are on. 40pt hit targets are a floor, not a suggestion.
- **Row counts**: the Reminders and Tasks lists do NOT have a fixed row count. `ViewThatFits` walks down from a per-family ceiling (10, both platforms, since 2026-09-23 — was 6) and renders the first card that fits, and each row RESERVES its lines so that measurement is honest — ViewThatFits compares _ideal_ heights, and a Text's ideal height is one unwrapped line. Without the reservation the tallest candidate always "fits", the card then squeezes, and every title truncates to one line. `systemMedium` still reserves a FLAT one line per title on both platforms (a 4×2 is ~128pt of usable height and holds a header plus two rows, nothing more — no room to measure). `systemLarge` reserves each title's REAL measured line count (`WidgetTheme.measuredLineCount`, real text-layout measurement — AppKit on macOS since 2026-09-22, the same call shared with UIKit on iOS since 2026-09-23) instead of a flat budget, threaded down from a `GeometryReader` placed OUTSIDE `ViewThatFits` (never inside a candidate — that would report "fits" at every height and defeat the measurement). Two platform differences remain, both deliberate: **the cap** — iOS caps a title at `WidgetTheme.iOSMaxTitleLines` (3; "I don't want to truncate the text until three lines"), macOS never caps at all; **the marker floor** — iOS's 36pt check-off/square column is a FINGER target and never shrinks below `WidgetTheme.rowMarkerSize` even when the measured text is shorter, macOS's marker has no floor (a mouse pointer needs none) and simply matches the measured height. That floor is also why the per-row space iOS wins back is smaller than macOS's was: at the iPhone 17 Pro simulator's default text size `rowTitleLineHeight` (18pt) already ties `rowMarkerSize` for a flat two-line title (2×18=36), so the real win on iOS is mostly the raised ceiling (more genuinely-short rows now get a candidate to fit into) and the end of silent 2-line truncation, not a large per-row height cut — see the "row-height truthing" comment block in `WidgetTheme.swift` for the full diagnosis, including the 2026-09-23 addendum and its measured numbers.
- **Budget**: reloads triggered by a widget's own intent, and by the app foregrounding, are free. Unprompted refreshes are budgeted, so the timeline policy is `.after(+30 min)` plus zero-cost entries pre-scheduled at each time-slot boundary and upcoming due time.
- **Undo / Redo (2026-09-23, replaces the old 60s window)**: `UndoRedoButtons` — two icon buttons (`arrow.uturn.backward` / `arrow.uturn.forward`), right-aligned before the chevrons, in ALL THREE kinds' `systemLarge` (and `systemMedium`, when it fits) headers — is ALWAYS present, not shown-then-hidden. Enabled state comes from the server's own counts, not a local clock: `WidgetStore.undoableCount`/`redoableCount` (a `-1` sentinel reads as "enabled" before the first fetch ever lands), refreshed on every widget fetch by piggybacking `GET /api/undo/status` onto `RemindersProvider`'s and `TaskFeed`'s existing network calls, plus updated optimistically the instant a local completion/`+1`/`−1` succeeds (`WidgetStore.recordLocalMutationForUndoCount()` — exact, since every mutation both adds one undoable entry and clears the redo stack server-side, `src/core/undo/log-action.ts`). Tapping either (`UndoLastActionIntent`/`RedoLastActionIntent`) calls `POST /api/undo`/`POST /api/redo` — the SAME endpoints the web toast's Undo/Redo buttons use, with no task id, so they act on "whatever changed/was-undone last" server-wide, not "this row specifically" — reload all three kinds (the one deliberate exception to `reloadOpenTaskWidget(kind:)`'s single-kind rule) and wipe every optimistic/confirmed marker in `WidgetStore` (`clearAllPendingState()`). A shared `WidgetStore.tryClaimUndoRedo()` in-flight claim (TTL-backstopped, not time-windowed) stops a double-tap or an overlapping Undo+Redo from firing two server calls for one intended action. The response's `description` is cached (`WidgetStore.recordLastAction`) and shown in place of the header's ordinary count subtitle — "Undid: …" / "Redid: …" — for `WidgetStore.lastActionWindow` (60s) on whichever slot/page happens to be on screen; each provider's `getTimeline` schedules an explicit expiry entry at that window's close (WidgetKit has no "expire after N seconds" primitive) so it reliably reverts to the ordinary subtitle. `WidgetStore.recordMutation`/`consumeLastMutation` still exist, narrowed to ONE job: correlating an undo with the Reminders auto-advance snapshot it might need to restore (see below) — not gating the buttons' visibility any more.
- **List paging (2026-09-23)**: where the Reminders/Tasks `systemLarge` list used to show "+N more" (a `Link` to the app), a `ListPager` (`‹ n/N ›`, non-wrapping, dims at the ends) now pages through the list in place — `ShiftReminderPageIntent`/`ShiftTasksPageIntent`. Page size is whichever `ViewThatFits` candidate's row count is currently winning (`RemindersListView.pagedReminders`/`TasksListView.pagedTasks`) — there is no way to ask ViewThatFits "which candidate won" from outside its own body, so each page independently resolves its own fit; see those functions' doc for the accepted (and in practice rare) imperfection that follows. The page index is stored per KIND (`WidgetStore.remindersPage(for:)`/`tasksPage(for:)`), paired with the slot/scope it was paged within so it self-resets to 0 the moment that slot/scope changes for ANY reason — a chevron, a jump, an auto-advance, or just the clock crossing into a new natural slot — without any of those call sites needing to remember a separate reset call.
- **Reminders slot strip and auto-advance (2026-09-23)**: `ReminderSlotStrip` draws one segment per slot with something in it (indigo = started and still waiting, green = started and finished, near-invisible = not started yet), mirroring the web's `ReminderSlotBar` for state/color but with equal-width segments (a widget has no room for the web's proportional layout). `systemLarge` only. Completing the last item in the on-screen slot auto-advances the widget to the EARLIEST slot (day's first through the slot the clock is in, inclusive) that still has something waiting (`RemindersTimeline.autoAdvanceSlot`, via the existing slot-override mechanism) — never forward into a slot that hasn't started. When every started slot is finished, the empty state reads "All caught up" instead of the per-slot "Nothing left here" / "\<Slot\> done". Each segment is its own tap target (`JumpToReminderSlotIntent`, same storage as the chevrons' `ShiftReminderSlotIntent` but addressed by slot key instead of an offset) — the finger target is taller than the 3-4pt bar via the same bleed trick `ReminderRow`'s check-off uses (`ReminderSlotStrip.segmentBleed`, half of `WidgetTheme.rowSpacing`), so it costs no extra row. The on-screen slot also draws a ring outside its bar (`.overlay(Capsule().stroke(...).padding(-2))`, not a stroke layered on the bar itself, which would eat into a 3-4pt fill) — the pre-existing height bump alone didn't read clearly enough at a glance (Trent, 2026-09-23: "we need some kind of outline... to show which segment we're currently on").
- **Deep links**: `opentask://today`, `opentask://reminders`, `opentask://reminders/slot/<slotId>`, `opentask://reminder/<id>`, `opentask://task/<id>`, `opentask://project/<id>`, `opentask://quota/<id>`, `opentask://quotas` — resolved to web paths in `OpenTaskApp.handleWidgetLink` (macOS: `OpenTaskMacApp.handleWidgetLink`, byte-parallel). A reminder row links to `reminder/<id>` → `/reminders?reminder=<id>` (its own surface, row brought into view and highlighted, no editor); `task/<id>` → `/?task=<id>&highlight=1` (the dashboard, row brought into view and highlighted, no editor — same shape as the reminder link); `quota/<id>` → `/quotas?quota=<id>` (the Quotas surface, same shape again — every Track widget row/card that links to a _specific_ quota uses this, never `task/<id>`, because a tracked id there lands on the full detail page instead, REDESIGN-V03, 2026-09-22). `quotas` (no id) → `/quotas`. **Header title links (2026-09-23)**: Reminders' header title links to `reminders/slot/<slotId>` (the ON-SCREEN group's `slotKey`, -1 for "Anytime") → `/reminders?slot=<slotId>`, bringing that slot into view rather than just opening the surface at the top — the bare `reminders` link (2×2, Lock Screen, background tap) still opens it unscoped. Tasks' header links to the bare `today` (→ `/`) on either unified page (Today or Up next), or `project/<id>` → `/?project=<id>` on a per-project page. The bare `/?task=<id>` (no `highlight` flag) is reserved for notification taps (`AppDelegate`/`MacAppDelegate` call `WebViewManager.navigateToTask` directly, bypassing `handleWidgetLink`) and Web Push, both of which still open the task's editor — `DashboardClient.tsx`'s `?task=` effect is what tells the two apart. `/quotas?quota=<id>` and `/reminders?slot=<id>`/`/?project=<id>` have no such ambiguity to resolve: nothing else currently deep-links into those surfaces with those params, so the bare param is unambiguous and carries no flag.
- **Tasks: Today / Up next / project pages (2026-09-23)**: the Tasks scope ring is now `[allProjects ("Today"), upNextScope ("Up next")] + per-project pages`, cycled by `ShiftProjectScopeIntent` — always ≥2 entries, so the chevrons never dim. "Today" is `TasksTimeline.todaysTasks` (due-or-overdue by end of local day, unchanged) and is what per-project pages still filter from; "Up next" is `TasksTimeline.upNextTasks` — the SAME three exclusions (undated/reminder/tracked) with NO end-of-day cutoff, soonest-due first. Both are project-less unified scopes (`TasksEntry.isUnifiedScope`), which is what gates two things: the header's project dot (shown only on a real project page) and each row's project CHIP (`TaskRow.projectChip` — the project's name in `caption2`, tinted with its color, sitting on the metadata line beside the due time; `systemLarge` only, reserved a fixed `WidgetTheme.projectChipWidth` budget that `minimumScaleFactor` shrinks a long name INTO rather than ever truncating the task title).
- **Due-date day-naming (2026-09-23)**: "anywhere a task time shows" (`TaskRow`, `TasksSmallView` — Reminders never shows a due time on any row) now reads a day word ahead of the time: "8:30 PM" (today, unchanged), "Tomorrow 9:00 AM", "Sun 9:00 AM" (2-6 days out), "Oct 1 9:00 AM" (7+ days out), "Oct 2" (date-only, no time at all). Overdue is DELIBERATELY UNCHANGED — always the plain time in red, never a day word. Date-only detection is an INVENTED convention (local time-of-day exactly midnight) — the wire format (`TaskDTO.dueAt`) has no date-only flag anywhere, and the web's own `DateTimePicker.tsx` defaults an unset time to 9:00 AM, not midnight, so there was no existing signal to key off. `WidgetTheme.dueLabelParts(for:now:isOverdue:)` is the ONE function both the styled `Text` render (`WidgetTheme.dueLabelText`) and the plain-string width measurement (`TaskRow.measuredLines`, via `DueLabelParts.plainString`) build from, so a row's reserved height always measures the exact string it renders.
- **Show completed (2026-09-23)**: an eye toggle (`ShowCompletedToggle`, self-contained, keyed by an arbitrary `kind` string so Track's own toggle can reuse it) sits left of `UndoRedoButtons` in Reminders' and Tasks' `systemLarge` headers only (a systemMedium card has no row budget for a DONE section). Off is exact current behavior; on appends a "DONE · N" divider (`DoneDivider`) and today's completed items below the open ones, struck through and muted, tap-to-restore. Persisted per-kind in the App Group (`WidgetStore.showCompleted(for:)`/`setShowCompleted(_:for:)`), NOT plumbed through the entry — it's pure local UI state, read live by the list views themselves. The combined open+divider+done sequence is built as ONE flat array (`ReminderListItem`/`TaskListItem`) and paged with the EXACT SAME `pagedReminders`/`pagedTasks` ladder the open-only list already used — `combinedItems.count` changing on a toggle flip is what makes `totalPages` recount, and slicing a flat array by row count can only ever break between two whole rows. Reminders' DONE data rides in `ReminderGroupDTO.consideredItems` (the same list `GET /api/reminders` already builds for "put back"); Tasks has no equivalent field on `/api/tasks`, so `TasksEntry.doneTasks` is populated from `GET /api/completions?since=&until=` (`APIClient.fetchTodaysCompletions`, always fetched inside `TaskFeed.snapshot` — never gated on the toggle, or flipping it on would render an empty DONE section for one repaint) filtered/scoped the same way the OPEN list is (`TasksTimeline.doneTasks`: reminders/tracked excluded always, a project page filters further, both unified pages show everything). Un-completing (`UncompleteTaskIntent` → `APIClient.markUndone` → `POST /api/tasks/:id/undone`, the SAME endpoint the web Reminders "put back" gesture uses) tombstones the item out of DONE instantly (`WidgetStore.pendingRestores`, mirroring the completion tombstone's shape/TTL) but does NOT synthesize it back into OPEN — `CompletionDTO` carries no due date/priority/labels to honestly reconstruct a `TaskDTO` from — instead it clears the interaction stamp so the next reload takes the network path and fetches the real restored task; net effect, an accepted asymmetry: the item leaves DONE instantly, reappears in OPEN one round trip later. A recurring task/reminder's restore can fail ("Task changed since it was completed" — same-day, already-modified-since-completion); this is treated like any other failure (the item honestly reappears in DONE for a retry), not given a special global-undo fallback. `WidgetStore.confirmCompletion`/`confirmRestore` cross-clear each other's tombstone (a fast re-complete-after-restore, or restore-after-complete, within the 90s window must not leave a stale tombstone hiding the item from the list it just moved back into).
- **Tasks snooze mode / bulk select (2026-09-23, Phase 2)**: a header clock (`SnoozeModeToggle`) and a bottom-left "Select" control (`SelectEntryButton`, resting mode only — mockup: `bulk.png`/`bulk2.png`, option 1) add two more mutually-exclusive Tasks-only row modes on top of "show completed" — `systemLarge` only, gated exactly like the eye toggle (`WidgetStore.tasksSnoozeMode`/`tasksSelectMode`; entering either clears the other and, for select mode, resets any in-progress pick). **Snooze mode**: each row's checkbox is replaced by its own "⏭"/"+1h" pair (`SnoozeTaskRowIntent`, `POST /api/tasks/bulk/snooze` with `ids: [taskId]` AND `include_task_ids: [taskId]` — an explicit, deliberate tap always bypasses the P3(High, only-once-nothing-lower)/P4(Urgent, never) sweep-safety filter, mirroring the web's OWN convention exactly, `src/lib/save-quick-panel-changes.ts`). A bottom "All overdue (N): ⏭ Next period · <time> · +1h" bar (hidden at N=0) sweeps the WHOLE server-side overdue set via the SAME `POST /api/tasks/bulk/snooze-overdue` the app's header clock button already uses (`APIClient.snoozeOverdue`, no client `include_task_ids` — this IS the sweep) — its count is a client-side ESTIMATE (`TasksTimeline.overdueSweepEligibleCount`, mirroring `filterForBulkSnooze`'s ceiling rule) from the raw open-tasks cache, not the current scope/page, since the sweep itself is scope-independent. **Select mode**: tapping a row toggles its pick (`ToggleTaskSelectionIntent`; the row's `Link` becomes a `Button`, and selected rows get an indigo background bled outward via negative padding on the fill layer so the row's own OWN reported size — and the row-height-truthing measurement built on it — never changes between picked/unpicked). Picks are a `Set<Int>` paired with SCOPE the same self-resetting way `tasksPage(for:)` is (`WidgetStore.selectedTaskIds(for:)`) — persisting across pages within one scope, never leaking into a different one. The bottom bar becomes "All [✓] · ⏭ Next period · +1h · ✓ · Cancel" (`bulk2.png`'s revision, adding "All" where "Select" sat); its two snooze actions go through `POST /api/tasks/bulk/snooze` with `ids`/`include_task_ids` BOTH set to the full selection (same "explicit selection bypasses the sweep filter" rule as the per-row buttons); "Done" reuses `CompleteTaskIntent`'s exact optimistic tombstone machinery, one `stagePendingCompletion`/`confirmCompletion` per selected id — no new completion mechanism. **`delta_minutes` has two different meanings depending on the endpoint** — worth knowing before touching either: `bulk/snooze-overdue`'s means "N minutes from NOW, snapped" (`snoozeOverdue(deltaMinutes:)`'s existing doc); `bulk/snooze`'s (every ids-based intent above) means "N minutes added to EACH task's own `due_at`" (confirmed against `src/core/tasks/bulk.ts`, and matched by the web's own bulk relative-snooze) — the SAME parameter name, two established, DELIBERATELY DIFFERENT server behaviors, each intent here mapped to whichever the web already does for that same gesture. "Next period" resolves differently too: server-side for the sweep (`slot: "next"` on `bulk/snooze-overdue`), but CLIENT-side for the ids-based endpoint (which has no slot mode at all) via `TimeSlotStore.nextPeriodStart()`, mirroring the server's own `nextPeriodStart`/`nextSlotStart` (`src/lib/time-slot-assign.ts`) — disabled (dimmed) on the per-row/select-mode "⏭" when `TimeSlotStore` has no cached slots yet (a widget-extension-only limitation: it only ever READS that cache, `TimeSlotStore`'s own doc). None of the snooze intents stage anything optimistically (unlike completion) — a due-date change can move a task to a different scope/page/sort position in ways neither this file nor the web app (`useSnoozeOverdue` just calls `fetchTasks()` once) predicts client-side; they call the API, `clearInteraction()`, and reload once.
- **A widget tap landing on the wrong tab (2026-09-23)**: a deep link tapped while the app is backgrounded on a NON-dashboard tab (e.g. Reminders, reached by an in-page SPA transition, never a native `navigate()` call) could open the app but leave it on the old tab instead of switching. Root cause, reproduced in the simulator (`ios/OpenTask/WebView.swift`'s `Coordinator`, instrumented with temporary `decidePolicyFor`/`didStartProvisionalNavigation`/`didFinish`/`didFail` logging — reached via a deep link to `/reminders` rather than an actual in-app tab tap, since the tab tap's pushState transition is invisible to this instrumentation; the race mechanism is the same either way): coming to the foreground fires TWO navigations at once — our own `WebViewManager.navigate(path:)` from `handleWidgetLink`, and a client-side redirect fired from the PAGE ITSELF (`router.push(loginUrlFromLocation())`, e.g. in `reminders/page.tsx`) — confirmed client-side (not our own request redirected server-side) because the `/login` this raced carried `callbackUrl=/reminders`, the OLD page's `window.location`, which only that still-loaded page's own `loginUrlFromLocation()` can produce. The likeliest trigger — not directly observed, but the only automatic session-recheck this app wires up — is `SessionProvider`'s NextAuth default `refetchOnWindowFocus: true`, firing on the same foreground/focus event and finding the session momentarily stale right after resume. When that competing redirect wins the race (cancelling our own request — logged as `didFailProvisionalNavigation`/`NSURLErrorCancelled` immediately before the `/login` decidePolicyFor), the existing `/login` rescue (`resumePath(fromLoginURL:)`) used to trust the redirect's callbackUrl unconditionally — which names the OLD tab, not the tap's actual destination. Fixed by tracking whether the navigation immediately preceding a `/login` bounce was cancelled (`Coordinator.lastNavigationWasCancelled`); when it was, `resumePath` trusts `lastRequestedPath` (set synchronously by `navigate(path:)`, before either navigation's network round trip) instead of the callback. See `resumePath`'s doc for the full mechanics and why the ordinary (non-race) case is unaffected. Every backgrounded-deep-link repro run in this investigation — control (dashboard) included — bounced through this `/login` detour once before landing; the fix corrects the destination but not that extra round trip, which may be worth a follow-up look.

**Adding a widget source file requires regenerating the projects** (`xcodegen` bakes the file list): `cd ios && xcodegen generate --spec project-sim.yml && xcodegen generate`.

### The two project specs

`project.yml` is canonical. `project-sim.yml` is **generated** from it by `ios/scripts/make-sim-spec.py` — it is the same spec minus the watchOS target, because generating and building the canonical spec requires the watchOS SDK to be installed, and without it every `xcodebuild` fails before compiling a single file (including iOS-only builds).

```bash
python3 ios/scripts/make-sim-spec.py            # regenerate project-sim.yml
python3 ios/scripts/make-sim-spec.py --check    # fail if it's stale
cd ios && xcodegen generate                     # canonical (OpenTask.xcodeproj)
cd ios && xcodegen generate --spec project-sim.yml   # sim (OpenTaskSim.xcodeproj)
```

Never hand-edit `project-sim.yml` — add targets to `project.yml` and regenerate, or the new target silently builds on one spec and not the other.

## Simulator Limitations

- **Notification content extensions cannot be tested in the simulator.** Long-press expansion is a known Apple limitation across all Xcode versions. Use a physical device.
- **watchOS notification actions cannot be tested in the simulator.** Mirrored notifications and action forwarding require a physical iPhone + Apple Watch pair.
- `xcrun simctl push` delivers banners but does not invoke service or content extensions.
- iOS 18.2 simulator: apps don't appear in Settings (known bug, fixed in 18.4+).

## Physical Device Caution

- **Avoid `devicectl device process launch` on a physical device** unless specifically needed. It kills the running app process, which can reset app state and force re-entry of credentials. Prefer letting the user launch the app themselves after install.
- **`install_app_device` (XcodeBuildMCP) / `devicectl device install app` is safe** — it replaces the binary without losing Keychain data or app state.

## XcodeBuildMCP Workarounds

XcodeBuildMCP is an MCP tool server for building and interacting with iOS simulators and devices from Claude Code.

- On iOS 26+, use `touch` (down+up) instead of `tap` to focus SwiftUI text fields — `tap` doesn't reliably activate them.
- WKWebView content is not exposed in the accessibility tree. Use screenshot coordinates for web view interactions.
- **watchOS device builds**: `devicectl` cannot reliably connect to the Apple Watch directly (shows "unavailable" even with Developer Mode on). XcodeBuildMCP's `build_device` and `install_app_device` also don't work for watchOS targets. Instead, deploy the watch app **through the iPhone** — the watch app is embedded in the iOS app bundle and iOS automatically syncs it to the paired watch over Bluetooth:

  ```bash
  # 1. Build (from ios/ directory) — builds both iOS and watchOS targets
  xcodebuild -project OpenTask.xcodeproj -scheme OpenTaskWatch \
    -destination 'generic/platform=watchOS' \
    -allowProvisioningUpdates -allowProvisioningDeviceRegistration \
    -derivedDataPath build build

  # 2. Install the iOS app on the iPhone (the embedded watch app syncs automatically)
  xcrun devicectl device install app --device IPHONE_UDID \
    build/Build/Products/Debug-iphoneos/OpenTask.app
  ```

  - Get the iPhone UDID: `xcrun devicectl list devices`
  - The watch app lives at `OpenTask.app/Watch/OpenTaskWatch.app` inside the iOS bundle
  - If the watch shows "unavailable" in devicectl, try `sudo pkill -9 remoted` on the Mac to force a reconnection (though direct watch install is not needed with this approach)
