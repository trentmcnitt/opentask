# Task Model

Complete reference for the OpenTask task data model: deadline, target and horizon, task segments, priority, recurrence, snooze, quotas and undo. The main `AGENTS.md` has a brief summary; this file has the full details.

## Deadline, target, horizon

The 2026-10-10 task model. Until then one field, `due_at`, carried four different things: real deadlines, the times Trent wanted to start, AI placeholders, and pure awareness. Daily bulk snoozing bent it until "overdue" meant nothing ("I have 25 overdue things, and I'm really not overdue on 25 things" — Trent, 10-10). Now a task carries a separate answer for each question:

| Column        | API name                                | Meaning                                                                                                    | Moved by                                                       |
| ------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `due_at`      | `target_at` (`due_at` deprecated alias) | The **target**: when nagging starts. A soft commitment to a day and time. Never after the deadline         | Any move ("Snooze" in the UI), remove target / Back to auto    |
| `deadline_at` | `deadline_at`                           | The **deadline**: the real cutoff. It can move, but only deliberately                                      | Only an explicit write of the field. Never a snooze            |
| `horizon`     | `horizon`                               | How soon it should get done, its pace: `days`, `weeks`, `months`, `eventually`, or `null` (unset, = weeks) | Only an explicit write. Nothing grows or shrinks it on its own |
| `priority`    | `priority`                              | Unchanged: what missing it costs                                                                           | Unchanged                                                      |

Target, deadline and horizon are each nullable, but tied by two rules since 2026-10-12 (spec §8): **a one-off with a deadline always has a target** (the deadline's stored automatic target, if the user picked none), and **the target is never after the deadline**. The pure rules live in ONE module, `src/lib/task-segments.ts` (each constant named once), shared by the server and the web UI — the native apps get them through the API (`attempts_label`, `attempts_offer`, `age_label`, the segments). `tests/behavioral/tm-task-model.test.ts`, `tm-auto-target.test.ts`, `tm-occurrence.test.ts`, `bg-badges.test.ts`, the seeded random invariants in `tm-invariants.test.ts` and the golden suite have the rules as tests (see [Testing the model](#testing-the-model-the-golden-suite-and-the-day-simulator)).

### API names

`target_at` is the primary name for the target, in requests and responses. `due_at` is its deprecated alias: older native builds, Shortcuts and the desks send it, so it is still accepted, and it is still returned with the same value (`formatTaskResponse`). The DB column is still `due_at`. `normalizeTargetAliases` (`src/core/validation/task.ts`) maps the names on create, update and the `changes` of a bulk edit. Sending both names with different values is a 400, never a guess.

Old clients' flags are accepted and change nothing (rulings Q1/Q4, 2026-10-12): `retarget` (alias `reset_original_due_at`) is a plain move on a task (on a reminder it is still the explicit reschedule a period move sends, see [Snooze](#snooze)); `allow_past_deadline(_ids)` and `cap_at_deadline(_ids)` change nothing, since every move stops at the deadline; `deadline_nag_off` is ignored (an old "Remove target" sends it with `target_at: null`, which on a deadline task is now Back to auto).

Reads also expose `deadline_at`, `horizon`, `horizon_set_at`, `last_considered_at`, `segment_deferred_at`, `segment_targeted_at`, `target_set_at` (when the target was last set, see [Upcoming](#upcoming)), `target_auto` (the target is the deadline's automatic one), `occurrence_at` (a repeating task's scheduled occurrence, see [Recurrence Model](#recurrence-model)), `original_due_at` (the first-target date), and the two badges' fields — `attempts`, `attempts_counted_through`, `attempts_label`, `attempts_offer`, `age_label`, `growth_kept_at` (see [The two badges](#the-two-badges-attempts-and-age)). `deadline_nag_off` is no longer stored, but is still returned for shipped native builds: computed per response, `true` only for a one-off whose deadline has passed and whose target is after it, `false` otherwise — so those builds' own implied-target rule reads the task's own target (see [Native builds](#native-builds)). `is_snoozed` and `snooze_count` left the API on 2026-10-12: there is no snooze state.

### Target

The target is when a task starts nagging: the dashboard's over-target list, the overdue notifications, the app-icon badge. **A target the user picked makes a task quiet until its date** (2026-10-12, reversing 10-10's "horizon before the target"): a one-off with a picked target is in no horizon segment, and before the date it shows only on its [Upcoming](#upcoming) heads-up days. A one-off with no target, or with a deadline's **automatic** target (`target_auto`, see [Deadline](#deadline)), sits in its horizon's [task segment](#task-segments). **Never two places at once.** The dashboard's main task list, **Now** (2026-10-14, `src/lib/now-view.ts`), follows the same split: each project shows only what is relevant now — over target, targeted today (automatic targets included, once their day comes), in today's Upcoming heads-up (not deferred), or undated High/Urgent — and folds the rest, future-targeted tasks included, behind "+ N more in <Project>". "Show all" lifts the folds; a search or filter lifts them too. A task that wants occasional early glances should have no picked target: a deadline plus a horizon.

| State                                                                              | Where it shows                                                                                             |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| No target, or the deadline's automatic target not here yet                         | Its horizon segment, on the check-in rhythm. A deadline pulls the horizon in as it nears. No Upcoming rows |
| A picked target (a one-off's, or a repeating task's next occurrence), not here yet | No horizon segment. Upcoming, on its heads-up days only                                                    |
| Target arrived (picked or automatic)                                               | Over target: dashboard, notifications, badge                                                               |

`hasPickedTarget` (`src/lib/task-segments.ts`) is the one test: a target that is not `target_auto`.

**On deck** (2026-10-20, see [On deck](#on-deck)) is a third place that keeps "never two places": a task on deck has no picked target (decking drops it; a pick clears the deck), is in no horizon segment, shows in Upcoming on its heads-up days and on its day in the On deck section, and never nags — unless it is a deadline task whose automatic target has arrived.

**The first target.** `original_due_at` is the first-target date. It no longer drives a badge (the attempts badge replaced the target-age "2d" tab, spec §7), but it is still written for shipped native builds, which read it as their age clock:

| Change                                                               | `original_due_at`              |
| -------------------------------------------------------------------- | ------------------------------ |
| Any move (every snooze; `retarget` from old clients changes nothing) | Kept: the age keeps counting   |
| A task with no target gets one (any path, including "Target today")  | = the new target: age restarts |
| A deadline's automatic target is stored                              | = that target                  |
| A repeating task's done / skip                                       | = the next occurrence          |
| Remove target (`target_at: null`, no deadline)                       | Cleared                        |

A no-target → target change always restarts the clock, even if a stale origin is somehow still stored, so a fresh target never shows an age inherited from an old one (`collectDueAtChanges`, `src/core/tasks/helpers/collect-field-changes.ts`).

**The attempts tab.** A row with a target and at least one attempt carries a corner tab with the count ("3×"): local days on which it was over target (see [The two badges](#the-two-badges-attempts-and-age)). It replaced the target-age "2d" tab on 2026-10-12.

**Remove target** sends a one-off with no deadline back to its horizon's segment (the row's snooze menu, the editor's … menu, Upcoming's target chip). **A deadline task never loses its target** (§8.3): in the same places it offers **Back to auto** instead — only when its target is one the user picked (ruling Q9); an automatic target offers neither. Back to auto is `target_at: null` on a deadline task: the server stores the automatic target again, computed from that moment (nothing records when the deadline was first set). One rule decides what each surface offers: `targetReset` (`src/lib/task-segments.ts`). A repeating task's target is never removed in the editor (PR 4c): its rule goes only with every-time mode's "Stop repeating" (a one-time task keeping its target and deadline).

There is no automatic target lapse. Over-target items are cleared by done, remove target / Back to auto (which the row offers at 3×), Process (targets missed on 3 or more days, `ATTEMPTS_OFFER_REMOVE`; it lists deadline tasks apart and unchecked, and never an automatic target) and review.

### Deadline

> **The deadlines page replaces the automatic target (2026-10-22, task-queue switch ON).** With `OPENTASK_TASK_QUEUE=1` no automatic target is ever written: a deadline task with no target is target-less, and the [deadlines page](#the-deadlines-page) holds it from its lead day, with a safety net from the day before the deadline. Points 1, 3, 4 (its automatic half) and 5 below, and Back to auto, are then the switch-OFF behaviour, kept for one release (plan A1) and then deleted. Point 2 (the cap) holds either way.

`deadline_at` is an ordinary field. No snooze path ever sends it, which is what keeps a snooze from moving it. Enrichment sets it only from an outside date stated in the wording: an AI-guessed deadline is worse than an AI-guessed date, because it caps snoozing.

**A deadline always has a visible target** (spec §8, 2026-10-12 — Trent: "the Friday-morning deadline-day nag is adding a required target, but through some other invisible mechanic, which I do not like"). It replaced the read-time implied target, `deadline_nag_off` and the deadline-day re-arm (ruling A4).

1. **Stored, not computed.** A one-off (not a reminder, not a quota) with a deadline and no target the user picked carries a real stored target, flagged `target_auto`, by the **wait** — local days from now (when the deadline is set) to the deadline's day — through ONE lead table shared with a deadline-anchored repeat's default target (2026-10-21, Trent: "one rule everywhere"; `leadTargetFor` / `deadlineLeadDays` in `src/lib/task-segments.ts`, Upcoming's constants): under 2 days, the deadline day at the user's `morning_time` (or the deadline's own time if that is earlier); 2–7 days, the day before; 8–15, 3 days before; 16 or more, 4 days before — at `morning_time`. If that moment has already passed, the target is now (ruling Q10): over target at once. Never after the deadline, so a deadline already past gives the deadline itself. `autoTargetAt`; every automatic target goes through the one table, so replacing them is one change. Examples (morning 9:00): deadline Fri Oct 23 23:59 set Mon Oct 12 → wait 11 → Tue Oct 20, 9:00 AM; set Mon Oct 19 → wait 4 → Thu Oct 22, 9:00 AM (until 2026-10-21 a 2–7-day wait took 3 days, too). **Only new or changed deadlines use the table**: a stored automatic target is not re-derived until its deadline is next written (no backfill). The editor labels it "auto · … (1 day before deadline)".
2. **Target ≤ deadline while the deadline is ahead.** Every move — `PATCH { target_at }`, the snooze endpoint, bulk snooze, snooze-overdue, bulk edit, Today and its picker, native quick snoozes and notification buttons — stops AT the deadline (`capAtDeadline`). There is no "past the deadline anyway": to go later, change or remove the deadline. A capped move says so: the description reads "Snoozed to deadline 6:00 PM", the response carries `capped_at_deadline` (single) / `capped_deadline` (bulk, a count), and a native quick snooze that sent `cap_at_deadline` (the content extension's custom time) or a notification button gets the quiet "Snoozed to deadline" push (`deadline-cap-feedback.ts`, ruling A3). **Once the deadline has passed** the cap is off (Trent's ruling, 2026-10-12): a single snooze or re-target can pick any target, later or earlier, and the row keeps its red "past deadline …" marker. In a **bulk** snooze a passed deadline puts the task in the High tier (see [Priority and bulk snooze](#priority-and-bulk-snooze)). The web toast for a sweep adds "· N stopped at their deadline". The pickers offer **Deadline day** (ruling Q8): the user's morning on the deadline's local day, or the deadline itself if earlier (`deadlineDayTarget`; the row's snooze menu, the editor's target picker, a segment row's Today picker) — never once the deadline has passed, nor once that morning has gone (`deadlineDayPick`).
3. **No Remove target on a deadline task**: Back to auto (see [Target](#target)).
4. **Deadline changes.** An automatic target moves with the deadline (re-derived from that moment). A **relative** target (2026-10-24, [below](#relative-targets)) moves with it too — re-derived from its offsets, and its `target_set_at` restamped; removing the deadline leaves it where it is, as a fixed target (ruling 5). Any other target the user picked stays, pulled back to the deadline if the new deadline is earlier. Removing the deadline removes an automatic target and leaves a picked one.
5. **Only a picked target is quiet.** An automatic target keeps the task on its horizon rhythm, with the deadline pull-in, until the target's day, then it nags. It has no Upcoming rows.

One function applies all of this to every writer — `resolveTarget` (`src/lib/task-segments.ts`), called by `collectFieldChanges` (update, bulk edit, bulk snooze, snooze-overdue, the snooze endpoint, Today), `createTask` and AI enrichment; completion and skip cap the advanced target too. Past the deadline, nagging continues (Trent: "sometimes it's for a client and you're in a rush, so we can't just stop nagging"), and the over-target row carries a past-deadline marker (`isPastDeadline`).

**The migration** (`src/core/db/migrate-deadline-targets.ts`, a `runMigrations` data step, idempotent, logged when it does something): repeating tasks get `occurrence_at` (see [Recurrence Model](#recurrence-model)); one-offs with `deadline_nag_off` and no target get an automatic target (the flag cleared); one-offs with `deadline_nag_off` and a target of their own keep it exactly, as a picked target (`target_auto = 0`, `due_at` and `target_set_at` untouched; only the flag cleared); one-offs with a deadline and no target get one; targets after a deadline **still ahead** are pulled back to it (a passed deadline caps nothing, so its target is left). `npx tsx scripts/count-target-migration.ts <copy.db>` prints each step's count and task ids (ids only), read-only. The `deadline_nag_off` and `snooze_count` columns are left in place (unused) so undo entries written before still apply.

**A repeating deadline is the schedule** (2026-10-21, the weekly Upwork lock; see [Deadline-anchored repeats](#deadline-anchored-repeats)). A repeating task with a deadline is DEADLINE-ANCHORED: its rule walks the deadline, and its target is derived from it at a fixed local offset. `advanceDeadline` (the "same distance after the new occurrence" carry of a rule that walked the target) is gone. Repeating tasks never get an automatic target (`target_auto`): their target is scheduled, not a lead-in.

### Relative targets

**2026-10-24** (plan `plan-relative-targets-1024.md`, APPROVED 10-24 — PR A the server; PR B the web, below; enrichment PR C). A one-off with a deadline can carry a target RELATIVE to it — "the evening before", "the morning of" — that moves with the deadline. It is the same three columns a [deadline-anchored repeat](#deadline-anchored-repeats) stores, and ONE derivation for both:

| Column               | Meaning                                                                                                                                             |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `target_days_before` | Local calendar days from the deadline's date back to the target's (0 = the deadline day)                                                            |
| `target_time`        | The target's local time (HH:MM). Linked: always the period's CURRENT start                                                                          |
| `target_slot_id`     | The reminder period the time follows (a link, no foreign key — the `quota_prompt_slot_id` precedent), or NULL for a custom time. The OWNER's period |

**One derivation.** `relativeTargetAt(deadlineAt, {days_before, time}, timezone)` (`src/lib/task-segments.ts`, pulled out of `occurrenceDates`, which now calls it): the deadline's local date minus the days (Luxon calendar days — a DST change between them never shifts it), at the time through `localMoment` (a skipped time → the next valid minute; a repeated one → its first instant), clamped to the deadline. In the task OWNER's zone. Nothing else does date maths on the offsets (guard RT-G01).

**A relative one-off** (`isRelativeOneOff`): no rule, a deadline, both offsets, not a reminder or a quota. Its target is a PICKED one (`target_auto` 0, `hasPickedTarget`): quiet until its [Upcoming](#upcoming) heads-ups, never on [the deadlines page](#the-deadlines-page) (it has a target), a 3× attempts offer like any target. A derived target already past is over target at once (ruling 3).

**What a write does** (`resolveTarget`'s four rules, judged before the automatic target; every writer goes through it — PATCH, bulk edit, create, the snooze endpoint, bulk snooze, snooze-overdue, Today, enrichment):

1. any non-null `target_at` makes the target FIXED: the offsets and the link are cleared (a pick, every defer, Today, a native quick snooze, a notification button — ruling 1);
2. `target_at: null` clears everything (Remove target, the 3× offer, Process, decking — a deck and a relative target never coexist);
3. `deadline_at: null` keeps the current target, fixed (ruling 5);
4. otherwise the offsets and the deadline give the target — re-derived on every deadline write (which restamps `target_set_at`, so the wait starts again) and every offset write.

`{target_days_before: null, target_time: null}` alone makes it fixed where it is. **400s** (`assertOneOffRelative`, `src/core/tasks/relative-target.ts`): offsets with no deadline; only one of the pair; `target_at` with offsets (ruling 7); `deadline_at: null` with offsets; the same day at a time after the deadline's (a later deadline move alone clamps instead); offsets on a reminder or a quota; offsets with `on_deck_day`; a period that isn't the owner's (a collaborator's own, on a shared task).

**The link** (`linkTargetTime`), resolved at WRITE time through anchor-times' `resolveTime`: `target_slot_id` sets `target_time` to the period's start (another `target_time` in the same body is a 400); `target_time` alone is a custom time and unlinks; `target_slot_id: null` unlinks and keeps the time. **Invariant**: a linked row's `target_time` IS its period's current start — unlike Morning / Wake / Sleep, which store a snapshot and look the period up when read — so every reader, and every advance (done, skip, Skip until, put-back, the rollover's undeck), reads stored columns and never looks a period up. Guard RT-G03: every writer of `target_slot_id` resolves it (or is a period hook, or exempt).

**A period retime** (`updateTimeSlot`, `src/core/time-slots/edit.ts`), inside its one `time_slot_edit` undo entry: every OPEN linked row follows (the period sent again) — a one-off re-derives its target, a deadline-anchored repeat its unmoved one (a moved one is kept, the offsets being the series'). A row the new time would be refused for (`retimeRefused`: a one-off's deadline day after its deadline; `after_deadline` / `overlaps_previous` against a repeat's rule) is UNLINKED and keeps its old time (decision 13) — the retime never fails because of a task. No `target_set_at` restamp (decision 11: the user didn't set a target; `stampTargetSet`'s `keepSetAt`), but the attempts checkpoint still fires; `original_due_at` unchanged, never a snooze. CLOSED rows (done, archived, trashed) get the new `target_time` only, in ONE compare-and-set statement recorded in `slot_state.target_times` (decision 14) that undo and redo mirror (`applyTargetRows`, `src/core/undo/slot-row.ts`); their `due_at` is re-derived when reopened (put back, restored — `rederiveOnReopen`). Known gap: `/api/undo` of a done task restores the `due_at` it had, which a later retime may have made stale. The response's `targets_moved` / `targets_kept`; the description "Moved "Evening" to 9:00 PM (2 reminders, 5 targets; 1 kept its time)".

**A period delete**: linked rows keep the period's start as a custom time — like the anchor settings, not the nearest period. Open rows through the entry's snapshots (`target_slot_id` → NULL; time and target unchanged), closed ones in one statement recorded in `slot_state.target_unlinked`; undo re-links compare-and-set (only rows still unlinked at the period's start); redo unlinks whatever links to it then. `targets_converted`.

**Repeats** share the shape: a deadline-anchored repeat takes `target_slot_id` too, and its every advance derives the next occurrence from the stored `target_time` (which follows the period). **Stop repeating** (`rrule: null`, ruling 6, a behaviour change) keeps the offsets and the link — a relative one-off — when the deadline stays, this occurrence's target wasn't moved and it isn't on deck (`stopKeepsRelative`); otherwise they go, as before. **Make it repeat** on the deadline keeps them, checked against the rule (`relativeTargetProblem`); on the target, they go (a target-anchored repeat has none).

**Undo** holds the target, the three columns, the deadline and `target_set_at` in one snapshot (`collectRelativeTarget` writes all three together). **A restored link is always re-validated against the current period** (`healRelativeLinks`, `src/core/tasks/relative-link-heal.ts`; guard RT-G05): undo stacks are per user (a collaborator's undo can restore a link from before the owner retimed or deleted the period) and a fence can skip a snapshot whole (the rollover's, on a decked repeat it took off deck after a retime), so every undo and redo runs one rule over every task its entry touched — applied or skipped, plus a period entry's linked rows. A link to a period that is gone is unlinked, keeping the time; a closed linked row takes the start as its time only; an open deadline-anchored repeat whose linked time is off is written as the retime writes it (unlinked where the start would be refused); and EVERY open relative one-off, linked or custom, is checked whole — its time is the period's start while linked and allowed (else unlinked), clamped to the deadline's time on the deadline day (as a deadline move clamps the target), and its target re-derived whenever the time, the link or the target is off. Every open write goes through `collectFieldChanges` with `retime`: attempts checkpointed, `target_set_at` kept. A refusal from any other rule unlinks the row and is logged (`log.warn`), never thrown — a throw would wedge the undo stack. Nothing goes in the undo log. Not covered: a plain FIXED target can still end up after a deadline through a cross-user undo (true before relative targets). The [auto-target fence](#the-deadlines-page) nulls them with the automatic target it drops. **Activity**: "Target the day before at Evening (8:30 PM)" (linked), "…at 6:00 PM" (custom); a pick that clears them reads as the pick.

**The web editor** (PR B, `src/lib/relative-target-ui.ts`, `src/hooks/useRelativeTarget.tsx`). ONE control, `RelativeTargetControl` — `[the day before ▾] at [Evening · 8:30 PM ▾]`, the user's periods first, then "Custom time…" (a time field appears only for a custom time; Settings' `AnchorTimeRow` pattern) — in every-time mode's Target row on a deadline-anchored repeat and in the target picker of a one-off with a deadline ahead, whose "Before the deadline" block also has chip rows "The day before" and "The deadline day" (one per period; a moment past is left out, a deadline-day period after the deadline greyed). The block replaces the editor picker's "Morning of the deadline" (ruling 4; the defer menu and the Today picker keep theirs). The Target row reads "Mon, Nov 2, 8:30 PM in 9 days · the day before, Evening · moves with the deadline" (custom: "· the day before · …"); a staged deadline shows the target it gives, blue. A pick is staged and saved with a staged deadline in one PATCH — `{target_days_before, target_slot_id}` linked, `{target_days_before, target_time}` custom; every pad tap, Set Date, Now, Next Hour and Remove target make it fixed (ruling 1). With nothing picked the control opens on the day before at Default task time, linked or custom as the setting is (ruling 10). 0 days reads "the deadline day" everywhere — the control, the row, a repeat's Deadline line, the activity log (Trent, 2026-10-24; it was "the same day"). Periods are offered on the user's own tasks only (a collaborator can't read the owner's; a stored link reads as its time). Settings' retime toast says "1 target follows" / "1 target keeps 8:30 PM"; a removal's "5 targets keep 8:30 PM". Every-time's Stop repeating hint says when the relative target is kept (`stopKeepsRelativeTarget`, the client's `stopKeepsRelative`).

**Native builds** need nothing: an old build's defer makes the target fixed (capped at the deadline), and they never see the period. A time-zone change doesn't re-derive stored targets (as for repeats). The migration: none — `target_slot_id` NULL (custom) on every existing row; no code path before 10-24 left offsets on a one-off (every writer nulled them off the deadline anchor). Tests: `tests/behavioral/rt-relative-target.test.ts` (RT, RT-G01..G04), `ts-relative-targets.test.ts` (TS-RT), TM-INV-12, the golden `tests/golden/relative-target.ts`.

**Every time** (`quick-panel/EveryTimePanel.tsx`; the pure core is `src/lib/every-time.ts`). ### Horizon

How soon the task should get done. It decides which [task segment](#task-segments) the task appears in, and nothing else. `null` is unset: treated as `weeks`, but never reported as set (`task.horizon` stays null, and the UI says "Unset"). Enrichment sets it only from explicit pace wording ("sometime this month"). Changing it restarts `horizon_set_at`, the clock Process reads to ask whether a horizon should grow; re-sending the same value is not a change.

**Effective horizon** (`effectiveHorizon`) is the sooner of the set horizon (unset = weeks) and the one the deadline implies:

| Deadline         | Implies  |
| ---------------- | -------- |
| ≤ 7 days away    | `days`   |
| ≤ 21 days away   | `weeks`  |
| ≤ 90 days away   | `months` |
| Further, or none | nothing  |

A deadline only ever pulls a horizon **in**. Nothing grows one on its own: growth is Process asking and the user saying yes. The 90-day step is this build's call, so a deadline months away still surfaces monthly on an "eventually" task.

The dashboard's `horizon` sort (`src/lib/task-grouping.ts`) orders over target first, then effective horizon, deadline, priority, newest. It is the default sort for new users since 2026-10-11 (`users.default_sort` defaults to `horizon`); a saved sort is never changed.

### Over target

"Overdue" (ruled by Trent 2026-10-21) is a task whose target (picked or automatic) has arrived. From 2026-10-10 to 2026-10-21 the UI called it "over target"; it is "overdue" again, the same word the code, the API and the query parameters always used — see [Over target (overdue)](#over-target-overdue) for the code. The UI word lives in one constant, `OVERDUE_WORD` (mid-sentence `OVERDUE_LOWER`) in `src/lib/task-model-words.ts`, beside `HORIZON_WORD` and the horizon labels. "Horizon" is still **PROVISIONAL** ("doesn't resonate"). The native apps keep their own copy (still "over target" until the native word pass).

## Task segments

Rules in `src/lib/task-segments.ts`; reads and actions in `src/core/tasks/task-segments.ts`; the row in `src/components/TaskSegmentRow.tsx`, the Reminders-screen section in `src/components/reminders/TaskSegmentGroup.tsx`, the panel page in `src/components/DashboardRemindersPanel.tsx`.

A task segment lists tasks for awareness, on the reminders screen: one-off tasks with no target in their horizon's segment, and targeted tasks on their heads-up days in [Upcoming](#upcoming). It answers "out of sight, out of mind": a squeaky door isn't worth today, but without being reminded at some clip, the day it would fit naturally is missed too.

**Which tasks (horizon segments).** The user's own open, one-off tasks with **no target the user picked** (since 2026-10-12): not deleted, not archived, not recurring, not a reminder, not a quota. Only the owner's: a task in someone else's shared project is theirs to consider. A deadline task with its automatic target is here until that target arrives (it has no Upcoming rows; the pull-in already shows it — a 23:59 deadline 11 days out: Days on D−6 to D−4, then nagging from D−3). A target later **today** takes a task out (`targetIsToday` compares local days).

**One segment per effective horizon, each on its own day** (`latestSegmentDay`), on the user's **check-in day** (`users.check_in_day`, Settings → "Check-in day", 2026-10-12): Luxon weekday numbering, 1 = Monday … 7 = Sunday, default 6 = Saturday. It is its own setting, independent of `week_start` (the quota changeover), and plays no part in Upcoming.

| Horizon      | Comes round                                                           |
| ------------ | --------------------------------------------------------------------- |
| `days`       | Every day                                                             |
| `weeks`      | Every check-in day                                                    |
| `months`     | The first check-in day of the month (it stacks with weeks that day)   |
| `eventually` | The first check-in day of each quarter: January, April, July, October |

**Panel titles (Trent, 2026-10-20).** Every segment's header has one format, "Task queue · <word>" (a middle dot, shown uppercase): **TASK QUEUE · DAILY**, **· WEEKLY**, **· MONTHLY**, **· QUARTERLY** (`days` … `eventually`), **· UPCOMING**, and the task queue's own **· TODAY'S PULLS** and **· PREVIOUS PULLS** (2026-10-21; "Staged" and "Previously staged" until then: "Stage is what happens before something goes live, whereas this is for things that were taken off and that potentially will stay off") (the words in `SEGMENT_TITLES`, `QUEUE_PANEL_TITLES`, `UPCOMING_LABEL`, the prefix in `taskQueueTitle`, all in `src/lib/task-model-words.ts`; `segmentTitle` in `src/components/TaskSegmentRow.tsx`). No hint after it. The horizon-move toast keeps the bare word ("Moved to Monthly"). These are display words: the segment kinds the API sends do not change. The horizon picker and the row corner's tooltip still say when each horizon comes round ("Tuesdays", "1st Tuesday": `horizonHints`).

A segment has rows only on a day it comes round (above). **The web shows every segment, every day, in fixed positions** (Trent, 2026-10-24; `GET /api/reminders?fill=1`): the server sends every kind the web draws in `SEGMENT_ORDER` — the deadlines page first, then the queue's two panels (both with the switch on), Daily, Upcoming, Weekly, Monthly, Quarterly — an empty one with no rows. An empty segment is **done** from the start of the day: a green bar in the dashboard strip and the /reminders day bar, "0 of 0 ✓" in its header, "Nothing today ✓" on its page or section. The dashboard card still opens on the first segment with something waiting, and collapses to its one line ("Tasks · N of N ✓") when nothing waits anywhere. Display only: placement is unchanged. Without `fill` (a native build) a segment comes only on a day it has items.

**Carry-over.** A task appears once its segment has come round since the task was last **seen**, and keeps appearing, day after day, until it is considered ("anything not considered shows again the next day until it is"). Seen is the later of `last_considered_at` and `created_at`. Writing a task down is seeing it, so a weeks task added on Tuesday waits for the next check-in day.

**States** (`segment_state` on each row): `waiting`; `considered` (considered today); `deferred` (Defer All today: off today's list, back tomorrow). The web lists only `waiting` rows; the header counts "X of Y" like a slot (X = considered + deferred today, Y = the segment's rows today), and "Show N considered" unfolds the rest, each with a put-back (`POST /api/task-segments/restore`, which clears both stamps; 2026-10-11).

**The day roster** (2026-10-22, Trent's phone review: "29 of 44" became "29 of 43" after a deck): Y is everything that came round TODAY, fixed for the day, and X every row handled today — considered, deferred, decked, targeted (Today) or done. On deck, Today and done take a row OUT of its segment, so with `GET /api/reminders?handled=1` (the web) the server remembers every row each segment lists for that segment's day (`segment_roster`; the user's OpenTask day for every panel since "Day starts at" PR 2 — until then the calendar day for all but the queue's panels) and sends a remembered row that has since left it handled as a `considered` row with `segment_left` (`done` · `deck` · `target` · `considered` — a queued one-off considered out of the queue). It counts in X and Y and sits behind "Show N considered" with no put-back (its way back is Undo). A row that left unhandled — trashed, its heads-up over, its horizon or target changed — drops out of Y. One rule for every panel: `segmentCounts` (`src/components/TaskSegmentRow.tsx`) on both surfaces, `src/core/tasks/segment-roster.ts` on the server. Known limit: a row handled before any read that day was never remembered. Without `?handled=1` (the native builds, the day simulator, the golden suite) the segments hold only the rows listed now, and a task marked done leaves its segment entirely.

**Order.** Priority, then id (Upcoming: the target, then id). Horizon decides **whether** a task shows, never where, so acting on one never reorders the rest under the finger (the 09-05 rule).

**Over 50 items** (`nudge`, strictly more than `SEGMENT_NUDGE_THRESHOLD`) the segment suggests Process or AI help instead of a tap-through.

**Never counted, never notified.** Segments are not in `groups[]`. Their rows never count in the nav badge, "Considered all so far", the slot notifications or the unfinished-slot nag, and a segment never sends a notification. **The headline counts them apart** (Trent, 2026-10-26, ruling "B": count "reminders and queue tasks SEPARATELY, e.g. '75 reminders · 84 tasks considered'"): with the task queue on, the Reminders page's headline counts everything its day bar draws — the periods (reminders and quota prompts) as one half, every task segment as the other, each segment by its own header's "X of Y" (`segmentCounts`) — so "14 reminders · 3 tasks waiting so far", "40 of 75 reminders · 30 of 84 tasks considered", and the green "All 75 reminders · 84 tasks considered today" only once both are handled; an empty half is dropped. While only later periods hold reminders, "Caught up until Evening · 6:00 PM" stays, with any tasks waiting after it ("· 3 tasks waiting"). Full words at every width: on a phone (< 640px) the count takes its own line under the full-width bar (Trent, 2026-10-26, layout "b"), from 640px it sits beside the bar. With the switch off it reads as before, reminders only (`headlineCounts` in `src/lib/reminders-summary.ts`). Anything time-critical has a target, and a task whose target has arrived is on the dashboard, not here.

**Where it shows.** After the periods, and shaped like one (Trent, 2026-10-11: "days, weeks, etc. should be individual segments and behave similarly to the segments for reminders"; earlier the same day each was a card of its own under the periods, and 10-10 had them first). On the Reminders screen each segment is a section like a period's: the collapsible header ("TASK QUEUE · DAILY", "X of Y"), the hairline, the rows, and "Show N considered" with put-back; "Defer all" sits where a period has "Considered all". On the dashboard the segments have their own **Tasks card**, directly under the Reminders card (Trent, 2026-10-11: "i liked the reminders on top of tasks like it was before"; for part of that day they were pages of the period pager). The Reminders card pages through the periods alone, as before. The Tasks card is a pager of the same shape across today's segments: its own strip of bars (proportional, gray track, purple while filling and green when all handled — see **Colours** — the page on screen drawn taller), the same chevrons, header ("TASK QUEUE · DAILY"), row cap and "Show more", the "X of Y" that opens what was considered with put-back, and "Defer all" behind the header tap. It opens on the first segment with anything waiting and, when one is finished (last row or Defer all), moves to the next that waits (`usePanelPager` with no slot pages: `naturalPageIndex`, `pageAfterFinishing` in `src/lib/time-slot-assign.ts`); it never lands on a finished segment while another waits. With every segment finished it collapses to one line, "Tasks · 75 of 75 ✓", whose count still opens what was considered. A horizon change that moves a row to another segment says so, by the panel's title: "Moved to Monthly". Rows use the slot rows' exact geometry on each surface (panel: 19px controls, 13.5px title; page: 24px, 16px), so circles and checkboxes line up down the column. The native surfaces follow: the Reminders widget's page ring is slots then segments with the clock's slot as the natural page, and the watch shows segments after the period's rows.

**Colours** (2026-10-11, Trent's pick): one teal per horizon, darkest for the soonest — the `--segment-*` tokens in `src/app/globals.css`. Fills, light: Days `#0f9d8f`, Weeks `#2bb5a6`, Months `#4fb8ab`, Eventually `#8ccfc6`; dark: Days `#2bb5a6`, Weeks `#4fc8bb`, Months `#8fdcd2`, Eventually `#c3ece6`. These teals are now the segment **titles'** only. **Bars** (2026-10-26, Trent: "Have them all just use the purple and green except for the deadlines, which finish the teal color that they currently finish at. That's the special one."): every bar — a period's, every task segment's, on the dashboard strips, the Reminders screen's day bar and section hairlines, and the Quotas page's period bars — fills in the reminders' purple (`--badge-reminders`) over the gray track and turns green when finished. The one exception is the **deadlines page**, which finishes in its own teal (`--deadlines-fill`, `segmentDoneColor`) — its title, hairline and finished "N of N ✓" too. The native apps follow the same rule (2026-10-26): the Reminders widget strip, the watch strip and the Quotas widget's period bars fill in the same purple and finish green, and so do the two native rings (the Quotas widget's 2×2 met ring and the watch Smart Stack's gauge); native draws no deadlines page yet. The Reminders screen's day bar (above the periods) shows the segments after the periods the same way, a tap scrolling to the section; they stay out of its "N waiting so far" and "X of Y considered".

**The row.** Circle on the left = considered (never a completion; a tap anywhere else on the row does the same, as on a reminder). Checkbox on the right = done. "Today" (target today) sits just left of the checkbox. A quiet horizon chip changes the horizon in one tap; it shows its word only when the task's own horizon differs from the segment's (a deadline pulled it in), and a faint dot marks unset. **API.** `GET /api/reminders` returns a top-level `task_segments` array. It is deliberately not inside `groups`: a native build that predates it ignores the key, so its "Complete all" can never reach a real task.   {
    "horizon": "weeks",

## Upcoming

The heads-up segment (2026-10-12; spec rev 3 §2), split into two **sections**, **Tomorrow** and **Later**, on 2026-10-25 (plan `plan-upcoming-split-1024.md`, APPROVED 10-25; PR A the server, PR B the web, PR C native). The rules live with every other date rule in `src/lib/task-segments.ts` (`upcomingDays`, `upcomingState`, `upcomingGap`), each constant named once; `tests/behavioral/up-upcoming.test.ts` has the reference dates, the DST day and a day-by-day golden timeline, `tests/golden/upcoming-sections.ts` the sections' timelines.

**Which tasks.** One-offs with a target the user **picked** (a [relative target](#relative-targets) counts — it is a real target) whose target hasn't arrived, and repeating tasks' next occurrences — `rrule` set, `is_reminder = 0`, not a quota (`isTracked`). Reminders and quotas never appear, and neither does a deadline's **automatic** target (§8.5): its task stays in its horizon segment. A target is never after its deadline (§8.2). **A future deck** (2026-10-20) is one more, its day the anchor ("On deck Sat Oct 24") — only for a client that sends `?deck=1` (see [On deck](#on-deck)). **Rule 3** (2026-10-25, `?deadlines=1` only): a deadline task with no target is never in Upcoming — the [deadlines page](#the-deadlines-page) alone holds it, from its lead day; strictly, a future deck on one gets no Upcoming row either (on the deck day the On deck section holds it).

**The rule** (`upcomingDays(anchorDay, setDay, leadDays) → { later, tomorrow }`). **A** = the anchor's OpenTask day: the picked target (one-off, relative target, a repeat's occurrence), else the future deck day. **Set day** = the OpenTask day of `target_set_at`. **Wait** = A − set day. **Lead** = `lead_days` ?? `deadlineLeadDays(wait)` — the one lead table (under 2 → 0, up to 7 → 1, under 16 → 3, else 4). Then:

1. **Tomorrow = A − 1**, only when the wait is at least 2 (`HEADS_UP_DAY_BEFORE_MIN_WAIT`). Made today for tomorrow: none (otherwise every defer sweep to tomorrow would fill Tomorrow).
2. **Later = max(A − lead, set day + 1)**, only when that day is ≤ A − 2. An override longer than the wait is clamped to the day after the target was set; a lead of 1 has no Later.

**Under the default leads no day moved**: Later is the old early heads-up (3 days before when the wait is 8–15, 4 at 16 or more; none up to 7) and Tomorrow the old day-before one — UP-001..021 pass unchanged on `upcomingDays(…, null)`. OpenTask days throughout (Luxon calendar days in the user's zone, cut at the day start) — UTC days and 24-hour math get DST and late-night waits wrong. At most one row a day.

**Lead time** (`lead_days`, 1–90): days ahead of the anchor — the target, else the deck day, else (a target-less deadline task) the deadline, for the deadlines page as before. One column, two anchors; derived on read, no backfill (`lead_from` keeps its deadline-only meaning). On a repeat it is series-level, applied to each occurrence, and must be shorter than the rule's wait (the smallest gap between occurrences, `leadDaysProblem` — a 400 on create, PATCH and bulk edit, for every repeat since 2026-10-25); the default wait still counts from the set day. A lead change does not restamp `target_set_at`. PATCH, bulk edit and create take it.

**Placement and carry-over.** A Tomorrow row shows only **on A − 1**. A Later row shows from the Later day and **carries over** — the same single row, day after day — until it is **seen** (`last_considered_at` on or after the Later day), at the latest to A − 2: on A − 1 the task is in Tomorrow whatever Later said. Seen is **per section** with no new state: seeing a row in Later does not silence Tomorrow (Tomorrow's day comes after that stamp). Considered today it is listed as `considered` in its section (so "X of Y" and put-back work); Defer all is `segment_deferred_at` as everywhere. On A it leaves Upcoming and is over target (or on deck). Never counted over target, never notified. A move restamps `target_set_at`, so a target moved after its Later day was seen gets a fresh plan (a period retime keeps the days).

**One place a day** (precedence): the queue, the deadlines page, On deck, over target, Upcoming (Tomorrow, then Later), the horizon segments.

**In the API.** One kind, `horizon: "upcoming"` — no new kinds (a shipped native build would list an unknown kind as a page of its own). Every row of it carries `upcoming_section: "tomorrow" | "later"`, and the server sorts Tomorrow's rows first (then the anchor, then id). Native builds ignore the key and draw one Upcoming page with both sections' rows — on the same days as before under the default leads. With `?handled=1` a left row carries the section the day roster remembered (`segment_roster.section`, kept current while the row is listed; NULL — a row remembered before the column — reads as the section computed now). The page's "N of M" counts both sections; each section heading has its own.

**On the web** (PR B, `UpcomingSections`, `src/lib/upcoming-sections.ts`): one Upcoming section on /reminders and one page on the dashboard Tasks card, with two sub-lists under its header — **Tomorrow** then **Later** (`UPCOMING_SECTION_TITLES`) — each with its own "n of m" (green with a check once nothing waits) and its own considered rows ("Show N considered" on /reminders; on the dashboard page the section's count opens them, and the page header's count opens both). Both headings are always drawn; an empty one reads "Nothing today ✓". The page keeps one "N of M", one Considered all and one Defer all (decision 11); the dashboard's row cap is one budget spent on Tomorrow first.

**`target_set_at`** is when the target was last set, by any path: create (every task gets it), any move (PATCH, bulk edit, bulk snooze, snooze-overdue, the snooze endpoint, native quick snoozes), Today and its picker, a completion advance, skip, put-back, AI enrichment, and any change to `deadline_at` (it can move the target: an automatic one follows it, a picked one is pulled back). Every writer goes through `src/core/tasks/target-set.ts`; a guard test fails when a file writes `due_at`/`deadline_at` in SQL without importing it. It is in every undo snapshot, so undo and redo restore it. Seeded once on migration with `created_at` (a repeating task: the later of that and `last_completed_at`); a null reads the same way. On the first day a heads-up day already past shows as carry-over — expected. Distinct from `segment_targeted_at`.

Header "Upcoming" (one word, no hint since 2026-10-20); a strip bar on the dashboard Tasks card and the Reminders day bar, the over-50 nudge and Defer all, like every segment.

## The two badges: attempts and age

Spec §7 (2026-10-12; rulings Q5–Q7, Q10 — Trent: separate signals). The rules are in the one rules module, `src/lib/task-segments.ts` (§ the two badges); `tests/behavioral/bg-badges.test.ts` has them as tests, and the golden suite (below) has them day by day.

### Attempts

**An attempt is a local day (the owner's zone) on which the task was over target.** The day counts **the moment** the task goes over target — the badge reads "1×" at once (ruling Q5), including a deadline's automatic target that is already past when it is set (Q10). One per local day: moving it again the same day adds nothing. Days before the target never count, so moving a target that has not arrived adds nothing.

- **Who counts:** any ordinary open task that can go over target — its own target, a repeating occurrence, a deadline's automatic target. Never a reminder or a quota (`canAttempt`).
- **Resets** only on done (one-off) and on each new occurrence of a repeating task (done or skip): attempts 0, checkpoint cleared. The completion row keeps the count (`completions.attempts`), so History shows a late occurrence ("· 3×").
- **Removing the target freezes the count** (nothing counts without a target); it resumes if the task is retargeted and goes over target again.
- **The badge shows only while the task has a target** (`attempts_label`, "3×"); the count is kept under it. On the dashboard row a corner tab, one calm plum in three depths (1–2 light, `ATTEMPTS_MEDIUM` 3–6 medium, `ATTEMPTS_STRONG` 7+ strong; red is kept for a passed deadline); on a segment or Upcoming row a chip at the end of the second line.
- **At 3× (`ATTEMPTS_OFFER_REMOVE`) the row offers to drop the target** — offered, never automatic: a small "Remove target?" on a one-off with a target the user picked, deadline or not (2026-10-22: "Back to auto?" is gone, and `attempts_offer` never sends `auto`). Nothing on an automatic target (Q9), on a repeating task (its target goes only with its recurrence), or once the deadline has passed ("auto" would be the passed deadline). `attemptsOffer`; the API sends it as `attempts_offer`. Process lists the same tasks in its old-targets step (over target now, 3×+).

**Storage and the read.** `tasks.attempts` is the count as of a checkpoint, `tasks.attempts_counted_through` (a local date, yyyy-MM-dd). Between two writes the target is constant, and a task over target stays over target, so the days since the checkpoint are exactly the local days from the latest of (the day after the checkpoint, the target's day, the day the target was set — `target_set_at` —, the creation day) through today if the target has arrived, else through yesterday (`effectiveAttempts`). Every read adds them: the server in `rowToTask` (the owner's zone, from a subquery in `taskColumns`), the web row at render — so "1×" appears the moment the target passes, without a refetch.

**Advancing it** — three places, one rule:

1. **On read**, as above (no write).
2. **The checkpoint on every target move.** A write that moves `due_at` or `deadline_at` first persists the count as of now, read from the row _before_ the move (`stampTargetSet`, `src/core/tasks/target-set.ts` — the module every target writer already goes through). Without it, a task that went over target at 9:00 and was moved at 9:00:30 would lose the day.
3. **The minute cron** (`persistAttempts`, `src/core/tasks/attempts.ts`, started in `src/instrumentation.ts`) writes the stored columns current for every task whose target has arrived, for anything that reads them raw. No undo entry, no `updated_at` bump, no sync event.

**Undo.** The checkpoint and the cron record the past, so they are not undo entries: undo of a move restores the old target and leaves the count, which is still true. Done and skip change the count, so their snapshots carry `attempts` and `attempts_counted_through`: undo restores the count, redo resets it again. Put-back (`markUndone`) restores the count from the completion row it deletes, checkpointed at the later of the completion day (or the day before, if the target had not arrived by then) and yesterday — so the days it sat done don't count, and today counts at most once.

**Migration.** New columns, `attempts = 0` and no checkpoint. The read then counts the over-target days of each task's _current_ target, from its day (never before the task existed or the target was set) — the part of the history that is recoverable. The days earlier targets were missed are not known.

### Age

Only a task with **neither a target nor a deadline** (truly undated), counted from `created_at`, shown only past one threshold per horizon — unset reads as weeks (`AGE_THRESHOLDS`, `AGE_LABELS`, `ageLabel`):

| Horizon         | Shown past | Label   |
| --------------- | ---------- | ------- |
| `days`          | 7 days     | `>1 wk` |
| `weeks` / unset | 1 month    | `>1 mo` |
| `months`        | 1 quarter  | `>3 mo` |
| `eventually`    | 6 months   | `>6 mo` |

Calendar arithmetic (a month is a calendar month) in the **user's timezone**, strictly past — the server's `age_label` and the web row compute it the same way (`ageLabel(task, now, timezone)`), so a task made late on the evening of Oct 30 turns `>1 mo` at that local evening on Nov 30, not at the UTC instant a few hours earlier. The API sends it as `age_label`; the dashboard row shows it where every row used to show "Xd old", and segment rows end their second line with it.

**The same thresholds are Process's growth asks** (ruling Q7; they replaced 14/60/180 days): a days task is asked "weeks?" past 7 days on its horizon, weeks or unset "months?" past a month, months "eventually?" past a quarter — counted from the latest of `horizon_set_at` (else `created_at`) and `growth_kept_at`. Choosing **keep** (`affirm_horizon`) stamps `growth_kept_at`, so Process asks again only one threshold period after it; the horizon's own clock is untouched and the badge still shows creation age. Growth asks about a deadline-only task too (when its deadline is far enough not to steer the horizon); the badge is for undated tasks only.

## Priority and bulk snooze

Priority is **what missing the task costs**. It no longer says whether a date is a deadline: the deadline is its own field (see [Deadline](#deadline)), and a low-priority meal voucher that expires on the 11th still expires on the 11th. Priority sets the nag cadence (`docs/NOTIFICATIONS.md` § Repeat intervals), the notification's interruption level, and how a bulk snooze treats an over-target task:

| Priority        | Bulk snooze                     | Over-target significance |
| --------------- | ------------------------------- | ------------------------ |
| 0-1 (Unset/Low) | Eligible                        | Normal — not a problem   |
| 2 (Medium)      | Eligible                        | Low                      |
| 3 (High)        | Only when nothing lower is left | Significant              |
| 4 (Urgent)      | Never                           | Critical                 |

`HIGH_PRIORITY_THRESHOLD = 3` and `URGENT_PRIORITY = 4` in `src/lib/priority.ts` are the boundaries. Urgent tasks also break through everything (critical-level notifications) and must be snoozed individually, so every change to one is a deliberate decision. On top of the priority rules, a sweep's move stops at a deadline still ahead (see [Deadline](#deadline)), and a **passed deadline counts as High**.

**Bulk snooze:** P0-P2 are always swept. **P3 (High) is swept only when no lower-priority task in the same batch is still eligible** — so the first press clears P0-P2 and a second press, finding only High left, takes it. Two presses, no mode, no second button. P4 (Urgent) is never swept: every change to an Urgent task's target has to be a deliberate, individual act.

**A passed deadline joins the High tier** (Trent's ruling, 2026-10-12; `bulkSnoozeTier` in `src/core/tasks/bulk.ts`): a P0-P2 task whose deadline has passed waits while anything lower is still eligible, and goes with the High tier after; alone, it moves. A P3 with a passed deadline is still just P3; a P4 is never swept, deadline or not. This holds for every sweep — snooze-all and snooze-overdue, `bulk/snooze`, a bulk date edit, the notification buttons — and `include_task_ids` rescues it like any High task. The response counts the ones held back only by the deadline in `skipped_deadline` (not in `skipped_urgent`), and the toast names them beside High: "Snoozed 3 tasks (2 high, 1 past deadline skipped)", "No snoozable tasks (1 past deadline, 1 urgent skipped)"; the sweep's feedback push says "1 past deadline still over target. Snooze again to move it".

The test is "is anything lower still eligible", **not** "is the batch pure": a P4 sitting in the batch does not hold the High tier back, because a P4 is never swept and would otherwise block it forever. `include_task_ids` still rescues an explicitly chosen task at any priority. The rule lives in `filterForBulkSnooze` (`src/core/tasks/bulk.ts`).

Why the change (Trent, 2026-09-15): with four overdue High tasks and nothing else late, the sweep button reported "no snoozable tasks" and the list stayed wrong. Excluding High outright protects a High task from a sweep the user did not read; a sweep aimed at a batch that is already nothing but High tasks is the user looking straight at them and pressing anyway. (Written when P3/P4 dates stood in for deadlines. A real deadline is now protected by the deadline cap at any priority.)

**Implications for code and AI:**

- A task's real cutoff is `deadline_at`, never its target. Don't read a target as a deadline at any priority, and don't infer a deadline from priority.
- `created_at` is the most reliable age signal — it never changes. Use it over `due_at` for understanding how long a task has existed.
- `original_due_at` is the first-target date: the gap to `due_at` is how far moves have carried the target since it was set, but not how many moves occurred or why. Don't infer snooze counts or user intent from dates alone. (There is no snooze count since 2026-10-12.)
- A target marked `target_auto` (printed "(from deadline)" in the AI's task lines) was not picked by the user: it is the deadline's automatic lead-in.
- For P0-2 tasks, avoid language like "deferred three times" (implies conscious decisions). Prefer factual framing: "has been on your list for 3 weeks." These tasks ride the bulk sweep, so a shifted target reflects a sweep the user never read, not a decision.
- An unset `horizon` is unset, not "weeks": never report it as stated.

## The OpenTask day, picks and defers

The task queue (2026-10-19; design in Trent's `task-queue-design.md`, "Picks and defers" and the red-team resolutions). It sits behind the server switch **`OPENTASK_TASK_QUEUE=1`** (`taskQueueEnabled()` in `src/core/tasks/task-queue.ts`, read at call time): a deploy and rollback switch for the whole server, not a per-user setting. Off, everything below is inert and every endpoint behaves as described in the rest of this file.

Task-queue PR 1 built the day, the classification and the mark; **PR 2 the rollover** (below), attempts per OpenTask day and the undo fence. The queue panels are PR 3: until they land, a stripped one-off is simply untargeted (it shows in its horizon segment like any untargeted task), and a waiting repeating task is quiet until its next occurrence.

### The OpenTask day

The OpenTask day runs from **rollover to rollover** (the user's day start), not midnight to midnight (`src/lib/opentask-day.ts`, pure — the one place a day boundary is computed; the TQ-G01 guard, `tests/behavioral/tq-day-guard.test.ts`, fails on any day worked out another way, and its allowlist lists what PR 2 still moves):

- **The rollover** is the user's **"Day starts at"** (2026-10-23; Settings → Your day; `users.day_start_time` / `day_start_slot_id`, resolved by `resolveDayStart` in `src/lib/anchor-times.ts`, read by `rolloverTimeForUser`). Unset — the default — it is a fixed **3:00 AM** for every user (`DEFAULT_DAY_START`, Trent 2026-10-24): never the first period or the Morning time, and nothing is written for existing users (they read it). It can also be a custom time at any hour (11 PM, 1 AM, midnight) or linked to a period like Morning (it follows the period's start; removing the period keeps the time as custom, with undo). `GET /api/user/preferences` reports it as `rollover_time` and `day_start_time` / `day_start_slot_id` / `day_start_default`; PATCH takes `day_start_time` (custom), `day_start_slot_id` (link) or `day_start_time: null` (back to the default).
- **Both directions — the naming convention** (Trent, 2026-10-24). A day start **at or before 12:00** names the day by the date it **begins** on: with 3:00 AM, Monday runs Mon 03:00 → Tue 03:00, and Tuesday 01:00 is still Monday. A day start **after 12:00** names it by the **next** date, the one it mostly covers: with 11:00 PM, Monday runs Sun 23:00 → Mon 23:00, and Sunday 23:30 is already Monday. Midnight is the calendar day. For every day start, `openTaskDayOf(x) = D` ⇔ `dayStartMoment(D) ≤ x < dayStartMoment(D + 1)`; nothing derives an OpenTask date from a moment's calendar date (after noon, a day starts on the date before its name).
- `dayStartMoment(openTaskDate, tz, time)`: the instant the OpenTask day `openTaskDate` starts — the time on that date (≤ 12:00) or on the date before (> 12:00). On a spring-forward night that swallows the time (a 02:30 start), it is the **next valid minute** (03:00); on a fall-back night, the first of the repeated times (`localMoment`). `openTaskDaySpan(now)` is `[dayStartMoment(D), dayStartMoment(D + 1))`; `dayStartOnDate(calendarDate)` is the one the cron fires on a calendar date (the day simulator walks those).
- `openTaskDayOf(instant)`: with 06:30, 00:00–06:29 belongs to the previous date and 06:30 exactly starts the new one; with 23:00, 23:00 exactly is already the next date. A night owl's 2 AM target belongs to the evening's day — the **late night** (`isLateNight`: after midnight, still the day before), which only a day start after midnight and at or before 12:00 has. **But an early-morning pick is spared at its first rollover** (designer ruling, 2026-10-19): an unmarked one-off whose target falls between local midnight and the rollover on the rollover's calendar day, and was set on an earlier calendar day than its target's (at 22:00, "tomorrow 6:00"), is a pick for the coming day — the 6:30 rollover keeps it, it stays over target and nags, and the next rollover strips it if it is still there. A pick made after midnight for before the rollover (the night owl at 1 AM picking 2 AM) stays with the evening's day and is stripped; a marked task (a defer) is always stripped. The same rule decides its attempts' day (`isEarlyMorningPick` / `targetOpenTaskDay` in `src/lib/opentask-day.ts`, shared by the rollover and `effectiveAttempts`): such a target belongs to its calendar day, so a missed 6:00 pick counts one attempt for that morning (at once, from 6:00), not one for the evening and another for the day. With a day start after 12:00 there is no late night, so no target is an early-morning pick (and A4's "tomorrow" before the rollover never applies: before midnight it is already the next day).
- `nextRollover(now)`: the first rollover strictly after now — the end of now's span (at exactly 6:30:00, tomorrow's); `latestRollover(now)` its start. With an 11 PM start, a defer or Try Tomorrow at 22:00 lands at 23:00 the same evening (the next day starts then), and a deck for the day ends at its 23:00.

**One day boundary (Trent, 2026-10-23).** With the switch on, the OpenTask day governs everything keyed to "today": the defer rule below, the rollover, attempts, decks' day ends, the deadlines page (seen, the safety net, defer bounds), the deadline nag, the queue panels' day roster — and the Reminders screen: its roster and "considered today" (a check-off at 00:30 with the day starting at 03:00 is the day before's), quota prompts and their `prompt_key` dates (a key from before the day turned is refused at that same instant), a daily quota's count (its period ends at the day start — a day's identity is its date, so a midnight anchor runs to the next day start, once, and is aligned from then on), and the slot nag (the evening's unfinished slots keep nagging until the day starts — with the 3:00 AM default, silently until 3 AM, as ruled; a period opens at the one moment of its wall-clock time inside the day, `periodOpensAt`: with 3:00 AM a 1:00 AM period ends the day, with 11:00 PM a 23:30 period begins it). The day turning sends **one sync event per user per day** (widgets included) from the rollover job even when it changes nothing, so open tabs and the Reminders widget refetch the new day's roster and prompt keys instead of acting on yesterday's (a stale key is a 400). Their one read is `dayBoundaryForUser` (`src/core/tasks/rollover-time.ts`): the day start with the switch on, midnight (`CALENDAR_DAY_START`) with it off, so a server without the queue is unchanged. **Everything uses the OpenTask date ("Day starts at" PR 2, Trent 2026-10-24).** One pure function maps an instant to its OpenTask date (`openTaskDayOf`; `openTaskLocalDay` for calendar maths on it; `openTaskDayBoundaries` for the instants yesterday/today/tomorrow start), and every surface downstream is plain calendar maths on that date: the Now view's "today" (`targetIsToday`), the Today pill and `GET /api/tasks/counts`' `today`, the "Today" / "Tomorrow" / "Yesterday" labels and the due-date filter chips, Upcoming's heads-up days, the horizon segments, "considered today" and `check_in_day` (an OpenTask date's weekday: with 3:00 AM, Saturday's segments are still Saturday's at 01:30 Sunday), the day roster (one day key for every panel), the overdue fallback (a repeat with no target is due from its occurrence in the OpenTask day, `effectiveDueAt`), decks (below), Defer's "tomorrow" and "next period still today", the dashboard clock (it wakes at the day start), daily stats and History's day. **Quota periods**: the week, month or year an instant is in is the one its OpenTask date is in, and the period runs from `dayStartMoment` of its first date to that of the next period's (with 3:00 AM a Sunday week runs Sunday 03:00 → Sunday 03:00; with 11:00 PM the week named by its Sunday starts Saturday 23:00); a period's **identity is its first DATE** and every step is calendar maths on dates; a stored anchor stands for the date its own wall-clock time names (`anchorDate`: at or before 12:00 its local date, after 12:00 the next — an anchor stamped at 23:00 by an 11 PM start begins the next date's period), so **changing the day start, in either direction — the switch going on or off, 03:00 → 23:00, a link to a 00:00 period — moves only the bounds, never the phase**: the period in progress ends at the new day start of its next first date (a few hours longer or shorter, once; a midnight anchor on deploy runs to the next 03:00, no short period), a fortnight stays a fortnight on its Sundays, a quarter that began Oct 1 ends at Jan 1's day start. Midnight is just another day start, through the same path. Only a **misaligned date** — not its unit's first date (a week anchored under the old Monday-only rule, a week-start change) — ends early at the next unit's start: a **transition** period, its record marked `progress_periods.transition`; unmet, it is neither met nor missed and breaks no streak (`getQuotaStats`); taps after its end carry into the next period (`quotaPeriodEnd`, `anchorOnPeriodStart`, `unitStartAt` in `src/lib/week-start.ts`; the property tests `tests/behavioral/tq-quota-phase.test.ts`; the served `progress_period_end` / `period_last_day`; the Quotas page's "% of the week gone" and "N days left"). Target and deadline timestamps never move — only which day's list they are on. The server reads the day start through `dayBoundaryForUser`, the browser through `useDayStart` (the same rule, `browserDayStart` in `src/lib/browser-day-start.ts`; the guard's TQ-G03 keeps midnight out of every other client file and out of every default). Before the preferences load the browser uses the day start it last saw (remembered in localStorage, like the queue switch); with nothing remembered it draws with midnight and the defers that commit a day — "tomorrow", "next period" — wait for the load (`useDayStartKnown`). With the switch off all of it is midnight, exactly as before. Known gaps: the early-morning pick (above) is a rollover and attempts rule only — a 6:00 pick made at 22:00 with a 6:30 start reads as "today" in the labels and the Today pill that evening; the enrichment rules read the user's words on the calendar (A4 still maps a late-night "tomorrow" to the coming day). **The native apps** ("Day starts at" PR 3) run on the same day through one Swift mirror of the helpers (`OpenTaskDay`, `ios/Shared/OpenTaskDay.swift`, checked against the TS by a shared table of cases, `tests/fixtures/opentask-day/`), reading the boundary they last fetched from `GET /api/user/preferences` (`DayStartStore`: `rollover_time` with `task_queue`, else midnight) — ios/AGENTS.md § The OpenTask day.

**The late night, at every entry point ("OpenTask day everywhere" part 2, Trent 2026-10-26).** The test for each: at 00:30 Monday with a 3:00 AM start it behaves exactly as at 23:30 Sunday. So "today" is the OpenTask day for a NEW RULE's day too: every-time's weekday default for a weekly rule with no day (`EveryTimeContext.dayStart`, from `useDayStart`), enrichment's pin of a repeat with no day named (`pinUnnamedDay`: "every 2 weeks" at 00:30 Monday is every other Sunday; the prompt then says the user's day, `userDayLine`, only when it is not the calendar date) and its "this weekend", and a floating rule's first occurrence (`computeFirstOccurrence`: day 0 is the OpenTask day, and its occurrence is the one instant at the rule's time inside it, `periodOpensAt` — with an 11 PM start, at Sun 23:26 an every-3-days 23:45 rule's first is Sun 23:45, Monday's; with 3:00 AM, at Mon 00:30 a 1:00 AM rule's is Mon 01:00, Sunday's; the long first gap, when that time has passed, is what Sunday night always gave). The floors: skip until's earliest date is the next OpenTask day and a date starts at its day start (`skipUntilFirstDay`, `parseUntil`, `planSkipUntil` with `dayStartMoment`); repeat until's earliest is today's OpenTask date (`repeatEndProblem`); "Morning of the deadline" is the morning of the deadline's own date — in its night (below), its OpenTask day's — near / far on OpenTask days (`deadlineDayPick`); the deck picker's today ring. **L9's night rule for every day word** (`src/lib/night-day.ts`, the deadline chip's rule): a time between midnight and the day start names its OpenTask day and says "night" — "Tonight, Oct 25, 1:00 AM" (a Mon Oct 26 01:00 seen Sunday) in the quick panel's header — a label's weekday and date always name the same day, so with the night cue the date is the evening's too (2026-10-27: "Mon night, Oct 26, 1:00 AM", never "Mon night, Oct 27"), "Tomorrow night 1:00 AM" / "Thu night 1:00 AM" on a row and in the defer words, "Thu night 1:00 AM" in a quota's "Last:", "since Thu night", History's entries. **A label with a clock time names the calendar day** (Trent, 2026-10-26): a day start after 12:00 has no night, and there a timed label shows the moment's own weekday and date with no cue — with an 11 PM start a Tue Oct 27 23:47 target is on Wednesday's list but reads "Tue, Oct 27, 11:47 PM" / "Tue 11:47 PM", never "Wed, Oct 27"; "Today" / "Tomorrow" / "Yesterday" are said only where the OpenTask day and the moment's own date agree (`wordsAgree`), else the weekday: at Sat 12:30 a Sat 23:30 target is "Sat 11:30 PM", a Sat 23:47 log "Sat 11:47 PM" whenever it is read. A label of a whole day with no time (the deadline chip, the bulk header's shared day) names the OpenTask day. A date alone (archive's "Completed", trash's "Deleted", a quota's "Created", History's older entries) is the OpenTask date (`openTaskDateLabel`). Left on the calendar on purpose: the year on a repeat's "until" at New Year, the AI context's rolling 24 hours, a rule's or occurrence's own date, and the user's words (A4). Pinned by TQ-LN (`tests/behavioral/tq-late-night.test.ts`, with the fall-back night) and guarded by TQ-G01 v2 (weekday and date-part operations), TQ-G03b v2 (no day-start default anywhere) and TQ-G04 (a type with `now` and `timezone` carries the day start) in `tests/behavioral/tq-day-guard.test.ts`.

### Picks and defers

Every target change is classed by what the gesture means, not by how many tasks it touches:

- **Pick** ("this, at this time"): the editor and the time pickers, the single snooze, Today, enrichment from the user's words, a single notification's snooze buttons, and **every multi-select edit** (`bulk/snooze` or `bulk/edit` with `include_task_ids` and no `source`). A pick is never marked.
- **Defer** ("not now"): **Snooze-all in every form** — the web clock and FAB (`useSnoozeOverdue` sends `source: 'sweep'` to `bulk/snooze`), and `bulk/snooze-overdue` (always a sweep: every native "All" button, widget bar and Shortcut) — and **Try Tomorrow** (`source: 'try_tomorrow'`, API only for now).
- **Defer a selection** (web, 2026-10-26). With tasks selected on the dashboard, the clock and the Defer FAB stay (the FAB shows the selected count, "Defer N selected") and act on the selection instead of every overdue task — a tap to the same default Defer all uses, the hold menu to its choices; the selection bar has no Defer of its own. **A defer only ever moves a target later**: the press resolves its one absolute time first (`until` from the menu, else the next period or the default option), and only the selected tasks whose target is before it are sent; one already at or after it, or with no target, is left alone and counted in the toast — "Deferred 2 tasks · 1 already later · 1 has no target" (`splitSelectionDefer`, `src/lib/defer-selection.ts`). Nothing qualifying sends no request ("Nothing to defer: 1 already later") and keeps the selection. What is sent is one `bulk/snooze` with `source: 'sweep'` **and** `include_task_ids` — a defer, so the table below applies, with no priority held back (High and Urgent move; no one-High rule); the deadline cap still applies and is reported as usual. One request, one undo entry; the selection clears once it went through. Reminders and quotas never reach it (the selection is resolved against the task rows). The "later" test reads the request's time, not the landing below: with the switch on, a below-High deadline-free task landing at or after the next rollover is parked AT the rollover, which can be before the defer time (at 22:00, "next period" tomorrow 8:00, the rollover 3:00), so a selected task targeted between the two goes into the queue at 3:00 — the queue taking it, not a pick moving it earlier.

The class comes from the gesture (`source` on `bulkSnooze`), so no target provenance is stored. For a defer, `bulkSnooze` takes each task's own landing time L (the absolute `until`, or its target plus the delta) and decides (`planLanding` in `src/core/tasks/bulk.ts`):

| Task (tier is `bulkSnoozeTier`: a passed deadline counts as High) | L before the next rollover                                               | L at or after the next rollover                    |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------- |
| Below High, no deadline (one-off or repeating)                    | moves to L                                                               | **target = the rollover moment, `queue_mark` set** |
| Below High, repeating, not marked (e.g. with a deadline)          | moves to L, but never past its next occurrence (`capped_occurrence`, B2) | the same                                           |
| A deadline task                                                   | moves to L, capped at the deadline                                       | the same                                           |
| High or Urgent (one per press, see below)                         | moves to L                                                               | moves to L                                         |

So Trent's evening sweep to "tomorrow" (morning_time 8:30) lands every ordinary task at **6:30**, marked; a 6:00 "+1h" sweep lands at 6:30 and is marked too (resolution 12). Picks are never capped at the next occurrence: a manual move may pass it (B2).

**Try Tomorrow** is one task's Snooze-all to the next rollover (no `until` needed): the target moves to the rollover, `queue_mark` is set, and `try_tomorrow` too, so tomorrow's queue row can be told apart. On a High or Urgent task (never stripped), or a deadline task, it is a plain move to the rollover with no mark.

### The queue mark

`tasks.queue_mark` (and `try_tomorrow`) mean "the rollover takes this into the queue". **Any other target change clears them** — a pick, the editor, Today, enrichment, an automatic target (a deadline added, "Back to auto"), done or skip of a repeating task, put-back — along with `queued_at` (a queued task that gets a target leaves the queue). Done of a one-off clears the mark and flag too. `queued_from_due_at`, the remembered original target, is kept. **The defer that newly sets the mark writes it** — the task's pre-sweep target, in the same write and undo snapshot (spec rule 2, "the original target is remembered"); a second defer of a marked task, or Try Tomorrow on a queued task with no target, keeps the value already there. One place does it: `stampTargetSet` (`src/core/tasks/target-set.ts`), which already runs on every `due_at` / `deadline_at` write through `collectFieldChanges` and enrichment; the defer that sets the mark writes the mark and flag in the same write so the stamp leaves those two — but it still clears `queued_at` (Try Tomorrow on a queued task takes it out of the queue), and a plain sweep's mark clears an earlier Try Tomorrow flag. The fixed-SQL writers (completion advance, skip, put-back) clear it in their own statements (`QUEUE_CLEAR_SQL`); `tests/behavioral/tq-summary.test.ts` guards that. Only fields actually set go into the undo snapshot, so undo of a marking sweep restores the target and clears the mark, and undo of a pick that cleared a mark puts it back.

`queued_at` / `queued_from_due_at` are written by the rollover (below).

### One High per press, and the summary

With the switch on, once nothing lower is left a defer (a Snooze-all press) moves **one** task of the High tier (passed-deadline tasks included) — the oldest target first, then the nearest deadline, then the lowest id — and names it (`snoozed_high_name`). The rest stay skipped and counted as before (`skipped_urgent` / `skipped_high` / `skipped_deadline` keep their meanings). Urgent is still never swept, and `include_task_ids` still rescues. A pick — `bulk/snooze` without `source`, and bulk edit — keeps the whole-tier rule.

Both bulk snooze routes return `queued`, `queued_name` (title when exactly one), `queued_until` (the rollover the marked tasks were targeted at; word them from it, never from `until`), `capped_occurrence`, `snoozed_high_name` and `summary` — one line built by `bulkSnoozeMessage` (`src/lib/snooze.ts`) and shared by the web toast, snooze-overdue's `message` (always equal to it) and, later, the native apps: "3 will move to the Tasks queue at 6:30 AM · Snoozed 2 tasks (1 urgent skipped)". A press that moves exactly one task names it; the one High moved is named. The sweep-feedback push stays counts only (no titles on the lock screen): its title is the same builder's line with every name suppressed (`bulkSnoozeCountSummary`). The undo / History entry says what happened: "Sent 3 tasks to the queue at 6:30 AM", or "Snoozed 5 tasks (3 to the queue at 6:30 AM)" for a mixed press. Switch off, `summary` is the line the toast always showed and the new counts are zero.

### The rollover

`src/core/tasks/task-rollover.ts` (task-queue PR 2). Once per OpenTask day, at the user's rollover moment M, it hands the over-target backlog to the task queue. It runs at the head of both minute jobs in `src/instrumentation.ts` (the notification check and the attempts persist), so it always runs before either at the same minute — a task a sweep marked has its target exactly at M, and must be stripped before a 6:30 notification or a new day's attempt.

**Who.** Below High (`QUEUE_KEEP_PRIORITY` 3), no deadline (passed or ahead — resolution 3), not done, deleted or archived, not a reminder or a quota (`is_tracked`, `progress_target > 1`), with a target that is **marked** (`queue_mark`) **or before M** — and was not set after M, and is not an early-morning pick spared at its first rollover (see [The OpenTask day](#the-opentask-day)).

A **from_completion** rule is stepped from its existing occurrence by its interval (as if each had been done on time), never from now: a system move never re-anchors the schedule. If the steps cannot reach M within a generous guard (5000), the task is left untouched and a warning logged. Archived tasks are never touched (waits, flags and the restore script included).

**Exactly once.** `users.last_rollover_date` is the OpenTask day (yyyy-MM-dd) whose rollover last ran. A run happens iff it is before the current OpenTask day, and its first write is the stamp, by a conditional UPDATE in the run's transaction, so two callers can never both run it. Dates are compared, not moments: a timezone change mid-day can't run it twice. By design that cuts both ways: a **westward** change (Chicago → Los Angeles after the Chicago rollover) can **skip one rollover** — the new zone's day is already stamped when its own rollover comes, and the next run is the following morning. **As of M**: a run after downtime happens once (never one run per missed day), as of the latest rollover moment, and ignores any task whose target was set after M (a 6:45 sweep caught up at 7:10 stays). The attempts checkpoint is taken as of just before M, so a task stripped at M gains no attempt for the new day.

**The stamp at deploy.** `runMigrations` stamps every user whose `last_rollover_date` is NULL with their current OpenTask day (`stampRolloverDates`), switch on or off — so nothing strips at deploy, and the first strip is the next real rollover. The job also reads a NULL (a user created later) as "stamp only", never "never ran". With the switch **off**, the job still advances the stamp every day and does nothing else, so turning the switch on later never catches up old days.

**A system action.** No undo entry (like the quota period rollover); one activity row per changed task with `source: 'rollover'` and `metadata.rollover` (`stripped`, `rolled`, `waiting`, `released`, `try_tomorrow_cleared`); `updated_at` set. After commit, per user: `dismissNotificationsForTasks` for the tasks whose target changed (it also resyncs the badge — a run that only released waits or cleared flags calls `syncBadgeCount` itself) and `emitSyncEvent`, then webhooks as every core mutation sends them: `task.updated` with `previous_due_at` for each strip, roll, wait and release, plus `task.skipped` where a missed occurrence was passed over (a Try Tomorrow flag cleared alone sends none). It writes targets with fixed SQL and SETS the queue state, so it is the one exception to the queue-clearing guard (TQ-G01).

**The undo fence (B5).** Every task the rollover changes gets `tasks.rolled_over_at`. Undo and redo skip the snapshot of a task whose `rolled_over_at` is after the entry's `created_at` (`rolledOverSince`, `src/core/undo/rollover-fence.ts`), the way `periodMoved` skips a closed quota period: the rest of the entry still applies and the entry is marked undone (or redone) as usual. So undoing last night's sweep at 6:31 restores only the tasks the rollover left alone; the Today tap is the way back for a stripped one. `logAction` writes `undo_log.created_at` from the app's clock (ISO with milliseconds) so the two compare exactly; both are compared as instants.

**Attempts per OpenTask day (B7).** With the switch on, an attempt is an **OpenTask day**, not a calendar day: every "day" in `effectiveAttempts` goes through `openTaskDayOf`, and `attempts_counted_through` names an OpenTask day (same format). The owner's rollover time comes from a `taskColumns` subquery (`owner_rollover_time`: the "Day starts at" rule in SQL — a live link's period start, the stored time, else the earliest `time_slots.start_time`, else `morning_time`). A miss at 00:00–06:29 is the previous day's attempt; a strip never resets the count; a Today tap from the queue that goes over target is a new attempt. A put-back (`markUndone`) checkpoints on the same OpenTask day (`putBackCountedThrough` with the owner's rollover time), so a put-back between midnight and the rollover loses no attempt. The web row's own live read (TaskRow, between refetches) still counts calendar days — it cannot read the server switch — so between midnight and the rollover it can show one more than the server until the next fetch. Since "Day starts at" PR 2 everything else moved to the OpenTask day too (§ The OpenTask day).

**The 3× offer (resolution 1).** With the switch on, "Remove target?" is retired on a task the rollover would strip (`queueStrippable`: one-off, below High, no deadline) — the queue does its job. High and deadline tasks keep their offers. The server's `attempts_offer` says so. Since PR 3 the browser knows the switch (`task_queue` in `GET /api/user/preferences`, `useTaskQueue`): the web row reads the offer live with it (`attemptsOffer(…, { queue })`), so with the switch off it behaves exactly as before. The same response's `rollover_time` makes the row's live attempts count OpenTask days, as the server does (`effectiveAttempts`' rollover time, the early-morning-pick rule included) — before PR 3 the browser counted calendar days and could show one attempt more than the server between midnight and the rollover.

**Roll over now (2026-10-20).** It also strips decks whose day is up to and including the current OpenTask day, and leaves the coming day's (A3: a deck for Tomorrow made after midnight stays); `deck_stripped` in the answer. `runRolloverNow` (`src/core/tasks/rollover-now.ts`; `POST /api/rollover/run-now`, `?dry_run=1` for counts and ids only; Settings → Advanced → "Roll over now", a closed fold shown only with the switch on) runs the same rules (`applyRollover`) for the caller with M = now and the day window [now, next real rollover): passed targets are stripped, repeating tasks roll or wait, waits due before the next rollover are released. It differs from the cron in four ways: a strip or a wait stamps `queued_at` = the **next** real rollover moment, not now ("end my day now" hands the rows to the coming OpenTask day: they show in "Today's pulls" at once, since `queueKind` asks `queued_at >= latestRollover`, and stay there through the next rollover, which neither counts them before M nor clears Try Tomorrow; `rolled_over_at` stays now), no early-morning-pick spare (a boundary rule), no Try Tomorrow flag clearing (rows stripped this morning are still in "Today's pulls"), and `last_rollover_date` is not touched (tomorrow's rollover runs as usual). It is a user action, so it writes **one undo entry** (`task_rollover`) with each changed task's snapshot; activity rows carry `metadata.manual: true`, webhook payloads `manual: true`. It stamps `rolled_over_at` like the cron, so older entries are fenced for those tasks; its own entry's `created_at` is written after the writes, so the fence never blocks undoing it. 409 with the switch off.

**Tools.** `POST /api/test/rollover { user_id?, now?, force? }` (test mode only) runs the job (`force`, with `user_id`, first sets the user's `last_rollover_date` to the day before, in the same step, so the run happens whatever the minute cron stamped); the day simulator's `rollover` option runs it at each day's moment (`late` moves a day's run, for a missed run); `scripts/simulate-days.ts --rollover` is the go-live dry run (it turns the switch on, on the copy). `scripts/restore-stripped-targets.ts <db> --user <id> [--apply]` (dry run by default; `src/core/tasks/restore-stripped.ts`) puts `queued_from_due_at` back on every one-off still queued with no target — the rollback, never run on production without Trent.

### The task queue

Task-queue PR 3 (2026-10-19; design rules 6–9, build-plan resolutions 6, 9, 10). Rules in `src/lib/task-segments.ts` (`queueKind`, `queueRowState`, `compareQueueRows`); placement in `getTaskSegments`, the consider in `considerTasks` (`src/core/tasks/task-segments.ts`). **Two panels, first.** The queue is two task segments that come before every other in `SEGMENT_ORDER` (spec rule 6: "the first and foremost thing to handle"), on `/reminders` and in the dashboard's right panel only (resolution 9 — not a Now section). Code words `queue_today` and `queue_previous`; on screen they are titled **Task queue · Today's pulls** (the latest rollover's strips, a manual Roll over now's included) and **Task queue · Previous pulls** (Trent, 2026-10-21; `QUEUE_PANEL_TITLES` in `src/lib/task-model-words.ts`), with no hint line.

**Who.** A task with `queued_at` set whose target has not arrived: a stripped one-off (no target), a repeating task waiting for its next occurrence (its target is that occurrence), or — since 2026-10-20 — a deck whose day ended undone, at any priority (a deadline one keeps its automatic target, so it is here only until that target arrives). Once the target arrives the task is over target, on the dashboard, not in the queue (the rollover releases a wait on its occurrence's day anyway). Putting a queued task on deck takes it out (rule 3). **Precedence (rule 7).** A queued task is in no horizon segment and not in Upcoming: `getTaskSegments` places it before anything else. One panel at most.

**Order.** Priority, highest first; then the OLDER remembered target (`queued_from_due_at`, or for a deck the rollover moment that started `queued_from_deck_day`) first, a row without one last; then id. **State.** The shared stamps (rule 7: one considered state): considered today, deferred today, else waiting. Considered rows sit behind "Show N considered" with their put-back, as in every segment.

**Days.** The panels split on the rollover (an OpenTask day), and a row's considered/deferred state is read on the same OpenTask day (`queueRowState`) — like every segment's since "Day starts at" PR 2: a repeating task considered at 23:00 is still considered at 00:30, in "Today's pulls", until the rollover moves it to "Previous pulls", waiting again.

**Put back is not re-queue.** "Show N considered" → put back on a one-off that left the queue clears the stamps only: the row waits again in its horizon segment. Only Undo of the consider puts it back in the queue.

## On deck

On deck D1 (2026-10-20; design `on-deck-design.md` and its red-team resolutions, APPROVED 10-20). A target does two jobs: it names a **day**, and it starts **nagging** at a time. **On deck is the first job alone**: "I'd like to get to this on that day; if it gets done it gets done." Today says "I'm getting it done today" (a target that nags); On deck says "I'm trying today" (no nag). The rules are pure, in `src/lib/task-segments.ts` (§ On deck: `deckDayProblem`, `deckRefusal`, `deckSkip`, `deckIsToday`, `deckSummary`); the write in `collectFieldChanges` (`prepareDeck`); the endpoint in `src/core/tasks/deck.ts`. It rides on the task queue's server switch (`OPENTASK_TASK_QUEUE`): off, nothing can be put on deck (409), the rollover leaves decks alone and the slot push carries no count. D1 is server only: the web buttons and the dashboard's On deck section are D2, enrichment's day words D3 (below), the native apps after.

**The field.** `tasks.on_deck_day` (API `on_deck_day`) is the owner's **OpenTask** date, yyyy-MM-dd ("Day starts at" PR 2, 2026-10-24 — everything uses the OpenTask date; until then the calendar date, red-team A2). "Today" between midnight and the day start is the day that is ending: a deck for "today" made at 1 AM is that day's, and the rollover queues it — the late night's pick for the coming day is **Tomorrow** (the menu's first item, the segment row's one-tap button). Today's decks (`deckIsToday`, `onDeckToday`) are those with `on_deck_day <= ` today's OpenTask date: a day not yet stripped (a rollover that has not run) still shows until it does. A deck day earlier than today's OpenTask date is a 400 (`deckDayProblem`). Decks made before PR 2 keep their date: a calendar-date deck made after midnight reads one day later than meant, once. `queued_from_deck_day` is the day the rollover remembered (below). `target_set_at` doubles as the deck's set stamp (A6): Upcoming's heads-ups count from it.

**The rules.**

1. **A picked target or a deck, never both.** Decking a task with a picked target drops it, time and all (`due_at` → the deadline's automatic target if it has a deadline, else NULL). A pick clears the deck (below). A deadline's **automatic** target lives beside a deck: the deadline protects regardless.
2. **A deck never nags**: not over target, not in the badge, never swept (it has no target to move).
3. **Decking takes a task out of the queue** (B8): `queue_mark`, `try_tomorrow` and `queued_at` cleared in the same write (`stampTargetSet`'s `deck` option, which also stamps `target_set_at` and checkpoints attempts — only when the day CHANGES: re-decking for the same day keeps the heads-up anchor).
4. **The rollover** sends an undone deck whose day has ended to the queue, at every priority (below).
5. **Quiet like a picked target** (B6, B7): in no horizon segment; a future deck shows in Upcoming on the days a picked target would get — its day is the anchor, its Tomorrow the day before and its Later from `lead_days` (else the default lead), counted from `target_set_at` (the same rule; the row reads "On deck Sat Oct 24", `upcomingGap`) — except on a target-less deadline task, which is never in Upcoming (rule 3, 2026-10-25); no age badge (`ageLabel`); no Process growth ask (`growthAsk`). A missed deck is never an attempt (there is no target to be over).
6. **Not a reminder or a quota.** A **repeating task** can be decked (Trent, 2026-10-20: "It needs to be added." — this reverses the D1 "one-offs only"): see **Repeating tasks on deck** below.

**Repeating tasks on deck (2026-10-20).** Decking a repeating task decks its **current occurrence** for the chosen day: "do this one sometime that day, no nag"; on a queue waiting row it means "try the missed one, quietly". `occurrence_at` stays on the decked occurrence; `due_at` is **NULL** while decked — never a held value (old native builds read over-target from `due_at` alone), and a deck and a picked target still never coexist. So it never nags: `effectiveDueAt` answers null for a target-less deck, and the badge, the notifier, each project's `overdue_count`, `?overdue=true`, the snooze-overdue sweep and the day simulator all leave it out (the candidate SQL in `currently-due.ts` and `overdue-checker.ts` too). High and Urgent repeating tasks can be decked. **Off deck it gets its target back**: taking it off (`day: null`, the toggle, PATCH `null`), or a deadline that outranks the deck (A1), sets `due_at` (and `original_due_at`) back to `occurrence_at`, capped at the deadline, in the same write and undo snapshot (`collectRepeatingUndeck`) — the debt returns and may nag at once (intended); the rollback (`clear-decks`) and the rollover do the same, capped too. **Done** completes that occurrence and advances normally (from the later of the occurrence and now, so a future deck that passed later occurrences absorbs them); **skip** passes over it; both take the deck off, and their undo puts it back. A **put-back** of a decked occurrence brings it back as debt (`due_at = COALESCE(due_at_was, occurrence_at_was)`), never target-less. No edit clears the deck of a decked repeating task by itself, and since PR 4a (2026-10-22) neither does a **schedule change** (a new rule, offsets, mode or anchor; PATCH or bulk edit): the decked occurrence is the user's (`occurrenceIsPersonal`), so no target is computed and the occurrence keeps its day at the new rule's time (a deadline-anchored one's rescheduled deadline keeps the deck too) — unless the deadline the write leaves outranks the deck (A1), when the deck goes and the target comes back from the new schedule; a PATCH (or bulk edit) carrying `rrule` with a deck day is a 400 (`DECK_WITH_RULE_MESSAGE`), and the Quick panel hides its On deck line while a recurrence change is staged. **At the rollover** an undone repeating deck whose day has ended gets its target back on the occurrence (`target_set_at` stamped then, so the deck's days are never attempts) and the repeating rules apply in the same run (`endRepeatingDeck`): below High with no deadline and an occurrence before M, it **rolls** to that day's occurrence with a skip (daily) or **waits** in the queue for its next one, then releases with an auto-skip on its day (`queued_from_deck_day` = the deck day, no `queued_from_due_at`, in the wait's own write and activity row; a deck that rolls or waits also counts as rolled or waiting — Roll over now's ids and summary, the cron's log); High and Urgent, a deadline task (never rolled, `ELIGIBLE_SQL`), or an occurrence still ahead only get the target back. from_completion is stepped from the occurrence, never from now; Roll over now does the same. A future deck shows in Upcoming like a one-off's (`repeatingTasks` reads decked rows; `?deck=1` only). Creating a repeating task on deck is still refused (it has no current occurrence yet). **Enrichment never decks a repeating task** (the rule it writes or the one it has): the day becomes a target as before D3, since a deck beside the rule's date would be a deck plus a picked target; and re-enriching a repeating task that is already on deck leaves every date field alone — the deck, the occurrence, the rule (`applyEnrichment`).

**Deadline tasks (A1).** Since 2026-10-22 (the deadlines page) the rule is the one in [The deadlines page](#the-deadlines-page): any day up to and including the deadline's OpenTask day, while it is ahead. The 10-20 rule it replaced: **Deadline tasks (A1, strict — review 2026-10-20).** A deadline task goes on deck only while its automatic target is still **ahead**, and only on a day **before** that target's local day — the target's own day is refused too, since the deck would meet the nag that morning. Otherwise the deck is refused for that task: `deadline_nagging` (the automatic target has arrived, or the deadline has passed — the D2 toast reads "This deadline is close and already reminding you — use Today.") or `after_auto_target` (that day or later; the picker greys those days). **Decks never nag.** The other way round too: a deadline added or moved on a decked task (PATCH, bulk edit, enrichment) re-runs the check, and when the new automatic target has arrived or falls on or before the deck's day, **the deadline wins** — the deck is cleared in the same write and snapshot, and the description says so ("Taken off deck: the deadline reminds you from Tue"). Belt and braces: `onDeckToday` (and so the push's count) leaves out any row whose target has arrived, and the rollover only clears (does not queue) such a deck. The one window left is a `morning_time` earlier than the rollover, where an automatic target can arrive minutes before the deck day's strip. A **repeating** task has no automatic target (its deadline is per occurrence): it goes on deck only while its deadline is ahead and on a day **before** the deadline's day — its OpenTask day, the local day of `deadline − rollover time`, so a deadline between midnight and the rollover counts as the evening before and can't pass silently while decked (`repeatingDeadlineDay`; `deckRefusal`'s repeating branch, the same two reasons; the web's `deckLimit` greys the same days, "deadline Fri", and words the refusal "That day is after this task's deadline." — `deckErrorMessage`, and a PATCH's 400 the same).

**The pick-only clear (B1, load-bearing).** `stampTargetSet` fires on any `due_at` or `deadline_at` write, automatic targets included, so the deck clear cannot ride on it. Instead a write that leaves the task with a **picked** target (`resolveTarget` → `auto === false` and a `due_at`), or makes it a reminder or a quota, clears `on_deck_day` in the same write and undo snapshot (`collectDeckClear`, `src/core/tasks/deck-clear.ts`) — judged on the resulting row. A schedule change on a decked repeating task computes no target (PR 4a, above), so it keeps the deck. A deadline added or changed, or Back to auto, leaves an automatic target: the deck stays — unless that target reminds on or before the deck day (above). The writers: `collectFieldChanges` (PATCH, bulk edit, every bulk snooze, snooze-overdue, the snooze endpoint, Today, period moves) and enrichment's `collectEnrichmentTarget`; the fixed-SQL writers (completion advance, skip, occurrence put-back, the stripped-target restore) write `DECK_CLEAR_SQL` in their own statements. The guards OD-G01–G03 (`tests/behavioral/od-deck.test.ts`) fail when a file that writes `due_at` neither imports `deck-clear.ts` nor is on the short exempt list (migrations, `create.ts`, the rollover); TM-INV-07 checks "a deck and a picked target never coexist" over a random list with rollovers — repeating tasks included: a decked repeating task holds no target, is never queued or currently due, and no repeating task is left target-less off deck. **Done keeps a one-off's deck**: a put-back brings it back, and a day that has passed by then is stripped at the next rollover (a repeating task's done completes the decked occurrence instead, above).

Sorted priority, then the NEAREST deadline, then id (A4). Rows carry `segment_state`, `recurring`, `safety_net`, `seen` and the task (`deck_day` is its `on_deck_day`). Never on the page and over target, or in Upcoming, on the same day (TM-INV-10); a future lead day is never after D−1 (TM-INV-11).

## Recurrence Model

RFC 5545 RRULE strings (the iCalendar recurrence rule standard, e.g., `FREQ=WEEKLY;BYDAY=MO`) stored in `task.rrule`. Anchor fields preserve the intended local time across DST (Daylight Saving Time) transitions (e.g., a task due at 9 AM stays at 9 AM local time when clocks change):

- `anchor_time` — time of day
- `anchor_dow` — day of week
- `anchor_dom` — day of month

`computeNextOccurrence()` in `src/core/recurrence/` handles timezone-aware advancement.

**Every repeating task or reminder has a time of day** (Trent, 2026-10-12: "That's supposed to be the default for the day if nothing's set. Nothing should have no time."). A rule that reaches the server without `BYHOUR` — create, PATCH, bulk edit, AI enrichment, the CLI/API, an old client — is stored with `BYHOUR`/`BYMINUTE` added, the time taken from, first match: a date sent in the same request (its local time — "weekly, starting Friday at 7 PM" keeps 7 PM); the task's stored `anchor_time` (a rule with no `BYHOUR` on a task anchored at 10:00 → `BYHOUR=10;BYMINUTE=0`); the task's current `due_at` (a dated one-off made repeating keeps its time); else the user's **Default task time** (`users.morning_time`, "Morning time" in Settings until 2026-10-24 — read from the setting, never a constant). `anchor_time` follows from the `BYHOUR` added, as always. **Quotas are exempt** (`isTracked`, judged on the row the write leaves — a request that makes a task a quota keeps the bare rule, one that retires a quota with a new rule gets a time): a quota's bare period rule (`FREQ=WEEKLY`) names a period, not a moment. A PATCH re-sending exactly the stored rule is no change (a legacy timeless rule sent back is left as it is). One helper, `fillRuleTime` (`src/core/recurrence/rule-time.ts`), called by the three writers: `createTask`, `collectFieldChanges` (PATCH, bulk edit, period moves) and enrichment's `collectEnrichmentChanges` (raw SQL). The web recurrence picker always writes a time, starting from the same order (anchor, the task's date, Default task time) rather than a fixed 9:00. Existing timeless rows are not rewritten by this; reads still treat a rule with no `BYHOUR` as before (the `anchor_time`, else local midnight). Bare `FREQ=WEEKLY`/`FREQ=MONTHLY` are still refused on a task.

**The occurrence apart from the target** (spec §6, rulings Q2/Q3, 2026-10-12). A repeating task keeps its **scheduled occurrence** in `occurrence_at`; `due_at` is its **target**. A move (any snooze, Today, the picker) changes only the target. Done and skip advance from the occurrence and set its dates (`occurrenceDates`): `rrule.after(max(occurrence_at, completedAt))`, so done early (Saturday, for a Sunday occurrence moved to Saturday) brings the following Sunday — never the next day — and a target moved past the next occurrence (a weekly moved +10 days) is allowed: done advances to the next occurrence after now, with no catch-up and no second row. A deadline-anchored repeat's occurrence IS its deadline ([below](#deadline-anchored-repeats)), so the deadline never drifts. A schedule change (a new rule) sets the occurrence to what the rule schedules — and the target with it, unless this occurrence is the user's own (`occurrenceIsPersonal`, PR 4a, 2026-10-22): a target **moved** this occurrence stays where it was (capped at a deadline), and a **deck** stays, its occurrence keeping its day at the new rule's time; one anchor or the other, PATCH or bulk edit. A kept occurrence keeps its `original_due_at` too (the age clock: still the same occurrence); a recomputed one drops it, as before. A repeat waiting in the task queue is not a move (its target was moved on by the rollover): it is recomputed and leaves the queue. A reminder's date is its occurrence (a reminder is never moved, only rescheduled). Put-back (`markUndone`) restores both, from the completion row's `occurrence_at_was`. `original_due_at` is still written — the first target of the current occurrence — for shipped native builds, which read it as the age clock. Migration seed: `original_due_at`, else `due_at` (every advance has written `original_due_at = the next occurrence`, and a snooze kept it).

**The every-N grid** (Trent, 2026-10-12). A rule whose phase **floats** — an "every N" rule (`INTERVAL > 1`: every 22 days, every 2 weeks, every 3 months), or a **bare** rule that names no day (`FREQ=WEEKLY`, `FREQ=MONTHLY`, `FREQ=YEARLY` with no `BYDAY`/`BYMONTHDAY`) — runs on a grid anchored at the task's **own occurrence** — `occurrence_at`, which starts at the task's first date — not at a fixed epoch: every 22 days with a first target of Tue Nov 3 comes next on Nov 25, then Dec 17; a bare weekly whose first date is a Sunday repeats on Sundays. The anchor is period 0 of the grid (its day for DAILY, its Monday-start week for WEEKLY, its month or year for MONTHLY/YEARLY — and its weekday, day of month or date when the rule names none), and each advance writes an occurrence on that grid back to `occurrence_at`, so the grid holds from occurrence to occurrence. Done, skip, the snooze guard and today's occurrence (reminders, and a repeating task with no target) all read it from `occurrence_at` (else `due_at`), never from a moved target; a deadline-anchored repeat's deadline and the Upcoming wait follow the advanced occurrence. A rule that pins its own phase (`FREQ=DAILY`, `BYDAY=SU`, `BYMONTHDAY=1` at `INTERVAL=1`) gives the same days from any start and keeps the fixed 2020 epoch, exactly as before; so does a floating rule on a row with **no date at all** (a quota's bare period rule). Until 10-12 every rule used that epoch, so a first target off its grid made the second occurrence come early (Nov 3 → Nov 13); stored dates were not rewritten — only advances from the fix on use the task's grid. `computeNextOccurrence` (`anchorAt`, `phaseFloats`, `gridDtstart` in `compute-next.ts`) still slides dtstart next to the reference (`advanceDtstart`), so every call stays O(1).

**The creation day is day 0** (Trent, 2026-10-12: "If I create it on a Sunday and it's every 7 days, and I complete it on that Thursday, then it should pop up on the Sunday."). A repeating task given a floating rule **with no date** — created without one, a rule added by PATCH or bulk edit without one, or a rule from AI enrichment — takes its first occurrence from the day the rule is set: that day itself, at the rule's time, if the time has not passed (every 22 days made Mon Oct 12 at 10 AM for 8 PM → Oct 12 at 8 PM), else the next grid point (for 9 AM → Nov 3). Every later occurrence is on the grid anchored there, whenever it is done: made Sunday, done Thursday → Sunday; done late or early → the next grid day, one cycle. A floating rule that names its days can't make an arbitrary day period 0, so its day 0 is the first matching day on or after today: every 2 weeks on Monday made Sunday → tomorrow, then every two weeks; every 3 months on the 1st made Oct 12 → Nov 1, then Feb 1 (never later than the plain weekly/monthly rule would be; made on a matching day after its time → the next grid point). A legacy rule with no time of day (no `BYHOUR`, no `anchor_time`) is at local midnight, which has always passed, so it starts one period on — no new rule is stored that way (every rule has a time, above). Reminders follow the same rule; quotas get no date at all. A rule set with a date anchors on that date, as before — except, for a NEW repeating task, a date already past (earlier today, or any earlier day; designer, 2026-10-16): it starts at its next occurrence instead, keeping the given time (weekly Fri 5 PM made Fri 8:30 PM → next Friday; the 15th of every month dated Oct 15 and made Oct 16 → Nov 15; every 2 weeks → the next grid point; `rollPassedFirstOccurrence`, in `createTask` for every client, and in AI enrichment of a just-created task, which writes its rule onto that task as an update). A date still ahead, a reminder (today's occurrence is still today's), and any later EDIT of an existing task's date (PATCH, bulk edit, re-enrichment of a task that already has a date or rule) are kept as set. Before the ruling the first date came from the epoch's grid (Oct 12, every 22 days → Oct 22; a bare weekly → a Wednesday). `computeFirstOccurrence` in `compute-next.ts`; the client's recurrence preview calls the same function. Bare `FREQ=WEEKLY`/`FREQ=MONTHLY` are still refused on a task by validation (they are a quota's period rule), so on a task the bare case is `FREQ=YEARLY`. AI enrichment pins TODAY's weekday for "every 2 weeks" / "every other week" / "biweekly" with no day named (`BYDAY=TH` on a Thursday), and today's day of the month for "every month" / "every quarter" / "every N months" with no date (`BYMONTHDAY=12` on the 12th; the last day of a month is `BYMONTHDAY=-1`), so those start on the creation day too (Trent, 2026-10-12; `pinUnnamedDay` in `src/core/ai/enrichment.ts`). A yearly repeat in a named month with no day is the exception: it starts on the 1st ("every year in March" → `FREQ=YEARLY;BYMONTH=3;BYMONTHDAY=1`, never March <today's date>; Trent, 2026-10-13; `pinYearlyFirstOfMonth`). "Every year" with no month named is left as the model wrote it, so a bare `FREQ=YEARLY` floats from the creation day. A yearly rule's `BYMONTH` is part of the rule: until 2026-10-13 `parseRRule` dropped it, and `FREQ=YEARLY;BYMONTH=3;BYMONTHDAY=1` ran on the 1st of every month.

**A recurring task carries debt.** Its `due_at` is the truth, past or future: in the future it is the next occurrence (or a moved target); in the past it has been overdue _since then_ and stays overdue — nagged at its priority cadence, across midnight, until done. It does not stop being overdue because a new day arrived. Completing it advances to the next scheduled occurrence after the completion (`from_due`, above), so a Mon/Thu task finished on Tuesday next lands on Thursday. Only a recurring task with no `due_at` derives today's occurrence from the rrule at read time. Reminders (`is_reminder = 1`) are the exception and roll forward: a missed one is not re-shown until its next occurrence. See `effectiveDueAt()` in `src/core/recurrence/occurrence.ts` and REDESIGN-V03 §4.6 (amended 2026-09-07).

`recurrence_mode`: `from_due` (default) keeps the calendar anchor — the next occurrence is the next scheduled one after completion; `from_completion` counts the interval from when it was actually done (e.g. "every 3 months from the last filter change").

**From completion counts from the OpenTask day** (Trent, 2026-10-26). The interval is counted from the completion's **OpenTask date** (`openTaskDayOf`, [The OpenTask day](#the-opentask-day)), not its calendar date, and the rule's time is placed **inside** the landing OpenTask day (`periodOpensOnDate`). With a 3:00 AM day start, Done at 00:30 Monday is Sunday's Done: "every 2 days at 09:00" lands Tuesday 09:00, exactly as Done at 23:30 Sunday does (before: Wednesday from 00:30). Weekly, monthly and yearly rules the same: every week, done Mon 00:30 → the next Sunday; monthly, done Sun Nov 1 00:30 (Saturday Oct 31's) → Nov 30. A 1:00 AM rule with a 3:00 AM start is the END of its OpenTask day: every 2 days from Sunday lands Wed 01:00 (Tuesday's night), so the gap is always N OpenTask days. With a start after 12:00 the same map runs forward: with 11 PM, Sun 23:30 is already Monday, so every 2 days lands Wednesday 09:00. The same step drives Done, skip one occurrence, Skip until (its floor and its walk, [below](#skip-until)) and the rollover's steps, all through `computeFromCompletion` with the user's `dayBoundaryForUser` — so with the task queue's switch off (midnight) every answer is the one it was. The time of day is set as before (the completion moved to the landing date, then set to the rule's time: on a spring-forward night a 02:30 moves on by the gap). Pinned by TQ-LN29–36 (`tests/behavioral/tq-late-night.test.ts`). The deadline walk (`deadlineWalk`, the relative-target checks) steps from one occurrence to the next — the occurrence's own date, which for an occurrence at the rule's time gives the same answer under any day start.

## Deadline-anchored repeats

**2026-10-21.** A repeating task has exactly ONE scheduled instant, `occurrence_at`; its rule (BYHOUR included) walks that instant and nothing else. `repeat_anchor` says what it is:

- `'target'` — the occurrence is the target, and the task has no deadline (every repeat before this);
- `'deadline'` — the occurrence is the DEADLINE: `deadline_at` mirrors `occurrence_at` (I2, kept as a stored mirror so every `deadline_at` reader — the cap, `ELIGIBLE_SQL`, `planLanding`, `deckRefusal`, the bulk tier — works untouched), and the target sits `target_days_before` local calendar days earlier (0 = the same day) at `target_time` (HH:MM), its time optionally following a reminder period (`target_slot_id`). On a repeat they are set only with the anchor `'deadline'`; since 2026-10-24 a one-off with a deadline may carry them too ([Relative targets](#relative-targets)). Never on a reminder or a quota.

**One derivation.** The other dates of an occurrence come from ONE pure function, `occurrenceDates` (`src/lib/task-segments.ts`): the deadline's local date minus the days (Luxon calendar days), at the time, through `localMoment` (`src/lib/opentask-day.ts`, the day start's own rule (`dayStartMoment`): a time the clocks skip → the next valid minute; a repeated one → its first instant), then clamped to the deadline. `due_at` differs from it only when the user moved the target THIS occurrence (`targetMoved`). Every writer that advances or restores an occurrence goes through it — done (and `bulk/complete`), put-back, skip, Skip until, the rollover's and Clear decks' undeck, a deck taken off, the bulk defer cap, the snooze guard, create, PATCH — and a guard test (TM-G01) keeps every SQL writer of `occurrence_at` / `deadline_at` importing it.

**Moves.** A move belongs to this occurrence only, capped at the deadline while it is ahead (as every move). Done and skip always write the next occurrence's derived dates: nothing a move did carries over. Attempts reset only on a new occurrence.

**No default target with the switch on** (2026-10-22, L1): a deadline-anchored repeat written with no offsets (and no `target_at` to take them from) has NO relative target — `target_days_before` / `target_time` NULL, `due_at` NULL, `occurrenceDates` answers `targetAt: null` and a lead day — and each occurrence goes on [the deadlines page](#the-deadlines-page). A target picked on one of its occurrences is that occurrence's alone; `target_at: null` on a repeat WITH offsets removes that one occurrence's target (A5). Switch off, as follows. **The default target** (A1, decided 2026-10-21), when a deadline-anchored repeat is written with none: by the WAIT — the smallest local-day gap between consecutive deadlines — with Upcoming's constants (`deadlineLeadDays`, `leadTargetFor`, `defaultRelativeTarget`): under 2 days, the deadline day at `morning_time` (or the deadline's own time if earlier); 2–7, the day before; 8–15, 3 days before; 16 or more, 4 days before — at `morning_time`. Daily → the deadline day; twice-weekly and weekly → the day before; fortnightly → 3 days; monthly → 4. Stored as real values, so the API always shows what it is.

**Validation** (`relativeTargetProblem`, a 400, never a clamp): the same day at a time later than the deadline's (`after_deadline`, A6); a target on or before the previous occurrence's deadline over the next 60 occurrences or a year (`overlaps_previous`; a from_completion rule is walked as if each were done on its deadline, so its lead must be shorter than its interval). Checked when the rule's walk changes (a new rule or anchor, new offsets, a new mode) — not for a reschedule of one occurrence.

**Writes** (`src/core/tasks/repeat-schedule.ts`; PATCH and bulk edit through `planRepeatSchedule`, create through `createAnchor` / `resolveRelativeTarget`):

The first occurrence is the deadline, or the rule's next one if it has passed (A4, judged on the deadline). The offsets: as sent; else from a `target_at` sent with it; else the default                                                                                                                                               |

**A rescheduled deadline never doubles an occurrence.** Every advance (done, skip, Skip until, the bulk defer cap, the snooze guard) starts from `scheduleBase`: the first rule occurrence on or after `occurrence_at`, then the first one strictly after the later of that and now. On its rule an occurrence is its own base; a deadline pulled from Friday to Thursday has base Friday, so done brings the NEXT Friday, not that one; a deadline pushed past the next rule occurrence covers it. from_due only (from_completion, and target-anchored repeats, advance from `occurrence_at` as before).

**A rule edit over target** on a deadline-anchored repeat keeps the occurrence's day (the debt) at the NEW rule's time — the deadline is never left at a time the rule no longer has. **A decked** one does the same (PR 4a) and keeps its deck, unless the new deadline outranks it (A1). A target-anchored repeat over target keeps its target (and its occurrence becomes that target); a decked one keeps its occurrence's day at the new time, and a moved one keeps its target while the occurrence takes the new rule's first.

**The web editor** (PR 4c) switches the anchor in every-time mode ("Repeats on", or "+ Add" a deadline): see [In the editor](#in-the-editor). AI enrichment never writes a rule onto a task with a deadline (`withoutRuleOnDeadline`, logged); teaching it deadline-anchored repeats is PR 5.

**The rollover** never strips, rolls or waits a deadline-anchored repeat (`ELIGIBLE_SQL` excludes every deadline task); a deck's end gives its derived target back. Notifications fire on the target only — there is no deadline-time push.

**The migration** (`src/core/db/migrate-repeat-anchor.ts`, a `runMigrations` data step after the target-model one, idempotent): every repeat with a deadline still anchored on its target (ordinary, open or not) becomes deadline-anchored at the same local offset — the rule's BYHOUR/BYMINUTE set to the deadline's time (`setRuleTime`), `occurrence_at := deadline_at`, `due_at` left as stored (on schedule it IS the derivation; moved, it is kept), its completion rows' occurrences moved to their deadlines, and `rolled_over_at := now` — the undo fence: an older entry's snapshot of the task holds the old meaning of `occurrence_at`, so undo skips it (`rolledOverSince`; the column now reads "the last system change older entries must not cross"). The rule's DAYS move with the offset too (`shiftRuleDays`: a Wednesday target with a Friday deadline becomes `BYDAY=FR`; the 1st's target with the 3rd's deadline `BYMONTHDAY=3`), proved by walking both rules (`walksShifted`). Skipped and logged on every start, never guessed: no occurrence, a deadline before its occurrence, a from_completion rule, a day shift that can't be expressed or doesn't walk the same (`rule_day_shift`: BYSETPOS, a month day past the 28th, an ordinal weekday crossing a week), an offset the validation refuses. Such a row stays target-anchored WITH its deadline, and its next done or skip drops the deadline (`occurrenceDates` gives a target-anchored occurrence none). `scripts/count-target-migration.ts` prints the ids (`repeatAnchor`).

**Native builds** decode with defaults and read `due_at` (the derived target), `deadline_at` and `occurrence_at`; none compares `due_at` to `occurrence_at`. The rule summary on an Upcoming row shows the deadline's time.

## Repeat ends

"Ends: never / after N times / on date" (2026-10-22, PR A — the server; the editor is PR 4c, enrichment PR 5). The end lives in three columns, **never in the stored rule**:

| Column              | Meaning                                                                                                                                                            |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `repeat_count`      | "After N times": the occurrences in the series, 1..999, counted from when the count was set — the current occurrence is #1 (A3).                                   |
| `repeat_count_used` | Occurrences **closed** since then: every done and every skip adds one (A2: skips count, like RFC COUNT); a skip until passing k adds k; a put-back takes one back. |
| `repeat_until`      | "On date": the last **local** calendar day (yyyy-MM-dd, the owner's zone), inclusive. An occurrence is in the series when its local date is on or before it.       |

The count and the date are exclusive. Only an ordinary repeating task has an end: a reminder (its missed occurrences roll forward at read time, so nothing would consume a count — a date end for reminders is a follow-up) and a quota (its rule is a period) are 400s, and so is a one-off. Responses also carry two derived fields: `repeat_last` (closing the current occurrence ends the series) and `repeat_remaining` (`count − used`, the current one included).

**One judge.** `repeatStep(end, landing, closes, timezone)` in `src/lib/task-segments.ts` (pure, browser-safe) says what closing `closes` occurrences leaves: the series ends when `used + closes >= count`, or the landing's local date is after `until`, or there is no landing; otherwise it lands. `nextOrEnd(task, tz, { completedAt, closes })` is the one-occurrence advance (`scheduleBase` + `computeNextOccurrence` + `repeatStep`), and `isLastOccurrence(task, tz, now)` asks it as if done at max(occurrence, now). **The engine never knows about ends** — `computeNextOccurrence` answers questions that are not advances too (`scheduleBase`, today's occurrence, the deadline walk, the first occurrence), and an end must not turn those into null. Guard RE-G01 (`tests/behavioral/rd-repeat-ends.test.ts`): every caller of the end-blind engine imports the judge or is on a short exempt list, and every SQL writer of `skip_count` / `completion_count` writes `repeat_count_used` too.

**What ends a series:**

- **Done on the last occurrence**: the one-off's write — `done=1`, `done_at`, `archived_at`, stats, attempts reset, queue mark cleared — plus `used + 1`. `due_at`, `occurrence_at`, the deadline and any deck **stay**, so `POST /undone` (the native DONE row) and undo reopen it exactly, `used − 1`, `last_completed_at` from the completion before; the reopen deletes the latest completion row BY ID and its undo entry carries it, so undo re-inserts it and a second reopen never takes an earlier one. The completion row records the occurrence it closed and no next one. `/done` answers `series_ended: true`, `next_due_at: null`; the history reads "Marked "X" done — the last of 6" (or "— the last; it ended Dec 31"); `task.completed` carries `series_ended`. Done on an ended series is a 400.
- **Skip of the last occurrence** (A1, pending Trent — `SKIPPED_LAST_MARKS_DONE` in `src/core/tasks/skip.ts`, the one switch): the one-off skip's write — archived, `done=0`, `skip_count + 1`, never a completion — plus `used + 1`. "Skipped "X" — the last of 6; the repeat has ended". Done, skip and `/undone` on it are 400s; undo reverses the skip.
- **Skip until past the end**: skips what the series had left — a count's `count − used`; a date's occurrences on or before it, re-counted — then ends as a skip (`series_ended` in the response, "· N ended" in the summary).

**What never ends a series:** the rollover (A4). A roll closes one occurrence (a skip, `used + 1`); when that would end the series the task is left **untouched** — the last occurrence stays over target as debt and nags at its priority until the user closes it. A wait released onto an occurrence that an end set during the wait leaves outside the series gives the debt back instead (the target returns to the missed occurrence, stamped `target_set_at` so the days it waited in the queue are not attempts, the queue state is cleared, no skip). Nor the snooze guard or the bulk defer cap: on the last occurrence there is no next one, so no guard and no cap.

**Writing an end** (POST, PATCH; `repeatEndProblem` in `src/core/tasks/repeat-schedule.ts`, pure, judged on the resulting row): `repeat_count` / `repeat_until`, or **COUNT / UNTIL inside `rrule` as shorthand** — lifted into the fields before the rule is validated (`liftRuleEnd` in `src/core/validation/task.ts`), UNTIL's `YYYYMMDD` taken literally as the local day with or without `T…Z` (`T235959Z` is the end of the day in UTC, the wrong day in most zones). A rule sent **without** an end leaves the stored end alone: responses return the rule end-free, so a client echoing it back must not wipe the end. A count set where there was none starts `used` at 0; changing N keeps `used` and must stay above it (A7); setting one end clears the other; `rrule: null` clears all three; a rule change keeps them. An end is judged only when it CHANGES — the same value echoed back (the editor saves the whole draft) is never re-judged, so a passed date on a debt row doesn't 400 a title edit. The date must be today or later, at most 10 years ahead, and — when it or the rule's walk is written — not before the local date of the occurrence the write leaves (a deadline-anchored repeat's: its deadline, A5; a reschedule of this occurrence's deadline past the end is allowed). Bulk edit never sets an end (A11): its `changes.repeat_*` and any COUNT/UNTIL in a bulk rule are 400s. `liftRuleEnds` (a `runMigrations` data step, idempotent) lifts any stored rule's COUNT/UNTIL into the columns at startup — on a reminder or a quota it only strips the end from the rule (logged), since lifted it would refuse every later edit.

**Modes and anchors.** from_completion with a count: each done or skip uses one. from_completion with a date: ends when the next occurrence, counted from the actual completion, falls after it (A6). A deadline-anchored repeat is judged on its occurrence — its deadline — and `scheduleBase` is unchanged.

**Not touched:** Upcoming, notifications and attempts (the last occurrence has a target and behaves normally; an ended series is `done=1` or archived, which every reader already filters out), `todaysOccurrence` / `effectiveDueAt` (reminders only), enrichment and its prompts (PR 5).

## Completion Behavior

- **Recurring tasks** advance in place: completing a daily task moves `due_at` forward and leaves `done=0`
- **One-off (non-recurring) tasks**: when completed, the app sets `done=1` and `archived_at` to the current time
- **A repeat with an end** completed on its last occurrence ends like a one-off — `done=1`, archived, its occurrence kept (§ Repeat ends)

## Skip until

**Skip until [date]** (spec rule 10, task queue PR 4, 2026-10-19): "A tap with the default skips this occurrence; a date skips every occurrence before it (the vacation case)." For repeating tasks only, on one or many at once — `POST /api/tasks/bulk/skip-until { ids, until? }`, `skipUntil` in `src/core/tasks/skip-until.ts`. Mostly driven through AI, so a mixed list is never refused: one-offs, reminders, quotas and done, archived or trashed tasks are left alone and **counted** (`skipped_not_repeating`, `skipped_reminders`, `skipped_quotas`, `skipped_inactive`). An id that does not exist or is not the user's refuses the batch (400), as on every bulk route. There is deliberately no away mode.

| `until`                                           | What happens                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Omitted / null                                    | Exactly `skip-occurrence`: the next occurrence after the scheduled one (after now, when it has passed). One skip.                                                                                                                                                                                                                                                                                           |
| A day (`yyyy-MM-dd`, the user's timezone)         | The task lands on its **first occurrence on or after that day's start**; `occurrence_at` and the target go there. Every occurrence passed over is a skip (`skip_count` += them): the current one — one however long it has been over target — then each later one before the day.                                                                                                                           |
| A day, the current occurrence already on/after it | Nothing is before the day, so nothing is skipped. **Nothing nags before the date**, though: if the target was pulled before the day, it goes back to the occurrence — a plain target move (stamped, queue state cleared, attempts kept, no skip), counted in `tasks_affected` and `targets_moved`. Only a task whose target and occurrence are both on or after the day is left as it is (`already_clear`). |

**On deck** (designer ruling, 2026-10-21 — "skip until Sunday" means nothing _before_ Sunday, and a deck already planned for Monday is part of the after). A decked repeating task has no target (`due_at` NULL, its occurrence kept), so every rule above reads `occurrence_at`, never the null target. **A deck day before the date is cleared** in the same write, `on_deck_day` in the undo snapshot: the task gets a target at its landing occurrence (or, with its occurrence already on or after the date, a target move back onto that occurrence, counted in `targets_moved`) — never a repeating task with neither a target nor a deck. **A deck day on or after the date is kept**: `occurrence_at` still moves to the landing occurrence with the same skip count, but the target stays NULL and `on_deck_day` is unchanged, so the deck now refers to the landing occurrence (with nothing to skip, the task is `already_clear`). No new A1 check is needed: the deadline only moves forward with the occurrence. **"Skip this occurrence"** (no date) and `skip-occurrence` always clear the deck. Undo puts back exactly what the write changed.

**A from_completion rule** (resolution 7): it has no schedule to walk, so it **lands on the date itself, at the rule's time of day** (`anchor_time`, else the rule's `BYHOUR`; placed inside that OpenTask day, `periodOpensOnDate` — the rule Done uses too, [above](#recurrence-model)), and the interval restarts from there — done on that day, the next one is an interval after the completion. **It never lands earlier than "skip this occurrence" would**: the floor is exactly the no-date skip's landing, computed by the same path (`nextOccurrenceAfterSkip`, which `skip-occurrence` uses — for from_completion, one interval on from now's OpenTask date — 2026-10-26). Every 2 weeks, now Mar 4, current Mar 5, until Mar 12: the plain skip lands Mar 18, so it lands Mar 18, not Mar 12. Every 2 days at 09:00 skipped until Tuesday lands Tue 09:00 whether asked at 23:30 Sunday or 00:30 Monday (3:00 AM start; before the fix the 00:30 floor made it Wednesday). The rule's time of day is `anchor_time`, else `BYHOUR`, else local midnight — the same fallback the next Done uses (`ruleTimeOfDay`, `src/core/recurrence/compute-next.ts`), so a Done never shifts the time. Its skip count is the number of interval steps from the current occurrence to the date, as if each had been done on time — stepped like the rollover's, but counted (the rollover adds one skip whatever it steps over).

`until` is tomorrow or later (today is a 400: "skip this occurrence" is the no-date call; the web picker starts at tomorrow), at most 10 years ahead. A from_due rule's occurrences are counted in one rrule.js pass (`occurrencesFromDue`), not stepped; no task may pass more than 5,000 occurrences (no real rule does in 10 years) — past that the request is a 400, never a 500. Each skip is the same write as `skip-occurrence` (`writeRecurringSkip` in `skip.ts`): never a completion (`completion_count` untouched, `task.skipped` webhooks), the deadline moves with the occurrence and caps the target, attempts start afresh, `target_set_at` is stamped, and the queue state is cleared (it is a target write). One undo entry (`bulk_skip`) for the batch with each task's snapshot, one activity row (`skip`, or `edit` for a target move; `metadata.skip_until`, `occurrences_skipped`) per task; after the commit the delivered notifications go, and open tabs and widgets refresh. A batch that skips nothing writes nothing, and the web offers Undo only when something was skipped.

**On the web:** the Quick panel's More menu has **Skip until…** for a single repeating task (the dashboard popover, a task segment row's peek bubble → Open, the task page — nothing on the task-segment rows themselves); the selection sheet (the action bar's More) has a **Skip until…** button under Remove target, counting the selection's repeating tasks when not all of them repeat. Both open the same picker (`SkipUntilDialog`): **Skip this occurrence** (the default), or a day on the calendar. The toast is the server's `summary` ("Skipped 2 tasks until Mon, Nov 2 (14 occurrences) · 1 not repeating") with Undo. Both are disabled while the panel has unsaved edits.

## Snooze

**One "move target" gesture, no snooze state** (spec §6, ruling Q1, 2026-10-12 — Trent: "snooze is just retargeting"; "Just keep snooze" for the word). Every date change of a dated task — the snooze endpoint, bulk snooze, snooze-overdue, notification snooze, the quick panel's buttons and picker, `PATCH { target_at }`, Today — is the same move of the target (`due_at`): the first-target date (`original_due_at`) is kept, the move never touches `deadline_at` or a repeating task's occurrence, and it stops at the deadline (see [Deadline](#deadline)). There is no snoozed flag, no snooze count, no "snoozed from" line, no snooze/re-target split: `retarget` / `reset_original_due_at` from old clients change nothing on a task. "Snooze" stays the word in the UI (the row's button, snooze-all, notifications, widgets, settings), and a user-sent move still counts the daily snooze stat and reads "Snoozed to …" in its toast.

| Change                            | What it is  | `original_due_at`       |
| --------------------------------- | ----------- | ----------------------- |
| Any move of a dated task's target | A move      | Kept (set on first one) |
| A task with no date gets one      | First date  | = the new date          |
| `PATCH { rrule, due_at }`         | Re-schedule | Cleared                 |
| `target_at: null` (no deadline)   | Remove      | Cleared                 |

A task already due at the target is left alone. Bulk snooze follows the same rule as `PATCH` and bulk edit — it goes through the same `collectFieldChanges`. Undo restores the prior `original_due_at`, `occurrence_at`, `target_auto` and `target_set_at`. `default_snooze_option` (the single-tap snooze) also accepts `next_period` (2026-10-10). `PATCH { rrule, due_at }` honors the date and derives the rule's anchors from it, like `createTask`.

**Default reminder slot** (2026-09-28). A reminder created without a schedule — `POST /api/tasks {"title", "is_reminder": true}` with `rrule` omitted and no `due_at`, as an Apple Shortcut or the Reminders quick add sends — is given `FREQ=DAILY;BYHOUR=h;BYMINUTE=m` at the start of the user's default reminder slot (`defaultReminderRule`, `src/core/time-slots/index.ts`), so it never starts in "Anytime". It is still title-only for the enrichment trigger (judged on the caller's input), and enrichment with no time cue keeps it in that slot. The setting is `users.quota_prompt_slot_id` (API alias `default_reminder_slot_id`) — the same default quota prompts use, resolved the same way (`resolvePromptSlot`: the stored slot, else the first period). An explicit `rrule: null` stays unscheduled (a one-time reminder); a supplied rule is used as sent; a user with no slots gets no default.

**Reminders** (`is_reminder`) are never snoozed: the snooze endpoint refuses them, bulk snooze skips them, and a bare `PATCH { due_at }` that would move a dated reminder is refused too. An explicit reschedule (`reset_original_due_at: true` — the one place that flag still means something; a period move sends it) is allowed and moves the reminder's occurrence with its date, as is giving an undated reminder its first date. `skip-occurrence` refuses reminders — a missed one rolls forward on its own, and completing one marks it considered.

## Quotas and completion

A quota (`isTracked`: `is_tracked` or `progress_target > 1`, one definition in `src/lib/track.ts`) is counted within its period; its period boundary resets `progress_current`. Marking one **done** closes the period early and zeroes the count, so `markDone` refuses a quota unless the caller passes `close_period: true`, and `bulkDone` skips quotas (reporting `quota_skipped`) unless the same flag is set — refusing only when the batch is nothing but quotas. No app surface completes a quota; they log progress (`POST /api/tasks/{id}/progress`).

**A quota always has a period** (Trent, 2026-09-25): its rule names a day, week, month or year (`quotaPeriodOf`). With no period there is no boundary, so the count would never reset and a met prompt would never return. Create, PATCH and bulk edit refuse a result that is a quota without one (`QUOTA_PERIOD_MESSAGE`, 400) — `rrule: null` on a quota, or making a task a quota without a rule; a bulk edit that would do it to any row is refused whole. A legacy period-less row (none in production) is still read harmlessly and stays editable while a write leaves its rule alone.

**A quota from words** (2026-10-24, quota enrichment): one exception at create. `{"title": "eggs twice a week", "is_tracked": true}` with NO `rrule` key is stored at once with a **provisional period** — `FREQ=WEEKLY` (`QUOTA_PROVISIONAL_RULE`), target 1, anchored as usual — when AI enrichment will run for it (AI on, the owner's enrichment mode not Off, title-only: a `progress_target` above 1 counts as structured input). Enrichment then sets the count, the period and the reminder period from the words through the ordinary edit path (`applyQuotaEnrichment`, so the re-anchor and its count carry apply), and keeps the weekly period when the words name none. Without enrichment it is the 400 above, which then also says to turn AI on; an explicit `rrule: null` is always the 400. The kind is the caller's to declare: nothing reads a task's words to make it a quota. See docs/AI.md § Enrichment → Quota enrichment.

**Interval quotas** (2026-10-16): a quota's period can span several units — `FREQ=WEEKLY;INTERVAL=2` is "every 2 weeks". The rule is written `FREQ=X;INTERVAL=N` (INTERVAL omitted at 1; the reverse order is refused) and capped for a quota at 1–30 days, 1–12 weeks or 1–12 months, a yearly quota being every year (`QUOTA_INTERVAL_MAX` in `src/lib/track.ts`, the editor's stepper range too; `QUOTA_INTERVAL_MESSAGE`, 400, on create and on any edit that sends the rule — a stored rule outside it stays editable while the edit leaves it alone).

- **The anchor** (`progress_period_start`) is the start of the calendar unit the owner is in — this week's first day (`week_start`), the 1st, midnight, Jan 1 (`quotaUnitStart`) — **stamped when the row becomes a quota** (create, or an edit converting it; `quotaAnchorNow`), no longer left for the rollover's first pass. A fortnight made on a Tuesday starts on that week's Sunday and runs two weeks; the next starts where it ended (the rollover steps `start = end`).
- **A period edit re-anchors** (FREQ or INTERVAL changes): to the current unit's start, inside the edit's transaction and undo entry, so undo restores the old rule, anchor and count together (`collectQuotaAnchor`, `src/core/tasks/helpers/collect-field-changes.ts`). The count becomes the taps logged since the new start, never more than it was (`min(progress_current, loggedSince(start))`): weekly → monthly keeps this week's taps (earlier weeks are already recorded), monthly → weekly keeps only this week's. The part of the old window before the new start is **not** recorded as a short period (its taps stay in `progress_events`) — recording would write rows undo cannot take back. A period that had already ended is closed by the rollover first (`settleQuotaPeriod`). Before this, weekly → monthly kept the Sunday anchor and its months ran the 11th to the 11th for good.
- **Served, not re-derived**: every task read carries `progress_period_end` (the current window's exclusive end, stepped past a period the cron has not closed yet), `period_interval`, `period_last_day` (end − 1 day, local) and `period_label` — "by Oct 24" above interval 1, **null at interval 1**, where clients keep "this week" / "today" (`quotaPeriodFields`, computed in `rowToTask` in the owner's clock). Prompts carry the same as `period_interval`, `period_end`, `period_last_day`, `period_label` beside the bare-FREQ `period`. Older native builds ignore them and say "this week" for a fortnight — wrong words, nothing worse.
- **Where they show**: the Track panel and the native Quotas widget give each (FREQ, INTERVAL) pair its own section ("Every 2 weeks"), with no shared clock — two fortnights can end on different days — and each chip/row carries its own "by Oct 24". Interval-1 sections keep their notch and "N days left". Prompts are unchanged: one a day until met, under the quota's own "Remind me daily" switch.
- **Week start changed mid-window**: a weekly window off the new boundary ends at the next boundary (a short **transition** period, `quotaPeriodEnd`, marked on its record and, unmet, breaking no streak), and fortnights run from there — the phase moves. Accepted; the served label shows the short period's real end. (A day-start change is different: it moves the bounds, never the phase — § The OpenTask day.)

A quota's completions are the period rollover's (`period-rollover.ts`): a met period closes into a completions row. `markUndone` (`POST /api/tasks/{id}/undone`) refuses a quota — putting one back deleted that record while the period stayed closed. Correct the count with a −1.

A quota's **record** — periods met and missed, the current and longest run of met periods — is read from `progress_periods` alone (`getQuotaStats` in `src/core/tasks/quotas.ts`, `GET /api/tasks/{id}/quota-stats`), never `completion_count`, which a task converted into a quota carries over from its life as a plain task. Only closed periods count. The web shows it in a quota chip's hold bubble (2026-10-16, replacing the Quotas page's Details list).

**Which period a count belongs to** (2026-09-24). The rollover cron runs every few minutes, so for a few minutes after a boundary a quota still carries the old period's count. Readers deciding what today looks like use `effectiveProgress()` (`src/lib/track.ts`), which reads an expired period as 0; writes (`incrementProgress`, prompt actions) run that quota's rollover inline first (`rolloverQuotaNow`), so a +1 at 00:02 counts for the new day. `progress_events` records the delta actually applied (a −1 at zero records nothing).

**Undo across a period boundary is a no-op.** Progress snapshots carry the period they were counted in (a `_period_start` witness; `createQuotaSnapshot`). Undo and redo skip a snapshot whose quota has since moved to a new period — they do not refuse, because a throw inside `undoEntry` would roll back the `undone` flag and wedge the undo stack. The entry is still marked undone.

## Quota reminders (prompts)

Every unmet quota also appears as a **prompt** in a reminder period (time slot) each day, so quotas get the attention reminders get (2026-09-24; `src/core/tasks/quota-prompts.ts`). Prompts are computed at read time — nothing is stored per prompt — and arrive in `GET /api/reminders` `groups[].prompts`, a separate array from `reminders` (which, with its counts, is unchanged). Identity: `prompt_key` = `q:<taskId>:<k>:<date>`.

- **Daily** quota (FREQ=DAILY, no INTERVAL), target N: numbers 1..N spread one per period from the quota's period, clamping at the last period; each number's period can be set in the editor. One row per quota per period, standing for the highest number there (`k`); done once today's count reaches `k`. The label shows progress ("Piano Scales · 1/2").
- **Every other** quota (weekly, monthly, yearly when enabled, daily with INTERVAL > 1, and every interval quota — "every 2 weeks" prompts exactly as a weekly one does, Trent 2026-10-16): one prompt a day. Done for today once any progress is logged today from anywhere; gone until the period resets once met.
- **The day** (2026-10-23): "today" for prompts — their list, the day record (`quota_day_state`), the `<date>` in every `prompt_key` and the actions' stale-key check — is the OpenTask day with the task queue's switch on (`promptDate` with `dayBoundaryForUser`), else the calendar day. A daily quota's count period ends at the same day start, so a prompt's "done" and its key turn together.
- Defaults: on for daily/weekly/monthly, off for yearly (and for a legacy period-less row, which can no longer be created — see below); `quota_prompt_config.enabled` overrides. Only the user's own quotas (never another user's shared-project quota).
- Off switches: the user's `quota_prompts_enabled` preference, and `OPENTASK_QUOTA_PROMPTS=off` on the server. Either empties every `prompts` array and takes prompts out of the notifications.
- **Notifications**: a waiting prompt (not considered, not done) counts exactly like a reminder in its slot's push and in the slot nag. A slot with only prompts still notifies, and a slot stays unfinished until its prompts are handled. The body counts both, e.g. "3 reminders · 2 quotas waiting". Prompts are never in the app-icon badge. See `docs/NOTIFICATIONS.md` § Time-slot notifications.
- **Priority paces the slot nag** (Trent, 2026-10-22; REDESIGN-V03 §6 as amended): a reminder's priority, and a prompt's quota's priority, is prominence AND how often its slot nags. The one slot nag repeats at the shortest considering rung (the user's overdue tier ×2 — Urgent 10, High 30, Medium 120, Low 480, Unset 60 minutes by default) among every waiting reminder and prompt it covers; finishing the fast item drops it back to the next rung. Never a nag per item. See `docs/NOTIFICATIONS.md` § The slot nag.
- **Where**: slot ids are stored (the quota's `quota_prompt_config.slot_id` / `numbers`, the user's `quota_prompt_slot_id` — the default reminder slot, which also places new reminders) and resolved at read time: the quota's slot, else the user's default, else the first period of the day (`resolvePromptSlot`). Retiming a slot keeps its id, so its prompts follow it. **Deleting a slot moves its prompts the way it moves its reminders** (2026-09-25): every stored id naming it is repointed to the remaining slot nearest the removed slot's start, in the delete's own transaction and undo entry (`deleteTimeSlot`, `src/core/time-slots/edit.ts`), so one Undo restores the slot, its reminders and its prompt placements. Only stored ids move — a daily quota's never-placed numbers re-spread over the remaining periods. The read-time fallback past a missing id remains only for ids left stale by deletes made before that rule. A write naming a slot id the stored config does not already name must name one of the quota **owner's** periods (`assertPromptSlotsOwned`, 400 otherwise); stale ids already stored are left alone, so such a quota stays editable.
- **Moving a prompt** (2026-09-25): the prompt's hold bubble on the web and a press-and-hold on the watch offer the user's periods; one tap is a `PATCH /api/tasks/{id}` of the merged `quota_prompt_config` — the quota editor's own write, so one undo entry. A non-daily quota gets `slot_id`. A daily row moves only the numbers it stands for (`groups[].prompts[].numbers`, e.g. `numbers: {"1": <slot>}`); the quota's other numbers stay put. Each prompt also carries the `slot_id` it sits in.
- **Several quotas at once** (2026-09-25): the quota editor's multi-edit (several quota prompts selected and opened together; the Quotas page's Details list, its other way in, was removed 2026-10-16) has "Remind me daily" (on / off / mixed "—") and a "Reminds me in" period row, and sends only what changed through `POST /api/tasks/bulk/edit` — one undo entry. There, and only there, `quota_prompt_config` is **merged** over each quota's stored config (`mergePromptConfig` in `src/core/tasks/bulk.ts`): `enabled`/`slot_id` replace that field, `numbers` replaces the map and `{}` clears it. Choosing a period sends `{slot_id, numbers: {}}`, so a daily quota's numbers spread from that base exactly as a fresh one's do.

Two actions, because ticking a reminder means "considered", not "did it" — and a way back from either:

| Action                                                          | Endpoint                                                                       | Effect                                                                                                                                                                    |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Consider (the circle; every "Considered all")                   | `POST /api/quota-prompts/consider`, or a bare key in `bulk/complete` `prompts` | Handled for today; no progress                                                                                                                                            |
| Did it (the square checkbox)                                    | `POST /api/quota-prompts/did`, or `{ key, did: true }` in `bulk/complete`      | Daily #k: count raised to ≥ k. Others: +1 unless this key was already done today — progress logged elsewhere today does not block it (Trent, 2026-09-25). Also considered |
| Put back (the filled dashed circle in a considered / DONE list) | `POST /api/quota-prompts/restore`                                              | Waiting for today again: the key leaves `considered` and `did`, and a did-it's progress comes off — exactly what it added                                                 |

Each is one transaction and one undo entry (`quota_prompt`, or the `bulk_done` entry of a mixed batch). The owner's day lives in `quota_day_state` (`{date, logged, did, considered, did_applied}`), written in the same transaction as the count and by every `incrementProgress`, and restored by undo — so undoing a +1 or a did-it brings the prompt back. Keys for another local day are refused (400).

**Putting a prompt back** (2026-09-25). A handled prompt is listed with the reminders in the web's "Show N considered" lists and the Reminders widget's DONE section; its filled dashed circle puts it back — never `/undone`, which a quota refuses.

- **What comes off.** `did_applied[key]` records what each did-it added to the count, accumulated, so a repeat did-it (which adds 0) keeps the first one's record. Daily #k adds only what was missing up to k, so a did-it that found the count already at k added 0, and its put-back takes 0: the row is un-handled but, with the count still at k, stays done. A did-it recorded before `did_applied` existed reads as 1 for a once-a-day prompt (its first did-it always added exactly 1) and 0 for a daily numbered one (not recoverable; the count is left alone rather than guessed).
- **Cascade.** A did-it the lower count no longer supports waits again with it (below).
- **No-op.** A key already waiting changes nothing, but the request still logs an undo entry, as a −1 at zero does, so a toast's Undo never reaches an older action.

**A −1 that takes back a did-it** (2026-09-25; settles PR #92's open question). When the count drops so a did-it no longer holds, that prompt waits again: its key leaves `did`, `considered` and `did_applied` (`withLogged`, `brokenDids` in `src/lib/quota-prompts.ts`). A daily #k did-it holds while today's count is at least k. Any other quota's holds while anything is still logged today. A prompt that was only considered stays considered through a −1.

## Over target (overdue)

"Over target" in the UI, "overdue" in the code and the API. Everywhere — the badge, the notifier, the snooze-overdue sweep and `GET /api/tasks?overdue=true` — it is `getCurrentlyDueTaskIds` (`src/core/tasks/currently-due.ts`): reminders and quotas are never over target, and a recurring task's due-ness is derived from its schedule (`effectiveDueAt`). Since 2026-10-12 a deadline's target is stored (`target_auto`, see [Deadline](#deadline)), so these queries — and the client counts (`countTasks`, `src/lib/task-counts.ts`) — read `due_at` alone again: a deadline task joins at its automatic target like any other. (From 2026-10-10 to 10-12 they computed an implied target at read time; that is gone.)

## Native builds

Shipped iOS / watchOS / Mac builds (including ones not yet reinstalled) decode every task field with defaults, and still run their own copy of the old implied-target rule (`TargetAge.swift`). The server keeps them correct without a rebuild: every deadline task now carries a stored target at or before its deadline, and `deadline_nag_off` is `false`, so their rule finds nothing to imply and reads `due_at` as the target — the server's own answer. The one exception is a one-off whose deadline has passed and whose target is after it (allowed since 2026-10-12): the response sends `deadline_nag_off: true` for it (computed, never stored), because their rule leaves a nag-off task with a passed deadline to its own target — without it they would imply a target 4 days before the deadline and show it over target. `original_due_at` keeps its meaning (the first target of the current occurrence, their age clock). `is_snoozed` and `snooze_count`, which no build decodes, left the response. `target_auto`, `occurrence_at` and the badge fields (`attempts`, `attempts_label`, `attempts_offer`, `age_label`, …) are new and ignored by them — they still draw their own "2d" age tab from `original_due_at` until rebuilt. A capped quick snooze still answers `capped_at_deadline` / `capped_deadline`, and `skipped_deadline` stays (now: held back like High because the deadline has passed — their sweep summaries ignore it); `skipped_recurring` stays, always `[]`.

## Updating Recurrence Rules

Updating `rrule` also re-derives `anchor_*` fields and may recompute `due_at`. When logging this for undo, include all derived fields in `fieldsChanged` so undo restores the complete prior state:

```ts
const fieldsChanged = ['rrule', 'anchor_time', 'anchor_dow', 'anchor_dom', 'due_at']
```

## Undo System

Functions from `@/core/undo`:

```ts
logAction(
  userId: number,
  action: UndoAction, // 'done' | 'undone' | 'snooze' | 'edit' | 'delete' | 'create' | 'restore' | 'bulk_*' | 'progress' | 'skip' | 'bulk_skip' | 'time_slot_*' | 'quota_prompt' | 'task_segment' | 'task_rollover'
  description: string | null,
  fieldsChanged: string[],
  snapshots: UndoSnapshot[],
  slotState?: SlotUndoState, // only for 'time_slot_edit' | 'time_slot_delete'
): number
```

**Time slot entries (2026-09-24).** Moving a time slot's start or removing a slot moves that slot's reminders (a reminder belongs to a slot only through its time of day). Those two changes log `time_slot_edit` / `time_slot_delete`, whose task snapshots are the moved reminders (and, for a delete, the quotas whose `quota_prompt_config` was repointed to the nearest slot, 2026-09-25) and whose `slotState` (`undo_log.slot_state`) is the slot row before/after, plus `prompt_default` when a delete repointed the user's default prompt period. Undo and redo write the slot row (and that default) back in the same transaction, so one Undo restores the slot together with its reminders and prompt placements — a deleted slot comes back under its original id. See `src/core/time-slots/edit.ts`.

- `createTaskSnapshot(beforeTask, afterTask, fieldsChanged, completionId?)` — build an `UndoSnapshot`. See [Critical Requirements](../AGENTS.md#every-mutation-must-be-atomic-and-logged-for-undo) for usage details and the `completionId` pattern.
- `executeUndo(userId)` — restores the task to `before_state` from the most recent undoable action
- `executeRedo(userId)` — re-applies `after_state` from the most recent undone action

Undo history is per-user and works as a stack (last action undone first).

**Fences.** A snapshot is skipped (the rest of the entry still applies) when the task has moved on since the entry: a quota count from a period that has closed (`periodMoved`), and a task the task queue's rollover changed after the entry was written (`rolledOverSince`, see [The rollover](#the-rollover)).

## Task Access

`canUserAccessTask(userId, task)` from `@/core/tasks` — returns `true` if the user owns the task or it's in a shared project. Use this in route handlers that need to verify access.
